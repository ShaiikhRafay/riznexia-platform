## [0.6.0] - 2026-08-04

Milestone: Modules M1 through M9 complete (Lead Discovery through Website Preview) — the full pipeline from raw Google Places discovery through a validated, publish-readiness-scored, previewable generated website. Tagged `v0.6.0`.

### M9 — Website Preview

- **Added:** New `packages/website-preview` package — a read-only module with zero import of `packages/website-generator`'s generator functions (structurally enforces "never regenerates"). `ast-inspect-helpers.ts` parses `GeneratedWebsite.files`' already-printed TypeScript source back into a real AST (`ts.createSourceFile()`), the exact read-only mirror of `website-generator`'s AST-building helpers. `color-contrast.ts` computes a real WCAG relative-luminance contrast ratio from two hex colors — not a heuristic.
- **Added:** Five independent validators, each owning exactly one rule category, none calling another (founder's explicit Decision 3): `structuralValidator` (missing pages/assets/routes, broken internal links, broken image references), `contentCompletenessValidator` (every M8.3-bound content field is non-empty), `seoValidator` (title/description/keywords/canonical/OpenGraph/Twitter Card/JSON-LD LocalBusiness/Organization/FAQPage/BreadcrumbList value-completeness), `accessibilityValidator` (skip-link, landmarks, alt text, heading hierarchy, keyboard-operable navigation, a real WCAG AA contrast-ratio check, focus-visibility, WCAG 2.5.5 minimum touch target), `performanceValidator` (next/image usage, priority loading, a client-bundle-size proxy, static-generation eligibility, `prefers-reduced-motion` respect — deterministic proxies only; explicitly never runs Lighthouse or any live tool).
- **Added:** `validator-registry.ts` — `VALIDATOR_REGISTRY`/`runAllValidators()`, the founder's Future Compatibility extensibility point: a future validator (Security/Legal/Cookie/Brand/Broken-Link, per the founder's own examples) is added as one new file plus one registry entry, with zero changes to any existing validator.
- **Added:** Every `ValidationRuleResult` carries all eight founder-required fields — ruleId, ruleCategory, ruleName, severity, status, message, recommendation, and a `documentationUrl` field reserved for future use (always null today, no docs site exists yet).
- **Added:** `generateWebsitePreview()` — a read-only file-manifest/business-summary view of an already-assembled `GeneratedWebsite`; businessName is read back out of the generated site's own JSON-LD (same technique M8.4 used for its own `package.json` naming). `aggregateReadiness()` — a pure fold over an already-computed rule list into six scores (SEO/Accessibility/Performance/Content Completeness/Structural Integrity/Overall), each explaining exactly why points were deducted via a `deductions[]` list naming the responsible rules (founder's explicit requirement) — never touches `GeneratedWebsite.files` or calls a validator itself.
- **Added:** New `WebsitePreview`/`PreviewReport`/`PublishReadinessReport` schema (`packages/shared-types/src/website-preview.ts`) and Prisma models — each independently versioned per business, each carrying the same 5-field metadata envelope (previewVersion/generatedWebsiteVersion/validationVersion/generatedByModuleVersion/createdAt), and — per the founder's explicit Decision 1 ("all reports must be generated independently") — none FK'd to each other.
- **Added:** `website-preview` module (`apps/api`) — `GET /leads/:id/preview`, `/preview/validation`, `/preview/readiness`. No POST anywhere in this module (unlike every M6-M8 phase): validation has no external cost to gate behind an explicit generate step, so each GET computes fresh and auto-caches, regenerating only when `GeneratedWebsite.configVersion` has advanced (founder's Decision 2). All three gated by a new dedicated `website:preview` permission (founder's explicit Decision 4: not a reuse of `website:assemble`) — unlike M6-M8's GETs, these require the module permission rather than `leads:read`, since a GET here triggers real computation. New `GeneratedWebsiteNotFoundException` (`GENERATED_WEBSITE_NOT_FOUND`, 404).
- **Added:** Structured logging for "Preview Opened" / "Validation Started" / "Validation Completed" / "Publish Readiness Generated", per the founder's explicit requirement.
- **Fixed (found via testing, not assumed correct):** the initial broken-internal-link check read `app/page.tsx`'s literal JSX attributes — but the real M8.4 templates spread props (`{...props}`) rather than printing literal `id`/`href` attributes, making the original check vacuously pass on every real generated site. Fixed to read the real values out of `lib/site-data.ts` instead, where they actually live.
- **Docs:** The module brief (objective, inputs, outputs, device preview modes, the full four-category validation checklist, per-rule field requirements, deterministic-only performance readiness) was given up front, architecture was presented and approved (including an AskUserQuestion-resolved fork on the rendering mechanism — structural/data preview only this phase, no live rendering server), followed by four explicit founder Decisions refining the approved architecture before implementation. See DECISIONS.md D-075 through D-081.
- **Tests:** 69 new `packages/website-preview` tests (new package); 15 new `apps/api` unit tests (399 total, up from 384); 15 new `packages/shared-types` tests (155 total, up from 140). New `apps/api/test/preview.e2e-spec.ts`, 12 tests including the full real (unmocked) preview/validation/readiness flow and an explicit independence assertion (166 e2e total, up from 154).
- **Not built, deliberately:** live visual rendering of the preview (an actual running instance a user can look at) — explicitly deferred to a future infrastructure decision, per the founder's chosen architecture option. AI generation, HTML/React/Next.js generation, website regeneration/modification/deployment — none of which this module performs, per explicit instruction.

### M7 — Theme Engine

- **Added:** New `packages/themes` package — `ThemeProvider` interface + `THEME_PROVIDER` DI token (registry-shaped: every registered theme is simultaneously available, unlike M5/M6's single-active-implementation provider abstractions); `StaticThemeRegistry` the sole implementation; 8 named theme definition modules (Restaurant, Salon, Dental, Law Firm, Gym, Real Estate, Medical, Corporate), each a versioned code module carrying name/version/hash/createdAt/updatedAt (hash computed from content at load, same technique as M6's `PROMPT_HASH`).
- **Added:** Deterministic compatibility scorer (`packages/themes/src/scoring/`) — 5 weighted checks (industry, layout, accessibility, mobile, component availability) per theme; `rankThemes()` scores every registered theme and returns only those clearing the minimum compatibility score, sorted descending. An empty result is the founder's explicit contract: `THEME_NOT_FOUND`, never a forced bad fit.
- **Added:** `AiService.recommendThemeCategory()` (`packages/ai`) — the "AI recommends" half of "AI recommends, rules validate." A single lightweight classification call (new `theme-recommendation/v1.0` prompt template), transient-retried only, no repair-prompt ladder or model escalation. Never throws — any failure resolves to a typed `failed` outcome so rule-based ranking always has a working zero-AI-dependency fallback path.
- **Added:** `BusinessAnalysis.brandBrief`'s `colorPalette`/`typography`/`layoutStyle`/`industry` flow through into `ThemeConfiguration` verbatim — theme selection never regenerates or overrides brand-identity fields M6 already produced. Only structural/presentational fields (component set, navigation/hero/CTA/card/footer style, animation level, image style, section order, accessibility profile, mobile preferences) come from the selected theme.
- **Added:** `ThemeConfiguration` schema — versioned per business like `BusinessAnalysis` (never overwritten), FK'd to the exact `businessAnalysisId` it was derived from, full theme-versioning provenance (`themeName`/`themeVersion`/`themeHash`/`selectedAt`/`selectedByEngineVersion`/`compatibilityScore`), and the complete ranked-theme list stored as JSON for a future manual-override feature. 7 new Prisma enums for the structural fields.
- **Added:** `theme-engine` module — `GET/POST /leads/:id/theme`, gated by a new dedicated `theme:select` permission (not a reuse of `business:analyze` — theme selection is its own independent, cost-bearing capability with its own future extensions: premium themes, a theme marketplace, manual override, an approval workflow, agency-specific themes). Runs synchronously (unlike M6's fire-and-forget dispatch) and is cached per `businessAnalysisId`.

A ceiling-exceeded rejection is handled by the exact same resilience path as any other AI failure (D-046) — theme selection still succeeds, rules-only, and the new fields stay `null`. The cost-computation formula was extracted out of `BusinessAnalysisRunnerService` into a new shared `apps/api/src/common/cost/ai-cost.util.ts` so M6 and M7 call the same function rather than each carrying their own copy. See DECISIONS.md D-048.
- **Docs:** The architecture was presented and approved in two rounds — an initial ThemeProvider/rule-based-selection design, then a founder follow-up locking the brand-field sourcing, the permission choice, four additional required `ThemeConfiguration` fields, the compatibility-validation gate, and the full-ranking requirement.
