## 2. Pre-Implementation Architecture Review

Before any code was written, existing infrastructure was audited first — a genuine naming collision was found: `packages/db/prisma/schema.prisma` already has a `Website`/`WebsitePage`/`GenerationJob`/`Deployment` scaffold from Module M2, unused by any module built since, and that legacy `Deployment` model FKs to the legacy `Website` model, not `GeneratedWebsite` (M8), which the founder's live brief names as the actual input. Unlike M10's roadmap conflict, this was not a scope question requiring the founder's judgment — the brief is unambiguous about what M11 deploys — so it was resolved directly (a new `WebsiteDeployment` model, distinctly named, legacy scaffold untouched) and presented as part of the architecture rather than raised via AskUserQuestion.

A full architecture (data model, provider abstraction, lifecycle state machine, five engines and their dependency graph, API design, validation strategy, permission model) was then presented and approved, followed by ten explicit numbered founder Decisions refining it further, all incorporated before implementation:

- **Decision 2 (Provider Architecture)** — resolved by mirroring `LocationProvider` (M5) exactly: one interface, one DI token, `VercelProvider` fully implemented via a real `VercelAdapter`, four reserved provider classes that genuinely implement the interface (provably a one-line `useClass` swap away from active) but throw until a real adapter backs them (D-093).
- **Decision 3 (Immutable Deployments)** — resolved by giving `DeploymentStatus` no "rolled back" value at all; rollback and retry both create a new row via self-referencing FKs (`rollbackFromDeploymentId`/`retryOfDeploymentId`) and funnel through the exact same orchestration method, so neither can accidentally diverge from the normal deploy pipeline's own validation/logging/health-check behavior (D-094).
- **Decision 4 (Publish Validation)** — resolved by calling `WebsitePreviewService.getValidationReport()` directly (newly exported from `WebsitePreviewModule`) rather than re-running validators; "required assets exist" was recognized as already covered by the Structural Integrity validator's own rules, so no second check was built for it (D-097).
- **Decision 5 (Health Checks)** — resolved by making the reachability check a plain HTTP request against the deployment's own `liveUrl`, never a call through `DeploymentProvider` — the Health Check Engine has zero dependency on `ProviderModule` (D-095).
- **Decision 6 (Domain Engine)** — resolved by modeling `Domain` as a mutable, long-lived pointer (unlike immutable `WebsiteDeployment` rows) and making `attachDomain()` best-effort: a missing provider capability or a failed call leaves the row `PENDING` rather than blocking domain registration (D-096).
- **Decisions 8/9/10 (Versioning/Logging/Future Compatibility)** — resolved as direct field/logging/reservation lists with no architectural fork to resolve; documented in D-099, D-100, D-101 respectively.

Full reasoning: `DECISIONS.md` D-092 through D-102.

## 5. `WebsiteDeployment` Field Reference

| Field                                              | Source / Computation                                                                              |
| -------------------------------------------------- | ------------------------------------------------------------------------------------------------- |
| `deploymentVersion`                                | Server-computed, `max` existing for the business `+ 1`, never client-supplied                     |
| `deploymentHash`                                   | sha256 over the deployed file set, sorted by path first for determinism                           |
| `deploymentEngineVersion`                          | `DEPLOYMENT_ENGINE_VERSION` constant, this module's own orchestration version                     |
| `provider` / `providerVersion`                     | Read from the injected `DeploymentProvider` instance's own `name`/`version`, never hardcoded      |
| `status`                                           | `REQUESTED → VALIDATING → IN_PROGRESS → COMPLETED`, or `→ FAILED` — no "rolled back" value        |
| `healthStatus`                                     | Denormalized from the latest `DeploymentHealthCheck`, maintained by the Health Check Engine       |
| `rollbackFromDeploymentId` / `retryOfDeploymentId` | Self-FKs set only on the _new_ row a rollback/retry creates — never mutated onto a historical row |
| `executionDuration`                                | `completedAt - buildStartedAt`, in milliseconds                                                   |
| `liveUrl` / `providerDeploymentId`                 | Populated from the provider's `deploy()` result on success, `null` until then                     |
| `errorMessage`                                     | Populated only on `FAILED`, from the caught provider error                                        |

## 6. Security Review

- **AuthZ** — every mutation across all five engines is gated by the specific permission it needs: `deployment:create` for requesting/retrying a deployment, `deployment:rollback` for rolling back only, `deployment:manage` for domain registration and manual health-check triggers, `deployment:view` for every read. Verified: a `sales_executive` (holds `view`/`create` but not `rollback`/`manage`) gets 403 on rollback, manual health-check trigger, and domain registration; `developer`/`viewer` (hold `view` only) can read history/status/health but cannot mutate anything.
- **Provider credential handling** — `VERCEL_API_TOKEN`/`VERCEL_TEAM_ID` are read via `ConfigService`, never logged, never included in any response body; `DeploymentProviderUnavailableException` is thrown before any deployment row is even created when credentials are absent, so an unconfigured environment fails closed rather than silently attempting a call.
- **No secrets in `WebsiteDeployment`/`Domain` rows** — `providerDeploymentId`/`liveUrl`/`verificationRecord` are all provider-returned identifiers/metadata, never credentials.
- **Trust boundary — no client-controlled provider/environment selection** — `createWebsiteDeploymentSchema`/`createDomainSchema` structurally have no `provider`/`environment` fields; a client cannot request deployment against an arbitrary provider or target a non-production environment this phase, verified by a shared-types test asserting an injected `provider`/`environment` key is silently stripped, never reaching the service.
- **SSRF surface** — the Health Check Engine's reachability check fetches `WebsiteDeployment.liveUrl`, a URL this system itself generated via the deploy call (provider-returned, not client-supplied), not an arbitrary user-provided URL — same trust level as the pre-existing `WebsiteFetchAdapter`'s own SSRF guard already established elsewhere in this codebase for genuinely externally-supplied URLs.
- **Bounded context integrity** — verified structurally: the Health Check Engine has zero import from `ProviderModule`; the Domain Engine's provider call is strictly best-effort and never blocks core domain-row creation.

## 7. Known Limitations (flagged, not hidden)

- The migration has not been run against a real Postgres instance, and no real deploy has been made against Vercel's live API — same constraint as every prior module; `VercelAdapter`'s tests mock `fetch` itself.
- **`WebsiteDeployment.create()`'s next-version computation has the same race-condition class already accepted for `SalesProposal.version` (M10)** — two concurrent `POST`s for the same business could compute the same `max + 1` and collide on `@@unique([businessId, deploymentVersion])`. Same acceptable-scope reasoning: an internal sales tool, not a high-concurrency public system.
- **`Domain.sslStatus` is a simplification, not a real SSL check** — it flips to `ACTIVE` alongside `verificationStatus` on verification rather than polling a dedicated "check SSL" provider endpoint, since Vercel auto-provisions SSL the moment a domain verifies and Decision 6 explicitly rules out building SSL-issuance/verification logic in this module regardless.
- **Health checks are point-in-time, not scheduled** — a check runs automatically once right after a deploy completes, and otherwise only on demand via `POST .../health-check`; nothing periodically re-checks a deployment's health in the background (no job scheduler wired to this module this phase).
- **`attachDomain()`'s failure mode is silent-degrade by design** — if the active provider's domain call fails or isn't implemented, `Domain.verificationStatus` simply stays `PENDING` with no error surfaced to the caller beyond a warning log; this matches the founder's "reserve architecture for future implementation" framing for Domain/SSL but means a caller has no direct signal _why_ verification hasn't progressed beyond re-checking the row's own state.
