## 2. Pre-Implementation Architecture Review

The founder's module brief specified the objective, inputs/outputs, device preview modes, the full validation checklist across four categories, per-rule field requirements, and the explicit no-Lighthouse instruction directly. Before any code was written, an architecture was presented resolving the brief's central technical tension — "render the existing website" vs. "business logic must never depend on Next.js internals" — with one genuine open fork flagged via AskUserQuestion:

1. **Rendering mechanism** — (a) structural/data preview only, no live rendering; (b) ephemeral build-and-serve, a real `next build`+`next start` per request; (c) a constrained server-side-rendered snapshot with a pre-compiled stylesheet. Founder chose (a) — DECISIONS.md D-076.

After that architecture was approved, the founder sent four explicit numbered Decisions refining it further, all incorporated before implementation:

- **Decision 1 (Preview Immutability)** — fully read-only; resolved structurally via a package-boundary guarantee (D-075) and by removing the FK chain between `PreviewReport`/`PublishReadinessReport` that an earlier draft design had (D-079).
- **Decision 2 (Cache Strategy)** — regenerate only on `GeneratedWebsite` version change; resolved by making every M9 endpoint a single GET that computes-and-caches, since there is no POST anywhere in this module's brief and no cost to gate behind one (D-078).
- **Decision 3 (Validation Architecture)** — validators independent, `PublishReadinessEngine` aggregates only; resolved by splitting the founder's own listed "Structural Integrity"/"Content Completeness" readiness scores into two additional real, independent validators (`structuralValidator`/`contentCompletenessValidator`) rather than having `PublishReadinessEngine` compute either directly (D-077/D-079).
- **Decision 4 (Permission)** — dedicated `website:preview`, not `website:assemble` — a direct, one-line implementation, no design tension.

Full reasoning: `DECISIONS.md` D-075 through D-081.

## 3. Implementation Summary

**New `packages/website-preview`:** `ast-inspect-helpers.ts` (read-only AST parsing — `findExportedConstValue`/`findAllExportedConstValues`, `extractJsonLdPayloads`, `findNestedObjects`, `collectStrings`, `importedSectionComponentPaths`), `color-contrast.ts` (real WCAG relative-luminance contrast ratio), `module-version.ts` (`WEBSITE_PREVIEW_MODULE_VERSION`).

**`validation/`:** `validator.interface.ts` (`WebsiteValidator`, `ValidatorInput`), `rule-builder.ts` (`passRule`/`warningRule`/`errorRule`), `structural-validator.ts`, `content-completeness-validator.ts`, `seo-validator.ts`, `accessibility-validator.ts`, `performance-validator.ts`, `validator-registry.ts` (`VALIDATOR_REGISTRY`, `runAllValidators()`, `VALIDATION_ENGINE_VERSION`).

**`preview/`:** `device-presets.ts` (`DEVICE_PRESETS`), `preview-generator.ts` (`generateWebsitePreview()`, `PREVIEW_ENGINE_VERSION`).

**`readiness/`:** `publish-readiness-engine.ts` (`aggregateReadiness()`, `PUBLISH_READINESS_ENGINE_VERSION`).

**Contracts (`packages/shared-types/src/website-preview.ts`):** `previewMetadataSchema`, `websitePreviewSchema`, `validationRuleResultSchema`, `previewReportSchema`, `scoreBreakdownSchema`, `publishReadinessReportSchema`.

**Schema (`packages/db/prisma/schema.prisma`):** new `WebsitePreview`/`PreviewReport`/`PublishReadinessReport` models — each versioned per business, FK'd to `businessId`+`generatedWebsiteId` only. New, purely additive migration `20260804000000_m9_website_preview`.

**Services (`apps/api/src/website-preview/`):** `WebsitePreviewModule` (imports only `LeadsModule`), `WebsitePreviewService` (three independent get-or-generate-and-cache methods), `WebsitePreviewController` (`GET /leads/:id/preview`, `/preview/validation`, `/preview/readiness`), three DTO mappers.

**Exceptions/permissions:** new `GeneratedWebsiteNotFoundException` (`GENERATED_WEBSITE_NOT_FOUND`, 404); new `website:preview` permission, same role set as `website:assemble`.

**Logging:** `Logger` on `WebsitePreviewService` — Preview Opened / Validation Started / Validation Completed / Publish Readiness Generated, on both cache-hit and cache-miss paths.

**A real bug found and fixed during this phase (D-081):** the first version of the broken-internal-link check parsed `app/page.tsx`'s literal JSX `href`/`id` attributes — vacuous against the real M8.4 templates, which spread props and build hrefs from a runtime template literal rather than printing literal attributes. Fixed to read `id`/`targetComponentId` directly out of `lib/site-data.ts`'s already-resolved props instead, caught by testing against a real assembled fixture rather than assuming the check was correct.

## 6. Security Review

- **AuthZ** — all three GETs require the new `website:preview` permission (same role set as `website:assemble`) — a deliberate departure from every prior module's convention of gating GET behind only `leads:read`, since an M9 GET performs real computation. Verified: a Viewer gets 403 on all three routes.
- **Cost governance** — not applicable. No AI call, no third-party API, nothing to meter against the monthly cost ceiling.
- **No secrets/PII newly logged** — log lines carry businessId/generatedWebsiteId/reportId/rule-and-error counts/overall score only.
- **Read-only, verified** — a dedicated test asserts `GeneratedWebsite.files` is byte-identical before and after every M9 operation, and that no `update`/`delete` method is ever invoked against it.

## 7. Known Limitations (flagged, not hidden)

- The migration has not been run against a real Postgres instance — same constraint as every prior module.
- **Live visual rendering is out of scope this phase** (D-076, founder's chosen architecture option) — `WebsitePreview` is a structural/data manifest (file list, business/theme summary, fixed viewport presets), not something a user can currently look at. A future module or infra decision would need to add an actual rendering surface.
- **A future validator with a genuinely new `RuleCategory`** (e.g. a Security Validator) contributes its rules to `PreviewReport` immediately (the registry pattern already supports it) but does not automatically get its own named score in `PublishReadinessReport` — `PublishReadinessEngine`'s five named score fields are fixed today; adding a sixth is a small, separate, deliberate future schema change to the engine itself, consistent with "PublishReadinessEngine only aggregates" (it can't infer what a sensible new named score should be called or weighted at).
- **`aggregateRating` accuracy in JSON-LD** is inherited from M8.4's own known limitation (D-070) — `seoValidator` checks that a JSON-LD entry exists and has the right `@type`, not the correctness of every individual field's schema.org conformance.
- **Performance proxies are heuristics, not measurements** — client-component count, `priority`-image presence, etc. are structural stand-ins for real bundle size / Core Web Vitals, per the founder's own explicit "no Lighthouse" instruction. Documented per-rule, not presented as equivalent to a real measurement.
- **Content Completeness only checks non-emptiness**, not correctness or quality of the bound content itself — a field with a real but nonsensical value would still pass.
