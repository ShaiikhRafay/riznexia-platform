## 2. Pre-Implementation Architecture Review

The founder's phase brief specified the objective, inputs, the full technology stack, accessibility/SEO/performance requirements, and the validation list directly, followed by the Additional Architecture Requirement quoted above. Before any code was written, an architecture was presented resolving that requirement concretely:

- **Tier 1 — static templates.** One real, production-quality `.tsx` component per `SupportedComponentType` (16) plus a Next.js project skeleton, authored once, never generated or modified, read verbatim off disk.
- **Tier 2 — structured data, not source strings, for the two files that vary.** `lib/site-data.ts` (typed per-component props objects) and `app/page.tsx` (which components render, in what order) are built via the TypeScript Compiler API (`ts.factory`/`ts.createPrinter()`), never string concatenation.

Two open forks were flagged and resolved via AskUserQuestion before implementation:

1. **Persistence model** — new `GeneratedWebsite` Prisma model with `files: Json`, vs. inventing new object-storage infrastructure. Founder chose the former — DECISIONS.md D-068/D-072.
2. **Component breadth** — all 16 `SupportedComponentType`s built now to one consistent, real, accessible standard, vs. a smaller reference slice. Founder chose full breadth — DECISIONS.md D-068.

Full reasoning: `DECISIONS.md` D-068 through D-074.

**Design note carried forward without re-asking:** validation-failure semantics (internal assertion vs. new domain exception) were already resolved for this same package/module in M8.1/M8.2/M8.3 (D-052/D-060/D-067); the identical reasoning was carried forward — DECISIONS.md D-073.

**A design decision revised mid-implementation, not re-asked:** the first `lib/site-data.ts` design used a single `export const siteData = {...} as const` object; this was replaced with one type-annotated `export const <id>Props: <Type> = {...}` per component after `as const`'s readonly-array/mutable-`string[]`-prop conflict was discovered — a correction to satisfy the same architecture requirement more precisely, not a scope change requiring founder input. DECISIONS.md D-069.

## 3. Implementation Summary

**Static template (`packages/website-generator/templates/nextjs-base/`):** full Next.js App Router project skeleton (config files, `app/layout.tsx`, `app/globals.css`, `app/icon.svg`), 7 shadcn/ui primitives, `lib/` helpers (`cn()`, `resolvePlacePhotoUrl()`, `gridColumnsClassName()`, standalone `types.ts`), and 16 real section components — one per `SupportedComponentType`, plus a structural `Footer`. Excluded from this package's own `tsc`/`eslint` scope (`templates/**` outside `tsconfig.json`'s `include` and added to `eslint.config.mjs`'s `ignores` — Next.js's own conventions require default exports, conflicting with this monorepo's "named exports only" standard).

**New `packages/website-generator/src/assembly/`:** `ts-ast-helpers.ts` (the `valueToExpression()` serializer and JSX/import/typed-const AST primitives), `component-template-registry.ts`, `component-props-mapper.ts`, `component-var-names.ts`, `jsonld-mapper.ts`, `site-data-generator.ts`, `page-ast-generator.ts`, `theme-tokens-css-generator.ts`, `seo-files-generator.ts`, `package-json-generator.ts`, `static-template-loader.ts`, `website-assembler.ts` (`assembleWebsite()`, `ASSEMBLY_ENGINE_VERSION`), `website-validator.ts` (`validateWebsiteAssembly()`), `assembly-fixtures.ts`.

**Contracts (`packages/shared-types/src/generated-website.ts`):** `generatedWebsiteFileSchema`, `generatedWebsiteSchema`.

**Schema (`packages/db/prisma/schema.prisma`):** new `GeneratedWebsite` model — versioned, quintuple-FK (`businessAnalysisId`, `themeConfigurationId`, `layoutConfigurationId`, `componentManifestId`, `contentManifestId`), `files: Json`. New, purely additive migration `20260803000000_m8_4_website_assembly`. The pre-existing `Website`/`WebsitePage`/`GenerationJob`/`Deployment` roadmap scaffolding is untouched, not repurposed — DECISIONS.md D-072.

**Services (`apps/api/src/website-assembly/`):** `WebsiteAssemblyModule` (imports only `LeadsModule` — no `BusinessModule`, unlike `ContentEngineModule`), `WebsiteAssemblyService` (cache check by `contentManifestId`, assemble + validate + versioned persistence), `WebsiteAssemblyController` (`GET/POST /leads/:id/website`), `dto/generated-website-response.dto.ts`.

**Exceptions/permissions:** new `ContentManifestNotFoundException` (`CONTENT_MANIFEST_NOT_FOUND`, 404); new `website:assemble` permission, same role set as `content:bind`/`component:generate`/`layout:generate`/`theme:select`.

**Logging:** `Logger` on `WebsiteAssemblyService` — cache hit/miss, completion with the generated file count.

**Bugs found and fixed during this phase (see §4/D-074 for how):**

- Tailwind JIT scanner cannot see dynamically-interpolated class names (`` `grid-cols-${n}` ``) — fixed with a static lookup-table helper (`lib/grid-columns.ts`).
- `hero.tsx` had an incorrectly-placed `id="main-content"` on its `<h1>` — removed; the landmark belongs on `<main>` in the generated `page.tsx`, which wraps every section regardless of which components a given business's manifest produces.
- `SectionWrapperProps.children` was required, but the generated `lib/site-data.ts` never includes a `children` field (real children are injected via JSX nesting) — a section with zero mapped children failed `next build`'s typecheck. Fixed by making it optional.

**Beyond the automated suite — a real, unmocked build smoke test (DECISIONS.md D-074):** unit/e2e tests never invoke Next.js's own compiler/bundler against the _generated project's own source_ — a type error inside the assembled `lib/site-data.ts`/`app/page.tsx` would pass every test above while still failing a real `next build`. ## 6. Security Review

- **AuthZ** — `POST /leads/:id/website` requires the new `website:assemble` permission (same role set as `content:bind`/`component:generate`/`layout:generate`/`theme:select`); `GET` requires only `leads:read`. Verified: a Viewer gets 403 on POST, 200 on GET.
- **Cost governance** — not applicable. `assembleWebsite()` calls no external service (no AI, no third-party API) — same as M8.1-M8.3, nothing to meter against the monthly cost ceiling.
- **No secrets/PII newly logged** — log lines carry `businessId`/`contentManifestId`/generated file count only. No file content is logged.
- **No secrets baked into generated output** — `NEXT_PUBLIC_GOOGLE_PLACES_API_KEY`/`NEXT_PUBLIC_SITE_URL` are referenced via `process.env` in the generated code, never resolved and inlined at generation time; they remain the deploying party's own deploy-time configuration.

## 7. Known Limitations (flagged, not hidden)

- The migration has not been run against a real Postgres instance — same constraint as every prior module.
- `LocalBusiness` JSON-LD's `aggregateRating` is emitted as a plain human-readable string ("4.5/5 (120 reviews)"), not a proper schema.org `AggregateRating` object with numeric `ratingValue`/`reviewCount` — the assembler only has M8.3's already-combined string, not the original separate numeric fields. A future refinement could thread the raw numbers through from `Business` for a properly-typed structured-data object.
- `map-embed.tsx` renders an external "View on Google Maps" link rather than a genuinely embedded `<iframe>` — a signed Google Maps Embed API call would be needed for a real embed, which no part of this pipeline currently makes (carried forward from M8.3's own map-embed content binding, `Business.googleBusinessUrl`).
- FAQ, class schedules, pricing plans, client logos, and individual team-member profiles still have no upstream data source (M8.3's `unresolvedBindings`, D-061) — the corresponding section components render correctly but produce nothing for any of the 5 of 8 themes that include one, since `assembleWebsite()` only assembles what M8.3 actually bound.
- The real `npm install`/`build`/`dev` smoke test (§4) was run once, manually, against one fixture business/theme combination — not automated as a repeatable CI check, and not run against all 8 themes individually (though every theme shares the identical 16-component template set and assembly code path, so the risk of a theme-specific build failure is low, not zero).
- `next-seo` remains a declared `package.json` dependency (matches the stated tech stack) but isn't actually exercised by any generated code — JSON-LD uses a raw `<script>` tag instead (D-070). A future revision could either wire it in for a narrower use case or drop the now-unused dependency.
