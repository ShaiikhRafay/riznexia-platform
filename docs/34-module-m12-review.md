## 2. Pre-Implementation Architecture Review

Before any code was written, a research pass across every completed module (M1-M11) was run first, per the founder's explicit research mandate — identifying `CostService`, M10's own `ReportingService` (not exported at the time — flagged as needing to become exported), `AuditLogService`, `BusinessAnalysis`'s cost/token fields, and the Deployment module's tables as the required-reuse infrastructure this module would sit on top of, and enumerating the full 31-model Prisma schema to confirm no domain the founder named lacked a source table.

An architecture was then presented distinguishing two genuinely separate concerns the founder's brief could otherwise be read as conflating: **internal Reporting** (this module's own Analytics/Reporting/Dashboard/Aggregation/Export Engines, which read our own Postgres and involve no vendor at all) versus the **external `AnalyticsProvider` abstraction** (vendor-agnostic event emission — PostHog, Google Analytics, etc. — a separate concern from internal reporting). This distinction, along with the five-engine layered architecture, the `AnalyticsEvent`-as-the-one-new-table proposal, the permission mapping, and CSV-real/PDF+Excel-reserved for Export, was explicitly flagged as a recommendation open to override — approved as proposed, with eleven explicit numbered founder Decisions refining it further, all incorporated before implementation:

- **Decision 2 (Analytics Layer)** — resolved by making `getSalesFacts()` a direct passthrough to M10's `ReportingService.getDashboardStats()` rather than re-querying `LeadCRM`, requiring that service to become exported from `crm/reporting/reporting.module.ts` for the first time (D-104).
- **Decision 3 (Analytics Provider)** — resolved by mirroring `DeploymentProvider` (M11) exactly: one interface, one DI token, `SelfHostedAnalyticsProvider` fully implemented, five reserved provider classes that genuinely implement the interface but throw until a real adapter backs them (D-105).
- **Decision 5 (Aggregation)** — resolved by building one shared `AggregationEngineService` with `resolveRange()`/`bucketize()`, consumed by every trend-shaped Analytics Engine method and by the Dashboard Engine — never a bespoke date-grouping written inline anywhere else (D-107).
- **Decision 6 (Dashboard)** — resolved by making `DashboardEngineService.composeWidgets()` a public method the Reporting Engine's `executive_dashboard` case calls directly, rather than two independent widget-assembly implementations (D-108).
- **Decision 7 (Export)** — resolved by having `exportQuerySchema` accept all three formats structurally (so the API contract never changes shape later) while `ExportEngineService` rejects `pdf`/`excel` at the service layer before any report is computed, the same split M10 used for `SalesProposal.status` transitions (D-109).
- **Decisions 8/9/10/11 (Permissions/Logging/Performance/Future Compatibility)** — resolved as direct permission/logging/reservation lists with no architectural fork to resolve; documented in D-110, D-111, D-112, D-113 respectively.

Full reasoning: `DECISIONS.md` D-103 through D-113.

## 3. Implementation Summary

**Schema (`packages/db/prisma/schema.prisma`):** `AnalyticsEvent` (append-only, the only model this module owns) + `AnalyticsProviderName` enum. New migration `20260807000000_m12_analytics`.

**Contracts (`packages/shared-types/src/`):** `analytics-provider.ts`, `analytics-event.ts`, `analytics-aggregation.ts`, `analytics-report.ts`, `analytics-dashboard.ts`, `analytics-export.ts` — six new files, each with its own test file. `salesPerformanceReportSchema` is a direct re-export of M10's own `dashboardStatsSchema`, not redefined; `analyticsDashboardQuerySchema` deliberately renamed from a first-draft `dashboardQuerySchema` to avoid a real export collision with M10's `dashboard-stats.ts`.

**Analytics Provider (`apps/api/src/analytics/provider/`):** `analytics-provider.interface.ts` (`AnalyticsProvider` + `ANALYTICS_PROVIDER`), `self-hosted-analytics.provider.ts` (writes to `AnalyticsEvent`), `unimplemented-analytics-provider.base.ts` + five reserved provider classes, `provider.module.ts`.

**Aggregation Engine (`apps/api/src/analytics/aggregation/`):** `bucket-math.ts` (hand-rolled ISO Monday-start day/week/month/year bucket math — no date library exists anywhere in this monorepo, confirmed by grep), `AggregationEngineService` (`resolveRange`/`bucketize`), `aggregation.module.ts`.

**Analytics Engine (`apps/api/src/analytics/engine/`):** `AnalyticsEngineService` — fifteen fact methods grouped Business Analytics / Usage Analytics / System Monitoring, `engine.module.ts` (imports M10's `ReportingModule` + `AggregationModule`).

**Reporting Engine (`apps/api/src/analytics/reporting/`):** `ReportingEngineService.generateReport()`, `ReportingEngineController` (`GET /analytics/reports/:type`), `reporting.module.ts` (imports `EngineModule`/`AggregationModule`/`DashboardModule`/`ProviderModule`).

**Dashboard Engine (`apps/api/src/analytics/dashboard/`):** `DashboardEngineService.getDashboard()`/`composeWidgets()`, `DashboardEngineController` (`GET /analytics/dashboard`), `dashboard.module.ts`.

**Export Engine (`apps/api/src/analytics/export/`):** `csv-formatter.ts` (hand-rolled RFC-4180-ish escaping), `ExportEngineService.exportReport()`, `ExportEngineController` (`GET /analytics/reports/:type/export`), `export.module.ts`.

**Exceptions/permissions:** `ExportFormatNotImplementedException`/`InvalidAggregationRangeException`; four new permissions (`analytics:view`/`analytics:report`/`analytics:export`/`analytics:manage`).

**App wiring:** `DashboardModule`, `ReportingModule` (aliased `AnalyticsReportingModule` to resolve a genuine class-name collision with M10's own `crm/reporting/reporting.module.ts` `ReportingModule` — both had to be imported directly at the app level, unlike M11's `HealthModule` collision which was avoidable via transitive import), and `ExportModule` registered in `apps/api/src/app.module.ts` (`EngineModule`/`AggregationModule`/`ProviderModule` for analytics are pulled in transitively, having no controllers of their own); the full `AppModule` DI graph verified by running `app.e2e-spec.ts`, confirming no route or DI-token collision.

**One self-caught architectural gap, fixed before this module was considered complete:** the `AnalyticsProvider` abstraction (Decision 3) was fully built and independently tested but never actually called by any of the other four engines — fully live, fully tested, but dead code from the rest of the module's perspective. Fixed by injecting `ANALYTICS_PROVIDER` into `DashboardEngineService`/`ReportingEngineService`/`ExportEngineService`, adding a private `trackBestEffort()` method to each (mirroring `AuditLogService.record()`'s established best-effort contract, D-028) that calls `.track()` alongside every `Logger.log()` call for the four user-facing events D-111 names, and adding new tests asserting both the tracking call's shape and that a tracking-provider failure never fails the primary request.

**D-numbers pre-allocated upfront, not cleaned up afterward:** unlike M11 (where inconsistent D-numbering required a renumbering pass at the end, per that module's own review report), M12's D-104 through D-113 mapping was decided before any code comment was written, and used consistently in every file's doc comments throughout the build — no cleanup pass was needed this time.

## 6. Security Review

- **AuthZ** — every read is gated by the specific permission it needs: `analytics:view` for `GET /analytics/dashboard` only, `analytics:report` for the full per-report drill-down (`GET /analytics/reports/:type`), `analytics:export` for the CSV download endpoint. Verified: `sales_executive` (holds none of the four) gets 403 on all three endpoints; `developer`/`viewer` (hold `analytics:view` only) can see the rolled-up dashboard but get 403 on both the detailed report and export endpoints — this asymmetry is deliberate (a widget summary is materially less sensitive than a full drill-down) and directly tested.
- **No AI content generation, no business-data mutation** — verified structurally: zero import of `@riznexia/ai` anywhere in `apps/api/src/analytics/`; `AnalyticsEngineService` has no `create`/`update`/`delete` Prisma call in the entire file.
- **`AnalyticsEvent` metadata is never client-controlled input rendered back out** — `track()`'s `metadata` field is always engine-constructed (e.g. `{format: 'csv'}`, `{period: 'monthly'}`), never raw user-supplied text, so there is no stored-injection surface through this table.
- **No secrets in any analytics response** — every report/dashboard/export payload is composed exclusively from already-computed facts other modules expose through their own service methods; no credential, token, or internal-only field is read or re-exposed by any Analytics Engine method.
- **Export headers set explicitly, not derived from user input** — `Content-Disposition`'s filename is server-constructed from the validated `reportType`/`period`/date (`ExportFormatNotImplementedException` guards the format before any string built from request data reaches a header), avoiding header-injection from an untrusted value.
- **Best-effort tracking never becomes a fail-open bypass** — `trackBestEffort()`'s catch only ever logs a warning; it cannot suppress or alter the primary permission check or response, since it runs after the gated action has already completed successfully.

## 7. Known Limitations (flagged, not hidden)

- The migration has not been run against a real Postgres instance, and no real vendor analytics platform (PostHog, Google Analytics, etc.) has ever been exercised — same constraint as every prior module's external-dependency disclaimer; `SelfHostedAnalyticsProvider` is the only provider ever actually called.
- **No caching is wired for any report/dashboard/export this phase** — every request recomputes from scratch, the same deliberate "no caching yet, cache-ready shape" stance M10's own Reporting Engine took (D-089); `AnalyticsReportEnvelope`/`AnalyticsDashboard` are both plain JSON-serializable snapshots with no live cursors, ready for a future cache layer without a redesign.
- **`getIndustryFacts()` loads the full `LeadCRM` table into memory to group by category in JS** (no `where` clause bounding it by date range), mirroring M10's own `ReportingService` pattern of fetch-then-JS-group for multi-hop joins Prisma's `groupBy` can't express directly — acceptable at this system's current scale (an internal sales tool, not a high-volume public system) but the one Analytics Engine method without a date-range-bounded query.
- **`getErrorFacts()`'s sample messages are capped at 5 per module** and are best-effort readable strings (e.g. a generic "Discovery job failed" placeholder where the underlying table has no dedicated error-message column) rather than a uniform structured error shape across all four source modules.
- **`analytics:manage` is defined and assigned to roles but enforced on no endpoint yet** — deliberately reserved (D-110, D-113) for the Future Compatibility management surface (Scheduled Reports/KPI Alerts configuration), not an oversight.
