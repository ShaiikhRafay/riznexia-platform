## 3. Backend Reality vs. the Brief — No Escalated Gap, Four Resolved Directly

Research read all six M11 controllers/services in full (`apps/api/src/deployment/{engine,health,domain,rollback}/`), plus `packages/shared-types`' `website-deployment.ts`/`deployment-status.ts`/`domain.ts`/`deployment-health-check.ts`/`deployment-provider.ts`, plus the module's own e2e spec (`apps/api/test/deployment.e2e-spec.ts`) for exact runtime behavior, before writing any component.

**No genuine architectural gap requiring `AskUserQuestion`** — every M11 resource is lead-scoped with a real GET and (where applicable) a real POST, and the founder's four brief permissions matched the real `PERMISSIONS` array exactly.

**Four brief-to-field mappings were resolved directly**, following F9/F10's established discipline — the brief's own governing rules ("never invent data," "never invent logs or metadata," "never compute health scores") left exactly one compliant path in each case:

1. **"Trigger Type" (History/Details) has no dedicated field.** `WebsiteDeployment` carries two real, mutually exclusive foreign keys instead (`rollbackFromDeploymentId`/`retryOfDeploymentId`). `getTriggerType()` derives Manual/Retry/Rollback from those two already-returned fields. See D-188.
2. **"Rollback Availability" (Details) has no dedicated field for an arbitrary historical deployment.** `isRollbackEligible()` mirrors the exact rule stated in the backend's own `rollback-engine.controller.ts` comment ("must be a previous COMPLETED + HEALTHY one") and enforced as `INVALID_ROLLBACK_TARGET` — a plain boolean over the same two fields already shown on the page. See D-188.
3. **"Deployment Logs (if available)" — genuinely not available.** `WebsiteDeployment` has no log-text field anywhere; the page states this fact rather than omitting the card or fabricating content. See D-188.
4. **"DNS Status (if available)" — no dedicated field.** `Domain`'s closest real field is `verificationRecord` (arbitrary provider metadata); shown under its own real name instead of mislabeled. See D-188.

**Health Monitoring's "Passed Checks"/"Failed Checks"/"Availability"/"Performance"** are handled the same way, verified against `health-check-engine.service.ts`'s `runCheck()` directly: `detail` always contains `{ checks: [{ name, passed, detail }] }` for four real checks (`deployment_status`, `website_reachable`, `domain_status`, `ssl_status`). `parseHealthCheckDetail()` reads this defensively (duck-typed, degrades to an empty list rather than throwing on a malformed blob) and the page tallies pass/fail counts from the single most recent row only — never aggregated, never weighted. "Availability" reuses the existing Health Status badge; "Performance" is the raw `responseTimeMs` value, formatted but not scored.

## 6. Security Review

- **AuthZ** — `deployment:view` gates the nav entry client-side for UI convenience; the backend's own guards on every M11 route remain the sole real enforcement. `deployment:create`/`rollback`/`manage` each gate their own real action precisely matching the backend's own permission split (confirmed against `permission.constants.ts` directly).
- **No page-level view-gate needed, unlike F10's `CrmViewGate`** — every role currently holds `deployment:view`, so there's no permission gap for a bypassed nav link to expose; documented as a deliberate difference from F10's pattern, not an oversight (D-187).
- **No new data exposure** — every field rendered comes directly from the five M11 endpoints' own response shapes; no invented field (Trigger Type, Rollback Availability) is ever sent back to the server or treated as anything but a display label.
- **Mutations carry only the fields the backend accepts** — `{commitHash?}` for Deploy, `{hostname, type}` for Register Domain, no body for Retry/Rollback/Verify/Trigger Health Check; the backend's own validation (`DEPLOYMENT_VALIDATION_FAILED`, `DEPLOYMENT_NOT_RETRYABLE`, `INVALID_ROLLBACK_TARGET`) is the real authority — this module's own eligibility checks (e.g. disabling Roll Back) are UX conveniences only, never a substitute for the server's own guard.
- **Domain verification never performs client-side DNS/registrar logic** — `POST .../verify` is a plain, unparameterized trigger of the backend's own real check.
