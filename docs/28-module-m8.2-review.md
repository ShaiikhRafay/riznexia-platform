## 2. Pre-Implementation Architecture Review

The founder's phase brief specified the objective, inputs/outputs, the determinism/no-hallucination requirements, and the validation list directly, followed by a dedicated Theme Tokens requirement with concrete examples (`token.primary`, `token.radius.large`, `token.heading`, `token.spacing.md`). Before any code was written, an architecture was presented covering: package placement, the full `ComponentManifest`/`ThemeTokens`/`ComponentDefinition` TypeScript shape, and the deterministic derivation rules per field — with two open forks flagged explicitly:

1. **Component-type taxonomy & classification mechanism** — the ~31 free-text `componentId`s across the 8 M7 themes needed collapsing onto a small closed enum for "only supported components" to be enforceable. Three options were presented (extend `ThemeDefinitionContent` again, explicitly; classify by name-pattern heuristic; ship with no sub-typing this phase). Founder chose to extend the explicit data model — DECISIONS.md D-055.
2. **Hierarchy depth** — whether the 2-level (section → theme component) hierarchy was sufficient this phase, or whether a 3rd synthetic level (e.g. individual cards inside a grid, with a fixed count) should be added now. Founder chose to stay at 2 levels — DECISIONS.md D-056.

Full reasoning: `DECISIONS.md` D-055 through D-060.

**Design note carried forward without re-asking:** validation-failure semantics (internal assertion vs. new domain exception) were already resolved for this same package/module in M8.1 (D-052); the identical reasoning was carried forward rather than re-litigated as a fresh fork — DECISIONS.md D-060.

## 3. Implementation Summary

**`packages/themes` extension (D-055):** new `component-type-registry.ts` — `COMPONENT_TYPE_REGISTRY: Record<string, SupportedComponentType>`, a single global lookup (not per-theme, unlike D-049's `sectionComponentMap`) covering all 31 known `componentId`s. New registry test asserts every theme's `componentSet` is fully covered.

**Contracts (`packages/shared-types/src/component-manifest.ts`):** `SUPPORTED_COMPONENT_TYPES` (16 values), `themeTokensSchema`, `contentSlotSchema`, `placeholderDefinitionSchema`, `componentResponsiveRulesSchema`, `componentAccessibilitySchema`, `componentVisibilitySchema` (discriminated union on `mode`), `componentDefinitionSchema`, `componentManifestSchema`.

**New `packages/website-generator/src/component/`** (extends the D-050 package): `component-tokens.ts` (`computeThemeTokens()`, `defaultRadiusToken()`), `component-type-definitions.ts` (hand-authored `COMPONENT_TYPE_DEFINITIONS` per type, `baseTokensForType()`), `component-generator.ts` (`generateComponentManifest()`, `COMPONENT_ENGINE_VERSION`), `component-validator.ts` (`validateComponentManifest()`), `component-fixtures.ts` (shared test fixtures reusing the real `generateLayout()`).

**Schema (`packages/db/prisma/schema.prisma`):** new `ComponentManifest` model — versioned, triple-FK (`businessAnalysisId`, `themeConfigurationId`, `layoutConfigurationId`), `themeTokens`/`components` as `Json`. New, purely additive migration `20260801000000_m8_2_component_generator`.

**Services (`apps/api/src/component-engine/`):** `ComponentEngineModule` (DI wiring, no `ThemeModule`/`AiModule` dependency), `ComponentGenerationService` (cache check by `layoutConfigurationId`, generate + validate + versioned persistence), `ComponentGenerationController` (`GET/POST /leads/:id/components`), `dto/component-manifest-response.dto.ts`.

**Exceptions/permissions:** new `LayoutConfigurationNotFoundException` (`LAYOUT_CONFIGURATION_NOT_FOUND`, 404); new `component:generate` permission, same role set as `layout:generate`/`theme:select`.

**Logging:** `Logger` on `ComponentGenerationService` — cache hit/miss, completion with component count.

## 5. `ComponentManifest` / `ComponentDefinition` Field Reference

| Field                                                                            | Source                                                                                                                                                        |
| -------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `businessId`/`businessAnalysisId`/`themeConfigurationId`/`layoutConfigurationId` | Provenance — all three upstream dependencies                                                                                                                  |
| `configVersion`/`componentEngineVersion`                                         | Versioning, same pattern as every prior M6-M8 output                                                                                                          |
| `themeTokens`                                                                    | `computeThemeTokens()` — colors/fonts verbatim from `ThemeConfiguration`, fixed radius/spacing scales, `cardStyle`-derived shadow                             |
| `components[].componentId`/`.componentType`                                      | Theme `componentId` verbatim, or a synthetic `section-<id>`/`navigation`/`sidebar` id; type from `COMPONENT_TYPE_REGISTRY`                                    |
| `components[].parentComponentId`/`.childComponentIds`                            | 2-level hierarchy — section wrapper (root) → mapped theme component(s) (D-056)                                                                                |
| `components[].requiredContent`/`.optionalContent`                                | Fixed per-type table (`COMPONENT_TYPE_DEFINITIONS`); `trustSignal` optional slot added to `hero` when `BusinessAnalysis.brandBrief.trustSignals` is non-empty |
| `components[].themeTokens`                                                       | Reference paths only (e.g. `token.radius.large`), resolved against the manifest's own top-level `themeTokens` — founder's explicit requirement (D-057)        |
| `components[].responsiveRules`                                                   | Inherited from `LayoutConfiguration.responsiveRules.perSection` + matching `grid` columns                                                                     |
| `components[].accessibility`                                                     | `role`/`altTextRequired` from the per-type table; `minTouchTargetPx`/`contrastLevel` pass-through from `ThemeConfiguration.accessibilityProfile`              |
| `components[].visibility`                                                        | `{mode:'always'}` by default; `{mode:'conditional', condition:'sidebar-present'}` for the sidebar component                                                   |
| `components[].placeholders`                                                      | Flattened required+optional content, each with a generic structural `placeholderLabel` derived from `slotName` — never business copy                          |

## 6. Security Review

- **AuthZ** — `POST /leads/:id/components` requires the new `component:generate` permission (same role set as `layout:generate`/`theme:select`); `GET` requires only `leads:read`. Verified: a Viewer gets 403 on POST, 200 on GET.
- **Cost governance** — not applicable. `generateComponentManifest()` calls no external service (no AI, no third-party API) — same as M8.1, nothing to meter against the monthly cost ceiling.
- **No secrets/PII newly logged** — log lines carry businessId/layoutConfigurationId/component count only.

## 7. Known Limitations (flagged, not hidden)

- The migration has not been run against a real Postgres instance — same constraint as every prior module.
- The 2-level hierarchy (D-056) means grid/carousel/profile-grid-type components don't yet declare individual item children (e.g. specific cards) — intentionally deferred to M8.3 (Content Binding), since their count depends on bound content this phase doesn't have. Downstream consumers should not assume a fixed child count for these types yet.
- `COMPONENT_TYPE_DEFINITIONS`' content-slot/accessibility-role table is hand-authored, reasonable-but-illustrative (not derived from real UX research) — same "starting point for founder/design review" caveat M7's theme definitions carried (D-047's "Reviewed and found sound" note).
- The sidebar component (and its `conditional` visibility path) is only exercised by a synthetic test fixture — no registered M7 theme currently uses `navigationStyle: 'sidebar'`, same limitation M8.1 already flagged for `LayoutConfiguration.sidebar`.
- `baseTokensForType()`'s token-reference assignments (which token each component type references for background/text/radius/etc.) are a considered but judgment-call starting point, same caveat as M8.1's grid/gap defaults — no real rendered output exists yet to validate them against.
