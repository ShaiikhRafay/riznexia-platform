# Architecture Decision Log

Short-form ADR log for decisions made _during implementation_ that aren't already captured in `/docs` — i.e., things resolved while writing code, not during the design-review phases. If a decision changes an approved design doc, it's recorded here **and** the doc is updated; this file is the "why," the doc is the "what."

## Project Setup — Pre-Module Tooling & Infrastructure

Historically labeled "M0" in the original 12-module plan (M0–M11). The roadmap was restructured on 2026-07-28 (D-022) into a new 12-module plan (M1–M12) that no longer has a numbered slot for pure tooling/infra bootstrap — this work is prerequisite setup, not a product-feature module. The decisions below (D-001–D-003, and the M0 references inside D-006/D-008/D-009) are about that tooling/infra work specifically, not about authentication — the Clerk/RBAC portion of the original M0 scope is retroactively **M3 — Authentication & RBAC** under the new numbering (see docs/21-implementation-roadmap.md), which has no ADR-worthy decisions of its own beyond what's already in Doc 16/18.

### D-001: `outDir` must not live in a shared base tsconfig

**Context:** `packages/config-typescript/nestjs.json` set `outDir: "./dist"`. TypeScript resolves relative `extends`-inherited paths against the _base config's own directory_, not the consuming project's — so `apps/api`'s build silently compiled into `packages/config-typescript/dist` instead of its own `dist/`. Invisible under `tsc --noEmit` (typecheck ignores `outDir`); only surfaced when the compiled server was actually run.
**Decision:** Shared framework-overlay tsconfigs (`nestjs.json`, `nextjs.json`) never set `outDir`/`rootDir`. Each consuming package's own `tsconfig.json` sets its own.

### D-002: Backend-consumed library packages compile to CommonJS, not ESM

**Context:** `packages/db` and `packages/shared-types` inherited `module: "ESNext"` from the framework-agnostic base config (correct for code a bundler consumes). But they're `require()`'d by `apps/api`'s plain Node runtime (`node dist/main.js`), and Node's ESM auto-detection tried to resolve their extensionless relative imports the ESM way and failed.
**Decision:** Any package under `packages/*` that's a _runtime_ dependency of `apps/api` (not just `apps/web`, which goes through a bundler) overrides `module`/`moduleResolution` to `CommonJS`/`Node` in its own tsconfig, and ships a real `build` script + `dist/` output — never `main`/`types` pointing at raw `.ts` source.

### D-003: ESLint 9 flat config needs one root-composable entry point, not just per-package configs

**Context:** Each package got its own `eslint.config.mjs`, which correctly fixed `pnpm --filter <pkg> lint` (CWD-scoped). But `lint-staged`, invoked from the repo root against a mixed list of staged file paths, failed outright — ESLint 9's flat config resolves **one config file for the whole invocation directory**, not a per-file upward search like the old `.eslintrc` cascade.
**Decision:** `lint-staged` only runs Prettier (which has no such resolution issue — one root `.prettierrc.json` genuinely applies everywhere). ESLint runs via `pnpm turbo run lint` in the same pre-commit hook, which shells out to each package's own correctly-scoped `lint` script.

## M1 — Lead Discovery

### D-004: Trigger.dev orchestration is deferred; pipeline logic is a plain injectable service today

**Context:** Doc 16 §9 specifies Trigger.dev as the job orchestrator. Wiring it in for real requires a live Trigger.dev project (API key, `trigger.config.ts`, and their own dev-mode CLI process) — none of which exists yet, and none of which is verifiable in this environment.
**Decision:** The discovery pipeline's business logic lives in `DiscoveryRunnerService`, a plain injectable NestJS service with no Trigger.dev-specific code in it at all. `DiscoveryService` dispatches it via in-process async execution today (fire-and-forget, progress tracked on the `discovery_job` row exactly as the API contract already promises). When Trigger.dev is actually provisioned, wiring `DiscoveryRunnerService.run()` into a `task()` definition is an _additive_ change — the retry/concurrency/observability behavior Trigger.dev adds comes for free without touching the pipeline logic itself.
**Follow-up:** Real Trigger.dev wiring is a small, separate piece of work once a project/API key exists — not blocking, not silently faked.

### D-005: The AI-assisted fallback tier for website classification is deferred to Module M3/M4

**Context:** Doc 20 §5 designs a rare AI-assisted fallback for website-status classification when the heuristic is inconclusive. `packages/ai` (the `AiService` gateway) doesn't exist yet — it's Module M6 (AI Business Analyzer) / M7–M8 (Theme Engine, Website Generator)'s deliverable, not M1's. (Renumbered 2026-07-28, D-022 — this was "Module M3/M4" under the original numbering.)
**Decision:** `WebsiteStatusClassifier` takes an _optional_ injected `AiFallbackClassifier` port. When it's not provided (true today), an inconclusive heuristic result falls straight through to Doc 20 §5's own documented fallback behavior — `outdated`, `confidence: low` — which is exactly what happens if the AI tier itself fails, so no new behavior was invented to cover the gap. Wiring in the real AI tier later means providing that one dependency, not restructuring the classifier.

### D-006: Local Redis dev needs an Upstash-REST-compatible proxy, not a plain Redis container

**Context:** `@upstash/redis`'s client speaks Upstash's HTTP REST protocol. The `redis:7-alpine` container already in `docker-compose.yml` (added in M0, before `packages/cache` had any real content) speaks the standard Redis wire protocol — the two are not interchangeable, and this only became apparent once `packages/cache` needed a real implementation.
**Decision:** Added `serverless-redis-http` (the standard community proxy Upstash itself points to for local development) as a sidecar in `docker-compose.yml`, sitting in front of the existing `redis` service and exposing an Upstash-REST-compatible endpoint on `localhost:8079`. Local `.env` points `UPSTASH_REDIS_REST_URL` at the proxy with a fixed dev token; production points at real Upstash.
**Verification gap:** This environment has no Docker available, so the proxy setup is written but not executable here — tests mock the cache client entirely (same pattern as D-002/M0's Prisma mocking) rather than depending on it.

### D-007: Places API cost figures are named constants, explicitly flagged as estimates

**Context:** Design review §9 already flagged that exact Google Places API (New) SKU pricing needs verification at implementation time rather than being asserted with false confidence.
**Decision:** `apps/api/src/common/cost/cost.constants.ts` holds the per-call-type cost estimates as named, individually-commented constants (not inlined magic numbers), so correcting a figure once real pricing is confirmed is a one-line change with no logic touched.

### D-008: Integration tests run against mocked Prisma/Redis, not a live database, in this environment

**Context:** Doc 13 §2 defines "integration" tests as running against a real ephemeral Postgres. This sandbox has no Docker, so no live Postgres or Redis is reachable here.
**Decision:** Integration tests use NestJS's `TestingModule` with the same DI-token mocking pattern established in M0 (`PRISMA_CLIENT`, and now `REDIS_CACHE`) — real guards, real pipes, real controller/service wiring, mocked data layer. This validates everything except actual SQL/constraint behavior. CI's ephemeral Postgres (Doc 14 §3) is what exercises the real database; that hasn't been run here and should be treated as the remaining verification step before this module is considered fully proven.

### D-009: `apps/api` was missing a `tsconfig.build.json`, so every `*.spec.ts` was shipping in the production build

**Context:** `apps/api/tsconfig.json` only excluded `node_modules`/`dist`/`test` — it never excluded colocated `*.spec.ts` files under `src/`, so `nest build` was compiling every unit test straight into `dist/`. This was true since initial project setup (`health.controller.spec.ts` shipped the same way) but only became visible once M1 added enough spec files to notice while inspecting `dist/` during this module's runtime-boot verification.
**Decision:** Added `apps/api/tsconfig.build.json` (extends `tsconfig.json`, additionally excludes `**/*.spec.ts`) — NestJS's CLI picks this up automatically for `nest build` if present, with no `nest-cli.json` change needed. `tsconfig.json` itself is untouched, so `tsc --noEmit` (typecheck) still covers spec files. Verified: `dist/` now contains zero `.spec.js` files.

## M1 Audit — Full Engineering Audit (pre-close review)

Founder requested a full audit (architecture, SOLID, performance, security, error handling, logging, validation, scalability, test coverage) before closing M1. Findings and fixes below; anything not listed was reviewed and found sound.

### D-010: Cost quota enforcement had a check-then-act race

**Context:** `CostService.assertWithinBudget()` (read) and `recordCost()` (write, called after the external API call) were separate steps. Two concurrent requests could both read a still-under-ceiling total and both proceed, together overshooting the $300 ceiling by up to a request's worth.
**Decision:** Collapsed into one atomic `CostService.charge()`: increments the Redis counter first (atomic `INCRBY`), decides from the _post-increment_ total, and refunds (decrements back) if that total exceeds the ceiling — called _before_ the external API call, not after. `DiscoveryService.createJobs`'s own pre-flight check is now explicitly advisory-only (`currentSpend()`, a plain read) — real enforcement happens once, atomically, at each actual charge point in `DiscoveryRunnerService`.

### D-011: Multi-category discovery-job creation wasn't transactional

**Context:** `DiscoveryService.createJobs` created one `discovery_job` row per requested category via `Promise.all`. A failure partway through (e.g. category 3 of 5) left categories 1–2 as orphaned `QUEUED` rows with no runner ever dispatched, while the whole request still threw.
**Decision:** Wrapped the batch create in `prisma.$transaction([...])` — all rows commit together or none do.

### D-012: A DB-update failure during job startup could strand a job in `QUEUED` forever

**Context:** `DiscoveryRunnerService.run()`'s first statement (mark the job `RUNNING`) sat _outside_ the try/catch that handles marking a job `FAILED`. If that specific update threw, the job would never transition again — stuck at `QUEUED` with no operator visibility.
**Decision:** Moved the RUNNING update inside the try block so any failure in it now correctly falls through to the existing FAILED-marking logic.

### D-013: No general rate limiting existed despite being part of the approved design

**Context:** Doc 22 §12 specifies IP-based rate limiting as a baseline abuse guard, and Doc 19 §4 defines a `RATE_LIMITED` error code — neither was implemented. Only dollar-based cost quota existed, which doesn't stop a client from hammering the endpoint with requests that individually stay under budget.
**Decision:** Added `@nestjs/throttler`: a global 100 req/min/IP baseline (`RateLimitModule`, registered ahead of the auth guard chain so abusive traffic is rejected before a token-verification round trip), plus a stricter 10 req/min limit specifically on `POST /discovery-jobs` (the cost-bearing endpoint). `ThrottlerException` is HTTP 429, which the existing exception filter fallback already mapped to `RATE_LIMITED` — no filter change needed.

### D-014: Validation gaps — whitespace-only input and unbounded wildcard search

**Context:** `city`/`categories` used `.min(1)`, which checks raw length, not trimmed content — `" "` passed validation and would trigger a real, wasted Places API call. Separately, `GET /leads?q=` had no minimum length, so a 1-character search ran an unindexed `ILIKE '%x%'` scan across every lead.
**Decision:** Added `.trim()` before `.min(1)` on `city`/`categories`. Added `.trim().min(2)` to `q`. Both are validation-boundary fixes, not query-level workarounds.

### D-015: No index backed the `businessName` search Doc 19 documents

**Context:** `GET /leads?q=` runs a `contains`/ILIKE search with no supporting index.
**Decision:** Added a plain btree index (`@@index([businessName])`, plus `city`/`category` while auditing the same query path) — schema-validated (`prisma validate`) without a live DB, per the pattern already established for M1's other schema work. **Deliberately not** added: a trigram GIN index (`pg_trgm` extension + `gin_trgm_ops`), which is what would actually make the wildcard search efficient at scale — Prisma's extension/index-type syntax for this needs verifying against a live database, which this environment doesn't have, and guessing at it risks a schema that parses but is subtly wrong. Add it when real lead volume makes the unindexed scan a measured problem, not speculatively now.

### D-016: `:id` path params weren't validated as UUIDs before hitting Prisma

**Context:** A malformed `id` in `GET /leads/:id` or `GET /discovery-jobs/:id` currently still works correctly (returns a clean 404) only because `Lead.id`/`DiscoveryJob.id` are Prisma `String` columns without `@db.Uuid` — Postgres never gets a chance to reject a malformed UUID at the type level. That's incidental, not load-bearing correctness.
**Decision:** Added NestJS's built-in `ParseUUIDPipe` to both `:id` params — a malformed ID now fails fast with `400 VALIDATION_ERROR` instead of a full DB round-trip that happens to land on 404.

### Reviewed and found sound, not changed

- **DNS-rebinding TOCTOU in the SSRF guard** (`website-fetch.adapter.ts`) — already documented as an accepted limitation in the file's own header comment. Fully closing it needs socket-level IP pinning via a custom fetch dispatcher; deferred as a dedicated hardening task rather than guessed at unverified.
- **Structured logging / correlation IDs** (`packages/logger`, Doc 16 §14) — genuinely cross-cutting, the (currently unscheduled) Observability & Hardening backlog item's scope — see docs/21-implementation-roadmap.md §5. `discoveryJobId` is already threaded through every log line this module emits, which is the practically useful part of correlation without building the full observability stack prematurely.
- **`PlacesAdapter`/`WebsiteFetchAdapter` injected as concrete classes, not interfaces** — idiomatic NestJS DI (the class doubles as its own injection token); `overrideProvider` in tests already gives full substitutability. Adding a separate interface for a single implementation each would be speculative abstraction, not a fix.

## M2 — Database & Core Domain Models

Doc 21 originally scoped "M2" as _Lead Pipeline / CRM_ (pipeline-stage mutation endpoints). The founder's actual M2 request retargeted the module to the data layer only — Prisma schema, migrations, seed data, and the repository-equivalent service layer — explicitly excluding AI, Google Places, and frontend work. This was a roadmap-numbering discrepancy against Doc 21 at the time, flagged here rather than unilaterally renumbered — **resolved 2026-07-28**: the founder made "M2 — Database & Core Domain Models" the official module identity across the whole roadmap (D-022). Doc 21's original "Lead Pipeline / CRM" content (mutation endpoints, stage-transition rules) now lives at **M4 — Lead Management APIs**, unbuilt.

### D-017: M2's requested entity list is reconciled onto the existing, already-approved schema — not modeled as new tables

**Context:** M2's brief listed `Business, BusinessCategory, Lead, LeadStatus, Project, Website, User, Role, AuditLog` as the entities to build. Several of these already exist under different names from M0/M1 (`TeamMember`+`TeamRole` enum ≈ User/Role; `Website` ≈ Project — Doc 19 already treats "Projects"/"Website Generator" as the same resource as `Website`), and `category`/`pipelineStage` were already deliberately-scoped enums (Doc 18), not lookup tables. Modeling the brief literally would mean parallel, duplicate tables for concepts that already exist, tested, and audited.
**Decision:** Resolved via `AskUserQuestion` before writing any code (this is exactly the kind of irreversible, hard-to-undo-cheaply modeling choice that's the user's call, not an inferable default). Founder chose the lowest-blast-radius option both times: reconcile onto the existing schema (`TeamMember`/`TeamRole` unchanged as User/Role, `Website` unchanged as Project, `category`/`pipelineStage` stay enums) and keep the current NestJS-idiomatic service layer rather than introducing a formal Repository interface/implementation split (`LeadsService` etc. already _are_ "the repository implementations" in this codebase's architecture). The only genuinely new modeling work is D-018.

### D-018: `Business` split out of `Lead` as its own table

**Context:** M1's `Lead` model held both "the real-world business and what we know about its web presence" (`googlePlaceId`, `businessName`, `category`, `city`, `address`, `placesData`, `websiteStatus`) and "Riznexia's pursuit of it" (`pipelineStage`, `assignedToId`, `notes`) in one row. Under the reconciled scope (D-017), `Business` is the one real piece of new modeling M2 does.
**Decision:** `Business` now owns all business-data fields (`packages/db/prisma/schema.prisma`); `Lead` slims to pure pipeline state plus a unique `businessId` FK (`onDelete: Cascade` — a Lead has no independent meaning without its Business). `BusinessAnalysis` and `DiscoveryJob`'s reverse relation retarget to `Business` accordingly; `Website`/`SalesProposal` are untouched (still keyed on `leadId` — deploying a demo site and drafting a pitch are genuinely about the sales pursuit, not the business record). Doc 19's public `GET /leads` response shape is unchanged — `apps/api/src/leads/dto/lead-response.dto.ts` composes it from a `Lead & { business: Business }` join instead of a flat row.
**Downstream effect on discovery semantics:** `DiscoveryRunnerService`'s "is this already-tracked, so a `present` result should still refresh it" gate now checks "does a `Business` already exist for this place" (`BusinessService.findByPlaceId`) instead of "does a `Lead` exist." These are equivalent under this design because a `Business` row is _only_ ever created alongside a `Lead` (in the qualifying/none-or-outdated branch) — never on its own — so a brand-new `present` candidate is still discarded with zero rows written (FR-1.3 unchanged), and an already-discovered business still gets its data refreshed without touching pipeline state (FR-1.7 unchanged).

### D-019: Soft-delete is now enforced structurally, via a Prisma Client Extension

**Context:** Doc 18 documented a `deletedAt` soft-delete pattern; M1 never enforced it as a structural guarantee — every call site had to remember to add `deletedAt: null` by hand. M2's brief explicitly asked for a soft-delete _strategy_, and building `Business` fresh was the natural point to close this gap rather than replicate the old ad hoc pattern onto a fourth table.
**Decision:** `packages/db/src/soft-delete.extension.ts` — a `$extends()`-based Prisma Client Extension applied once in `packages/db/src/client.ts` — auto-scopes `findFirst(OrThrow)`/`findMany`/`findUnique(OrThrow)`/`count` to `deletedAt: null` and reroutes `delete`/`deleteMany` into an `update`/`updateMany` that sets `deletedAt`, for `TeamMember`/`Business`/`Lead`/`Website` (the four models carrying the column). No hard-delete escape hatch exists yet — nothing in this module needs one.
**Known limitation, documented rather than silently accepted:** the extension only intercepts the _top-level_ model a query is issued against — it does not auto-filter rows reached through a nested Prisma `include`/relation `where` (a well-known limitation of extension-based soft delete, not specific to this implementation). `LeadsService.findMany`/`findById` compensate by explicitly adding `business: { deletedAt: null }` to the query — since `business` is a required (non-null) relation on `Lead`, this is always safe and always-applicable, not conditional. Any _future_ nested-relation read added on these four models needs the same explicit treatment; there's no automatic guarantee.

### D-020: Initial migration generated without a live database, same pattern as D-008

**Context:** No M0/M1 migration was ever generated (schema-only, applied via `prisma db push` conceptually, never actually run against a live Postgres in this environment) — M2 is genuinely the first migration this repo produces, and needs to capture the _entire_ current schema, not just the Business/Lead diff.
**Decision:** `prisma migrate diff --from-empty --to-schema-datamodel=schema.prisma --script`, which needs no database connection, generated `packages/db/prisma/migrations/20260728000000_init/migration.sql` (312 lines — every enum, table, index, and FK constraint in the current schema). Output was inspected end-to-end against the schema by hand rather than round-tripped through `prisma migrate diff --from-migrations` (which does need a live/shadow database to replay against and isn't available here). CI's real Postgres running this migration for the first time is the remaining verification step, consistent with D-008's existing gap.

### D-021: `packages/db` gained its own test suite (vitest, matching `packages/cache`/`packages/shared-types`)

**Context:** `packages/db` previously shipped no tests of its own — M0/M1's Prisma work was schema/config only, nothing with standalone logic worth unit testing. The soft-delete extension (D-019) is genuine, non-trivial logic that needs coverage independent of any consuming service's mocks.
**Decision:** Added `vitest` as a devDependency and a `test` script, following the exact convention `packages/cache`/`packages/shared-types` already established (`*.test.ts`, no config file needed). `soft-delete.extension.ts` exports its query hooks as plain functions (not wrapped in `Prisma.defineExtension`), so `soft-delete.extension.test.ts` calls them directly with a stub `query` callback — full behavioral coverage with no live Prisma engine or database involved.

## M3 — Authentication & RBAC

### D-023: Authentication stays on Clerk — M3 builds authorization only, not a parallel credential system

**Context:** The founder's initial M3 brief asked for JWT authentication, refresh tokens, login/logout endpoints, and password hashing — a self-rolled credential system. This directly conflicts with an already-made, documented architecture decision: Doc 15 §"AuthZ" states "No custom password handling anywhere in our code," and Clerk (integrated in the original Platform Foundation work, now retroactively this same M3 slot per D-022) already issues JWTs and manages sessions/refresh entirely off Riznexia's infrastructure. Replacing it would be a major, security-critical rewrite reversing that decision — not something to infer or guess at silently.
**Decision:** Resolved via `AskUserQuestion` before any code was written (mirroring D-017's precedent for the M2 entity-list conflict). Founder chose to keep Clerk as the authentication provider and scope M3 to **authorization only**: RBAC, permission middleware, route guards, role hierarchy, organization future-readiness, and audit logging for privileged actions. No JWT issuance, refresh-token handling, login/logout endpoints, or password hashing were written — Clerk already owns all of that, unchanged. This is the official architecture decision going forward: Clerk stays; any future request to add custom credential handling needs the same explicit confirmation this one got.

### D-024: Six-role taxonomy replaces the original three; migration hand-authored without a live database

**Context:** The original `TeamRole` enum (`ADMIN`, `MANAGER`, `SALES_REP`, built in initial project setup) doesn't match the founder's requested taxonomy: `Super Admin, Admin, Sales Manager, Sales Executive, Developer, Viewer`.
**Decision:** `TeamRole` becomes `SUPER_ADMIN, ADMIN, SALES_MANAGER, DEVELOPER, SALES_EXECUTIVE, VIEWER` (`packages/db/prisma/schema.prisma`). `ADMIN` is unchanged; `MANAGER`→`SALES_MANAGER` and `SALES_REP`→`SALES_EXECUTIVE` are renames (existing semantics preserved, just relabeled — same mapping used throughout `packages/shared-types`, `team-member.mapper.ts`, and every test fixture); `SUPER_ADMIN`/`DEVELOPER`/`VIEWER` are net-new. The default role for a newly-synced team member moves from `SALES_REP` to `SALES_EXECUTIVE` (its direct successor).
**Migration:** `packages/db/prisma/migrations/20260729000000_m3_rbac_role_taxonomy/` — hand-authored, same constraint and same technique as D-020 (no live/shadow database available to run `prisma migrate diff --from-migrations` against). Written as `ALTER TYPE ... ADD VALUE`/`RENAME VALUE` statements and cross-checked against a fresh `prisma migrate diff --from-empty` of the final schema to confirm both produce an identical end state (enum order and column default). Safe as a single transaction: PostgreSQL only forbids referencing a newly-`ADD VALUE`'d enum member within the same transaction it was added in, and this migration never does — it only adds/renames labels and repoints the column default at an already-renamed value.

### D-025: Role hierarchy is a linear ranking, with Developer deliberately off the sales ladder

**Context:** The brief asked for a "role hierarchy" (an "at least this seniority" concept). `Super Admin`/`Admin`/`Sales Manager`/`Sales Executive` are real seniority rungs in the sales chain of command; `Developer` is a lateral technical-access role with no natural seniority relative to sales roles, and `Viewer` is a read-only floor.
**Decision:** `apps/api/src/common/rbac/role-hierarchy.constants.ts` — a single numeric ranking (`super_admin(50) > admin(40) > sales_manager(30) > developer(20) > sales_executive(10) > viewer(0)`), used only for "at least this seniority" checks (`@MinRole()`/`MinRoleGuard`). Developer is placed between Sales Manager and Sales Executive specifically so `@MinRole('sales_manager')` correctly excludes it (not part of the sales command chain) while the ranking still reads as coherent. This hierarchy does **not** drive what actions a role may take — that's the independent permission matrix (D-026). A higher hierarchy level does not imply a superset of a lower role's permissions (Developer outranks Sales Executive here but has none of its lead-mutation permissions).

### D-026: Fine-grained permissions are an explicit per-role matrix, not hierarchy-derived — grounded in Doc 15's existing AuthZ statement

**Context:** The brief separately asked for "Permission middleware" alongside "Role hierarchy" — two distinct mechanisms, not one derived from the other (see D-025 on why hierarchy-inheritance would be wrong here: Developer's elevated hierarchy must not grant it Sales Executive's lead-management permissions).
**Decision:** `apps/api/src/common/rbac/permission.constants.ts` defines 8 permissions (`leads:read/write/delete`, `discovery:read/run`, `team:manage`, `cost:view`, `system:debug`) and an explicit `Record<TeamRole, Permission[]>` matrix, enforced by `@RequirePermissions()`/`PermissionsGuard`. `super_admin` gets every permission unconditionally. The matrix isn't invented from scratch: Doc 15 §"AuthZ" already stated "only Admin/Manager can manage team accounts or view the cost dashboard" — carried forward directly as `admin`/`sales_manager` owning `team:manage`/`cost:view`, which every other role (including `viewer`, deliberately) lacks. `team:manage` and `cost:view` aren't enforced on any route yet — no endpoint exists to enforce them on until Module M4, the Team & Settings backlog item, or M12 build one; defined now so the contract doesn't shift later, same rationale as Doc 19's schemas predating their endpoints.
**Applied to existing routes:** `LeadsController` now requires `leads:read` (class-level); `DiscoveryController` requires `discovery:run` on `POST` and `discovery:read` on both `GET`s. Every role has `leads:read`/`discovery:read`, and every pre-existing role (`admin`, `sales_manager`, `sales_executive`) retains `discovery:run` — so this is additive enforcement, not a behavior change for anyone who could already reach these routes. Only the two brand-new roles (`developer`, `viewer`) are denied `discovery:run`, which is correct by design (neither should spend Places API budget) and can't be "breaking" since no user held those roles before this module.

### D-027: Organization support stays commented-out schema, not an active column

**Context:** The brief asked for "Organization support (future-ready)." This is a single-organization internal tool (Doc 01) — there is no second organization to support today, and no code that would read an `organizationId`.
**Decision:** Followed the project's own established convention for this exact situation (`schema.prisma`'s existing "FUTURE (INACTIVE)" section, used for `Agency`/`Subscription`/etc. since M0): added a commented-out `Organization` model plus a doc-comment on `TeamMember` noting where the FK would attach if multi-org is ever built. No active column was added — nothing consumes it, and Doc 12's "don't build for hypothetical future requirements" applies here exactly as it did to those earlier future models. "Future-ready" is satisfied as a documented attachment point, not a half-built feature.

### D-028: Audit logging ships as a reusable mechanism; no new business endpoint was invented to exercise it

**Context:** `AuditLog` existed in the schema since M0 with no write path. The brief asked for "audit logging for privileged actions," but no genuinely privileged mutation endpoint exists yet in the app — `PATCH/DELETE /leads/{id}` (Lead Management APIs) and `/team` (role management) both belong to other, currently-unscheduled-in-this-module roadmap items (D-022). Adding a role-change endpoint here just to have something to audit would have pulled Team & Settings' scope into M3 without being asked.
**Decision:** Built `AuditLogService` (the write path, best-effort — a logging failure never fails the privileged action it's describing), `@Audited()`, and `AuditLogInterceptor` (global, no-op unless a route opts in) as a complete, independently-tested mechanism with no route in the real API wired to it yet — same "infrastructure ready, nothing forced onto it prematurely" treatment as D-026's `team:manage`/`cost:view`. Proven end-to-end via `apps/api/test/rbac.e2e-spec.ts`, a dedicated throwaway test controller/module (not part of `AppModule`, never becomes real API surface) exercising the full `ClerkAuthGuard → RolesGuard → MinRoleGuard → PermissionsGuard → AuditLogInterceptor` chain together over real HTTP requests — the only way to prove the chain composes correctly, which no single guard's unit test can show alone.

### Reviewed and found sound, not changed

- **`@Roles()`/`RolesGuard` (exact-role-list check, built in M0/original Platform Foundation)** — left as-is, just retyped for the 6-role enum. Still unused by any real route (as before M3), but now sits alongside `@MinRole()` as a second, complementary role-check mechanism for whichever future endpoint needs an exact list rather than a seniority threshold.
- **`ForbiddenRoleException` reused for `@MinRole()`, a new `ForbiddenPermissionException` added for `@RequirePermissions()`** — both map to the same `FORBIDDEN` code and 403 status at the API-contract level (Doc 19 §4 doesn't distinguish the two internally-different rejection reasons), so this is a server-log/message distinction only, not a new documented error code.

## M4 — Lead Management APIs

Before any code was written, an architecture review (required by the module brief) found four places where the requested feature set didn't fit the frozen Module M2 schema without either a schema change or an interpretation call. All four were resolved via `AskUserQuestion`, not guessed at — consistent with D-017 (M2's entity-list conflict) and D-023 (M3's auth-architecture conflict).

### D-030: Lead creation references an existing Business; notes become an append-only, authored collection

**Context:** Module M2 made `Lead.businessId` a required, unique FK — a Lead cannot exist without a Business, and `Business.googlePlaceId` is required and unique, so there's no schema-level "standalone lead" shape. Separately, `Lead.notes` was a single nullable string column with no author attribution; the brief's "add internal notes" (additive) doesn't fit a field whose only write path is overwrite.
**Decision:** `POST /leads` takes `{ businessId, ... }` and creates the pursuit of an already-discovered Business — useful for the real case of a business Discovery classified `PRESENT` (no Lead auto-created, DECISIONS.md D-018) that a rep decides to pursue anyway. Manual business entry (BRD §9's "allow manual lead entry as fallback") was explicitly declined for this module — it needs `Business.googlePlaceId` to tolerate null, which is Module M5's territory, not M4's, and the roadmap is frozen. `Lead.notes` is replaced by `LeadNote`: append-only, `authorId` + `createdAt` per row, no update/delete path in application code. The migration backfills existing `leads.notes` content into `lead_notes` (author `NULL` — the old column never recorded one; `created_at` approximated from the lead's `updated_at`) before dropping the column, so no note content is lost in the transition.

### D-031: Tags are a Postgres text array with a GIN index, not a normalized Tag/LeadTag pair

**Context:** No tag support existed anywhere in the schema. Two shapes were viable: a `String[]` column on `Lead`, or normalized `Tag`/`LeadTag` tables enabling tag governance (rename, merge, colour).
**Decision:** `Lead.tags String[] @default([])` with a GIN index (`@@index([tags], type: Gin)`) — covers every M4 requirement (add, remove, filter-by-tag) in one migration, consistent with this project's established "build what's needed now, document the attachment point" precedent (D-027's `Organization` model is the same pattern applied to a schema decision rather than a whole table). Tags are lowercased and format/length/count-validated at the zod boundary (`packages/shared-types`) — the one piece of governance a plain array can still provide cheaply, closing most of the "VIP vs vip" duplicate-tag risk without the normalized tables' added machinery. Revisit if/when tag _management_ (not just tag _use_) becomes a real requirement, most likely in Module M10 (Sales CRM).

### D-032: Lead activity timeline is a separate table from `audit_log`, written alongside it for user-initiated writes

**Context:** Module M3 already built `audit_log` (D-028) — a security/accountability trail. "Record activity history" could have reused it via a filtered read endpoint instead of a new table.
**Decision:** New `LeadActivity` table + `LeadActivityType` enum (`CREATED`, `STAGE_CHANGED`, `ASSIGNED`, `UNASSIGNED`, `NOTE_ADDED`, `TAGS_CHANGED`, `DELETED`), exposed via `GET /leads/:id/activity`, kept deliberately separate from `audit_log`: different consumer (a sales rep viewing their own lead's timeline vs. an admin investigating), different content (no IP addresses in `LeadActivity`), different vocabulary (a closed enum scoped to what can actually happen to a Lead, vs. `audit_log.action`'s intentionally open string spanning every entity type in the system). `LeadActivityService.record()` is transaction-aware and propagates failures (unlike `AuditLogService.record()`, which is deliberately best-effort/swallowing since it fires after the audited action already succeeded) — a `LeadActivity` row and the Lead mutation it describes commit together or not at all, so the timeline can never claim something that was rolled back. `DiscoveryRunnerService`'s pipeline-initiated lead creation (`ensureForBusiness`) also writes a `CREATED` entry with a `null` actor — there's no human to attribute a discovery-triggered lead to, and `actorId` is nullable for exactly this reason (same pattern as `AuditLog.actorId`/`LeadNote.authorId`).

### Reviewed and found sound, not changed

- **Assignment has no separate permission from `leads:write`.** Reassigning a lead to any team member is gated the same as any other lead mutation — consistent with Doc 15 §2's already-documented "lead visibility is org-wide, a deliberate simplification appropriate for a small internal sales team." Flagged during the architecture review as a choice, not an oversight; revisit only if Riznexia's sales org structure requires per-rep assignment restrictions later.
- **`sort`/`tag` query params extend, not replace, Module M1's filter set** — `stage`/`city`/`category`/`assignedTo`/`q`/cursor pagination are unchanged. Sorting by the joined `business.businessName` uses Prisma's relation-`orderBy` support directly; no new index was needed beyond what Module M1's audit already added (D-015).
- **`PATCH /leads/:id` uses `.strict().refine()`, not a partial-with-defaults schema** — an empty body or an unknown field key is a `400 VALIDATION_ERROR`, not a silently-accepted no-op. `assignedTo: null` (explicit unassign) and an omitted `assignedTo` (leave alone) are distinguished via `Object.hasOwn()` on the parsed input, not by treating `undefined` as meaningful (a JSON body can never contain a literal `undefined`, so this distinction is unambiguous from the wire).
- **Pipeline list/kanban UI and the global `/search` endpoint+UI, both in Doc 21's original M4 task list, were not built** — the module brief was explicit ("Do NOT implement frontend"). Flagged in `docs/21-implementation-roadmap.md`'s M4 entry and TASKS.md rather than silently redefining the module's Definition of Done to match only what was actually delivered.

## M5 — Google Places Synchronization

Before any code was written, the M5 brief's own explicit process gate ("review existing architecture, identify conflicts, present the plan, wait for approval") was followed. Three genuine forks surfaced — Business schema shape, whether the "never depend on Google Places directly" rule applies retroactively to Module M1, and the exact provider-abstraction naming — resolved via `AskUserQuestion`/direct confirmation before implementation started, consistent with D-017/D-023/D-030's precedent.

### D-033: `LocationProvider` interface + `GooglePlacesProvider`, applied to Module M1 too — not just new M5 code

**Context:** The brief was explicit: "Business logic must never directly depend on Google Places APIs. Google Places should be one provider implementation only," with named future providers (Yelp, Facebook, Bing Places, Foursquare, Custom CSV Import). `DiscoveryRunnerService` (Module M1) already existed with a direct `PlacesAdapter` constructor dependency — the rule, read literally, means M1 needs refactoring too, not just new M5 code following it going forward. That's a real scope question: touching a frozen, already-shipped module's internals for an M5-driven abstraction.
**Decision:** Resolved via `AskUserQuestion` — "apply the rule everywhere, including M1" (the recommended, and chosen, option). `LocationProvider` (`apps/api/src/common/providers/location-provider.interface.ts`) is the provider-agnostic contract: `search()` (one page per call — see D-034), `getWebsiteUri()` (cheap tier), `getDetails()` (full tier). `GooglePlacesProvider` wraps `PlacesAdapter` and is the only implementation, registered behind the `LOCATION_PROVIDER` DI token via a new `ProvidersModule` that both `DiscoveryModule` and `PlaceSyncModule` import. `DiscoveryRunnerService`'s constructor now takes `@Inject(LOCATION_PROVIDER) locationProvider: LocationProvider` instead of `PlacesAdapter` directly — `discovery-runner.service.spec.ts` was rewritten against the interface, but `DiscoveryRunnerService`'s _observable_ behavior (FR-1.3/FR-1.7, the 3-page/60-result cap, charge-before-call ordering) is unchanged; only the dependency shape moved. The founder separately confirmed the naming itself (`LocationProvider`/`GooglePlacesProvider`/`LOCATION_PROVIDER`) already matched this plan exactly before implementation began. `CSVImportProvider` is flagged, not built, as a probable future exception to this exact interface shape — file-based ingestion doesn't naturally fit `search()`/`getDetails()` — explicitly out of scope for M5.

### D-034: `PlacesAdapter`/`LocationProvider.search()` is one page per call; the multi-page loop moved to a shared, caller-owned utility

**Context:** Before M5, `PlacesAdapter.searchText()` looped internally up to `MAX_SEARCH_PAGES` (3), sleeping between pages for a fresh `pageToken` to become valid, and returned the fully-collected candidate list. The M5 brief separately requires "pagination," "batch processing," and "progress tracking" as first-class sync-engine features — features that need real per-page control, which an adapter that already flattened multi-page results into one list doesn't expose.
**Decision:** `PlacesAdapter.searchText`/new `searchNearby` each fetch exactly one page (`{candidates, nextPageToken}`) per call — no internal loop, no internal sleep. The loop itself (page cap, inter-page delay, an optional `onPage` progress hook) is now `collectSearchPages()` (`apps/api/src/common/utils/paginate-search.ts`), a small shared utility both `DiscoveryRunnerService` and the new `PlaceSyncRunnerService` call with their own cap/delay constants — avoiding two independent copies of the same pagination logic. This matches the project's existing cursor-based-pagination convention (used throughout the REST API) rather than hiding page-by-page control inside the adapter.

### D-035: Business schema — promote Google Places fields to typed columns; add the five founder-requested fields as a distinct extension

**Context:** `Business` stored coordinates/phone/rating/reviewCount/openingHours/photos/businessStatus only inside the opaque `placesData` JSON blob — fine for M1 (which never queried them), not fine for M5's stated "Business Data" requirement list, which implies these need to be real, filterable fields. Separately, after the initial plan was presented, the founder requested five more fields by name: `googleBusinessUrl`, `websiteDetectedAt`, `websiteDetectionMethod`, `syncVersion`, `sourceProvider`.
**Decision (typed columns):** Resolved via `AskUserQuestion` — "promote to real typed columns" (recommended, chosen). `Business` gains `latitude`/`longitude` (`Decimal(9,6)`), `phone`, `rating`, `reviewCount`, `openingHours`/`photos` (`Json` — structurally variable per provider, kept as real top-level columns rather than buried in `placesData`), and `businessStatus` (`BusinessOperatingStatus` enum: `OPERATIONAL`/`CLOSED_TEMPORARILY`/`CLOSED_PERMANENTLY`, mirroring Google's own field).
**Decision (founder's five fields):** `sourceProvider` is a `BusinessSourceProvider` enum (not a plain string) with every named future provider (`GOOGLE`/`YELP`/`FACEBOOK`/`FOURSQUARE`/`CSV_IMPORT`) declared now — cheap type safety, not built machinery; defaults `GOOGLE`. `syncVersion` starts at 1 on create (schema `@default(1)`, applied by omitting the key on Prisma's create path) and is atomically incremented (`{ increment: 1 }`) on every subsequent sync write. `websiteDetectionMethod` is a `WebsiteDetectionMethod` enum (`GOOGLE_API`/`HEURISTIC_SCAN`/`AI_FALLBACK`/`MANUAL`) recording _how_ `websiteStatus` was last determined — `GOOGLE_API` when Places' own `websiteUri` field settles it (no fetch needed), `HEURISTIC_SCAN` when M1's existing classifier ran against a fetched site; `AI_FALLBACK`/`MANUAL` are reserved attachment points (the AI tier is still deferred, D-005; no manual-edit feature exists yet). `websiteDetectedAt` is stamped on every `upsertByPlaceId` call, deliberately distinct from `updatedAt` (which moves on any field change) since website checks are cached on a different TTL (7 days) than general sync cadence. `googleBusinessUrl` is named provider-specifically on the DB column (the founder's literal ask) but the equivalent field on the provider-agnostic `LocationDetails` interface is named `profileUrl` — the Google-specific name only exists at the write boundary (`BusinessService.upsertByPlaceId`/the runner services), not leaked into the abstraction layer D-033 introduced.
**Not built:** manual-edit-protection machinery for any Business field — no manual-edit path exists anywhere in the system yet (M4 only added `Lead` mutations), so "preserve manual edits" is satisfied by construction today. Flagged as a future attachment point (most likely Module M10), consistent with D-027/D-031's "build what's needed now" precedent — not built speculatively.

### D-036: `PlaceSyncJob` — a new model, not a `DiscoveryJob` extension; six requested progress/cost fields plus a `PARTIAL` status

**Context:** M5's "background job support"/"progress tracking" requirements need a job row with a lifecycle, same shape-of-problem as M1's `DiscoveryJob`. Reusing `DiscoveryJob` directly was considered and rejected on my own judgment (not asked about — no pushback received): it would mean M5 writes to a model M1 owns and the roadmap treats as frozen, and the two modules' job semantics genuinely differ (M5 supports coordinate search and a `PARTIAL` outcome; M1 doesn't). After the initial `PlaceSyncJob` shape was presented, the founder requested six additional fields by name: `duration`, `startedAt`, `finishedAt`, `successRate`, `apiCallsUsed`, `estimatedCost`.
**Decision:** New `PlaceSyncJob` model, `PlaceSyncJobStatus` enum (`QUEUED`/`RUNNING`/`COMPLETED`/`FAILED`/`PARTIAL`). `startedAt`/`finishedAt` mark the actual processing window (distinct from `createdAt`, which is queue time). `duration` (seconds) and `successRate` (`(created+updated)/(created+updated+failed)`, `null` while running or if nothing was attempted) are written once, at completion, not recomputed on every read. `apiCallsUsed`/`estimatedCost` (`Decimal(10,4)`, matching `CostEvent.costUsd`'s existing precedent — not `Float`, to avoid rounding drift on money) are tracked per Places API call actually made (charged inside `collectSearchPages`'s `onPage` hook, one charge per page fetched — more granular than M1's single per-search-operation charge, since these fields exist specifically to report real API usage). `PARTIAL` is its own resolved status (not folded into `FAILED`) because "some candidates succeeded, some failed" is a materially different outcome from "the search itself never returned anything" — `resolveFinalStatus()` in `place-sync-runner.service.ts` picks `COMPLETED` when nothing failed, `PARTIAL` when at least one candidate succeeded and at least one failed, `FAILED` when every attempted candidate failed (or the search itself failed).
**Known limitation, flagged not hidden:** a coordinate-only sync request (no `city`) has no dedicated locality field available from Google's search-tier field mask; `Business.city` falls back to the candidate's full formatted address in that case, which is a worse value than a real city name but strictly better than leaving a required column empty.

### Reviewed and found sound, not changed

- **M5 reuses Module M3's `discovery:run`/`discovery:read` permissions rather than inventing new ones** — `POST /place-sync-jobs` spends the same real Places API budget as `POST /discovery-jobs`, so the same "withheld from Viewer/Developer" floor applies; no new permission string was needed for the RBAC matrix to express that correctly.
- **"Detect duplicates" is the existing exact-`googlePlaceId` dedupe (`BusinessService.upsertByPlaceId`'s `findUnique`-then-`upsert`), extended unchanged to the new sync engine** — not fuzzy cross-listing/near-duplicate matching, which is a materially harder, unrequested data-quality problem.
- **`PlaceSyncRunnerService` also creates a `Lead` via `LeadsService.ensureForBusiness` for a qualifying (none/outdated) candidate**, mirroring `DiscoveryRunnerService` exactly — a business discovered via coordinate search or a keyword sync still needs to enter the sales pipeline the same way a city+category discovery result does; this is "sync" producing the same downstream outcome as "discovery," not new pipeline behavior.
- **Retries (2 attempts, linear backoff) wrap individual provider calls (`search`/`getWebsiteUri`/`getDetails`), not the whole job run** — a candidate that still fails after retries is caught by the per-candidate `try`/`catch` in `PlaceSyncRunnerService.run()` (the same FR-1.8-style isolation M1 already has), so one bad candidate degrades the job to `PARTIAL` rather than failing everything already succeeded.

## M6 — AI Business Analyzer

The founder required a complete AI architecture design — approved through two rounds (an initial architecture plan, then ten mandatory requirements covering prompt versioning, an AI result cache, analysis versioning, provider abstraction, JSON schema validation, cost tracking, retry strategy, logging, forward compatibility, and explicit constraints) — before any code was written, consistent with D-017/D-023/D-030/D-033's precedent for a founder-gated pre-implementation review.

### D-037: `AiTextProvider` interface + `AI_TEXT_PROVIDER` DI token, mirroring M5's `LocationProvider`

**Context:** The brief required an AI provider abstraction supporting Claude/OpenAI/Gemini/DeepSeek/Local LLMs, with business logic never depending on a vendor SDK directly — the same shape of requirement M5's `LocationProvider` already solved for location providers.
**Decision:** `AiTextProvider` (`packages/ai/src/provider/ai-text-provider.interface.ts`) — a single `complete()` method taking `{systemPrompt, userPrompt, model, maxTokens, timeoutMs}` and returning `{rawText, promptTokens, completionTokens, model, stopReason, durationMs}`. `AnthropicProvider` wraps `@anthropic-ai/sdk` and is the only implementation, registered behind the `AI_TEXT_PROVIDER` token via a new `AiModule` (`apps/api/src/common/ai/`) that `BusinessAnalysisModule` imports — the same "one DI wiring point" pattern as M5's `ProvidersModule`/`LOCATION_PROVIDER`. `OpenAiProvider`/`GeminiProvider`/`DeepSeekProvider`/`LocalLlmProvider` are named in the `AiProviderName` Prisma enum (forward-declared, same rationale as `BusinessSourceProvider`) but not built — cheap type safety, not built machinery.
**`AiModule`'s API-key resolution:** Initially wired with `ConfigService.getOrThrow('ANTHROPIC_API_KEY')`, which crashed every existing e2e suite that boots `AppModule` without that env var set (discovery/place-sync/leads/rbac/rate-limit — none of which know about M6). Corrected to `config.get('ANTHROPIC_API_KEY') ?? ''`, matching `PlacesAdapter`'s existing `GOOGLE_PLACES_API_KEY` convention exactly: tolerant at boot, fails as a real upstream auth error only when a call is actually attempted. Own judgment call, not asked about — the established convention was already unambiguous and the alternative broke five existing test suites.

### D-038: `BusinessAnalysis` — typed columns for metadata/lifecycle fields; `brandBrief` stays a single `Json` column

**Context:** The existing model stored everything in two opaque `Json` fields (`brandBrief`, `sentimentSummary`) — fine for a scaffolded M0 placeholder, not fine for M6's requirement that every analysis record prompt name/version/hash, AI provider/model, token usage, cost, execution time, validation status, and a queryable confidence score. The founder's final decision explicitly listed every column to add.
**Decision:** `BusinessAnalysis` gains `analysisVersion` (unique per `businessId`, computed as `MAX(analysisVersion) + 1` inside a transaction, unique constraint as the concurrency backstop — never overwritten, matching the founder's explicit "keep historical analyses" requirement), `promptName`/`promptVersion`/`promptHash`, `aiProvider`/`aiModel` (two new columns replacing the old single `aiModelUsed` string), `inputHash` (the AI result cache key, D-039), `status` (`AnalysisStatus`: `PENDING`/`COMPLETED`/`FAILED` — no `PARTIAL`, unlike M5's `PlaceSyncJobStatus`, because a single AI call either produces a valid structured brief or it doesn't; there's no per-candidate batch to be partially successful over), `confidenceScore` (`Float`, promoted to a typed column specifically so a future "show me low-confidence analyses" query doesn't need to parse JSON — everything else the AI returns stays in `brandBrief`), `rawResponse`/`validationErrors` (populated only on `FAILED`, per the founder's explicit AI Safety requirement to never persist invalid structured data while still keeping a diagnostic trail), `executionTimeMs`/`completedAt`, and `promptTokens`/`completionTokens`/`totalTokens`/`estimatedCost`.
**`brandBrief` deliberately NOT promoted to typed columns:** unlike M5's `Business` fields (D-035), which were promoted because M1/M5 needed to filter/sort on them individually, nothing in this module or its documented consumers (M7 Theme Engine, M8 Website Generator) queries a single field of the 19-field output in isolation — the whole value is always read together. Keeping it as one `Json` column is the same judgment call M2 made for `placesData`, applied consistently.
**Migration:** hand-authored and explicitly non-destructive (the founder's stated requirement) — every new NOT NULL column is added nullable first, backfilled with satisfiable sentinel values for any pre-M6 row (`analysisVersion=1`, `promptName='unknown'`, `promptHash='legacy'`, etc.), then constrained; `ai_model_used` is dropped only after the backfill. Same no-live-database constraint as every prior module's migration (D-020/D-024/D-029/M5).

### D-039: AI result cache — business fingerprint hash compared against the latest COMPLETED analysis's `inputHash`

**Context:** The founder's Implementation Rules required checking a business fingerprint (name/category/rating/reviewCount/reviews/website/phone/address/photos metadata/Google sync version) against the stored fingerprint before calling the AI provider, returning the cached analysis on a match and invalidating on a mismatch.
**Decision:** `computeBusinessFingerprint()` (`apps/api/src/business-analysis/business-fingerprint.ts`) hashes exactly the founder's named fields via SHA-256, including `Business.syncVersion` (D-035's atomically-incrementing sync counter) as the primary change signal — every field in the founder's list is written exclusively through `BusinessService.upsertByPlaceId`, the same path that bumps `syncVersion`, so `syncVersion` alone is already a sufficient signal; the explicit field list is included as a secondary safety net for a future write path (e.g. a manual-edit feature) that might not go through that upsert. `BusinessAnalysisService.triggerAnalysis()` computes the current fingerprint and compares it to the latest `COMPLETED` analysis's stored `inputHash`: a match returns the cached analysis without calling the AI provider (200, "Cache Hit" logged); a mismatch, or no prior `COMPLETED` analysis at all, creates a new `PENDING` row and dispatches the AI call (202, "Cache Miss" logged) — matching Doc 19's async-trigger contract (a cache hit isn't "processing started," so it isn't 202).

### D-040: Two independent retry mechanisms — exponential backoff for transient failures, a separate repair-prompt ladder for validation failures

**Context:** The founder's requirements named both a transient-failure retry strategy (exponential backoff, max 2 retries) and a validation-failure retry strategy (repair prompt, then one more retry, then FAILED) as distinct requirements — Doc 20 §1's "transport retries are separate from quality retries" principle already established this split for the (still-deferred) AI layer in general.
**Decision:** `withExponentialBackoff()` (`packages/ai/src/utils/retry.ts`) is a new, separate utility from M5's `withRetry` (linear backoff) — deliberately not extended from the shared one, so the "transient vs. validation" distinction can never be accidentally conflated, and so `packages/ai` stays free of an `apps/api` dependency. `AiService.analyzeBusiness()` wraps every individual provider call in `withExponentialBackoff` (2 retries, 1s/2s), and separately runs its own 3-attempt ladder for validation failures: initial attempt → 1x same-model repair-prompt retry → 1x escalation to a stronger model (also with a repair prompt) → `FAILED`. The two nest (each of the 3 logical attempts is itself transient-retried), matching both the founder's explicit "retry using a repair prompt, retry one final time, then FAILED" rule and Doc 20 §6's "same-model retry then Opus escalation" ladder.
**Model tiers:** `STANDARD_MODEL = 'claude-sonnet-5'` for attempts 1–2, `ESCALATION_MODEL = 'claude-opus-5'` for attempt 3 (`packages/ai/src/provider/model.constants.ts`) — a two-tier strategy specified by Doc 20 §6 before this module existed, not a cost-driven downgrade decided here; using Opus as the base model would make "escalate to Opus" a no-op and break the documented ladder.

### D-041: Persisting a FAILED analysis — never store invalid structured data, but never lose the diagnostic trail either

**Context:** The founder's AI Safety requirement: "Never persist invalid structured data" on the one hand, "store the raw response, log the validation errors" on the other.
**Decision:** `brandBrief` stays `null` on a `FAILED` row; `rawResponse` (truncated to 64KB — bounds storage on a pathological response without losing diagnostic value) and `validationErrors` (a string array) are stored instead. The same two fields are reused for non-validation failures too (a quota-exceeded pre-flight check, an unrecoverable provider exception) — `validationErrors` holds a single-element array with the exception message in that case, rather than adding a fifth generic-error column beyond the founder's approved list; `rawResponse` stays `null` when there was never a model response to record.

### D-042: `packages/ai` gains a real build step

**Context:** The package was source-only scaffolding through M0–M5 (`main`/`types` pointed at `./src/index.ts`, imported directly by `apps/api`'s Node runtime). M6 is the package's first real implementation, and Doc 21's roadmap already names M7 (Theme Engine)/M8 (Website Generator) as future consumers — likely from a different app context than `apps/api`'s plain Node runtime.
**Decision:** Added `tsc` as the `build` script, `dist/index.js`/`dist/index.d.ts` as `main`/`types` (matching `packages/shared-types`'s existing pattern exactly), and `module: "CommonJS"` in `tsconfig.json` for the same reason `packages/shared-types`/`packages/db` compile to CommonJS — required by `apps/api`'s plain Node runtime today, and a compiled `dist/` is a more stable contract for whichever runtime M7/M8 turn out to use than requiring every future consumer to run TypeScript source directly.

### D-043: `business:analyze` — a new, dedicated permission, not a reuse of `leads:write`

**Context:** The founder was explicit and gave the reasoning directly: an AI analysis call is a real, cost-bearing operation; it must be independently assignable/revocable; future plans include usage limits, billing, quotas, AI analytics, and cost reporting that will want their own permission boundary separate from general lead editing.
**Decision:** `business:analyze` added to the `PERMISSIONS` matrix (`apps/api/src/common/rbac/permission.constants.ts`), granted to the same role set as `discovery:run` (`super_admin`/`admin`/`sales_manager`/`sales_executive` — not `developer` or `viewer`) since both gate real per-call spend the same way. `POST /leads/:id/business` requires it; `GET /leads/:id/business` only requires the existing `leads:read` (reading a cached analysis costs nothing). This is the same "new permission when the action spends real money, not a role-list reuse" judgment as `discovery:run`/`place-sync`'s own permission choice — the difference here is the founder asked for it explicitly rather than it being resolved via `AskUserQuestion`.

### Reviewed and found sound, not changed

- **`GET /leads/:id/business` returns `null` (not a 404) when a lead has no analysis yet** — a missing analysis is a normal state for an otherwise-valid lead, not an error; only an unknown `leadId` itself is a 404 (`LEAD_NOT_FOUND`).
- **Cost charging is a conservative pre-flight reservation (`AI_BUSINESS_ANALYSIS_ESTIMATED_COST_USD`), with the real cost computed from actual token counts persisted on the `BusinessAnalysis` row itself, not reconciled back into the `CostService` ledger** — unlike a Places API call, an LLM call's real cost isn't knowable until it returns (it varies with output length and which of up to 3 retry-ladder attempts actually ran), so `CostService.charge()`'s "reserve before spend" invariant (D-010) is satisfied with a worst-case-sized conservative estimate rather than an exact figure; the accurate number is what's reported per-analysis.
- **`AiService` is Prisma- and NestJS-free** — `BusinessAnalysisRunnerService` (`apps/api`) is the only place an `AiAnalysisOutcome` gets persisted; `packages/ai` has no framework dependency, consistent with D-042's reasoning that it must stay usable by M7/M8 outside `apps/api`'s specific NestJS/Prisma stack.

## M7 — Theme Engine

The founder required a complete Theme Engine architecture (ThemeProvider abstraction, rule-based selection with AI recommendations, the full `ThemeConfiguration` output field list) presented and approved before any code was written — consistent with every prior module's founder-gated pre-implementation review. A follow-up message then resolved two explicit forks the architecture doc had flagged (brand-field sourcing, permission naming) and added three requirements not in the original brief: four additional `ThemeConfiguration` fields, an explicit compatibility-validation gate, and a full-ranking (not single-recommendation) output contract.

### D-044: `ThemeProvider` — registry-shaped, not swap-shaped; `packages/themes` mirrors `packages/ai`'s structure

**Context:** The brief named a `ThemeProvider` abstraction with 8 concrete themes (RestaurantTheme, SalonTheme, DentalTheme, LawFirmTheme, GymTheme, RealEstateTheme, MedicalTheme, CorporateTheme) as its "pluggable" examples — structurally different from M5's `LocationProvider`/M6's `AiTextProvider`, where exactly one implementation is active behind the interface at a time (swap Google for Yelp, swap Claude for GPT). Here all 8 themes are simultaneously available; business logic selects _among_ them, never depends on a concrete one.
**Decision:** `ThemeProvider` (`packages/themes/src/provider/theme-provider.interface.ts`) is registry-shaped: `getTheme(id)`/`listThemes()`. `StaticThemeRegistry` is the sole implementation, aggregating 8 versioned theme-definition modules (one file per theme, e.g. `restaurant.theme.ts`) at construction — adding a ninth theme means adding one file and one registration line in `StaticThemeRegistry`, never touching selection logic. Registered behind the `THEME_PROVIDER` DI token via a new `ThemeModule` (`apps/api/src/common/theme/`), the same single-DI-wiring-point pattern as M5's `ProvidersModule`/M6's `AiModule`. New `packages/themes` package (not folded into `packages/ai` or `apps/api`) mirrors `packages/ai`'s exact structure — a real `tsc`/CommonJS build step from day one (D-042's precedent applied proactively, since M8 is already a known future consumer) — and is Prisma/NestJS-free.
**Theme versioning (founder's explicit requirement):** every `ThemeDefinition` carries `{name, version, hash, createdAt, updatedAt}`; `hash` is a SHA-256 of the theme's fixed content computed at module load (identical technique to M6's `PROMPT_HASH`), so it can never drift from what actually produced a given `ThemeConfiguration`. Themes are versioned code modules, not DB rows — same "prompt templates must never be hardcoded inside business logic, but versioned as reviewed code" precedent M6 established for prompts, applied here to themes.

### D-045: Brand-identity lock — themes adapt to the brand, the brand never adapts to the theme (founder's explicit Decision 1)

**Context:** `BusinessAnalysis.brandBrief` (M6) already contains AI-generated `colorPalette`, `typography`, `layoutStyle`, and `industry` — grounded in that specific business's real data. The Theme Engine architecture doc flagged this overlap directly as an open fork before implementation: do these fields flow through from M6 as-is, or does theme selection regenerate/override them? The founder's follow-up resolved this explicitly and expanded the locked-field list beyond what the architecture doc's fork covered: Brand Personality, Tone of Voice, Color Palette, Typography, Layout Style, Brand Style, Target Audience, Website Sections, and CTA Recommendations are all named as M6-authoritative, never to be regenerated or overridden.
**Decision:** `colorPalette`, `typography`, `layoutStyle`, and `industry` are copied verbatim from `BusinessAnalysis.brandBrief` onto every `ThemeConfiguration` row (`ThemeSelectionService.selectTheme()`) — no code path in this module writes a different value for these fields. The remaining locked fields the founder named (brandPersonality, toneOfVoice, targetAudience, websiteSections, ctaRecommendations) are not part of `ThemeConfiguration`'s own column list (they were never in the original 16-field output spec) — the lock for these is enforced by omission: nothing in this module reads, reclassifies, or persists a competing value for them; they remain readable via the `businessAnalysisId` FK. The one place `websiteSections` is _read_ (not written) is the compatibility scorer's component-availability check (D-046) — a soft coverage check, never a mutation. `sectionOrder` (a `ThemeConfiguration` output field) is theme-owned, not the same thing as `websiteSections`: it's the selected theme's authoritative page-layout arrangement, informed by but not copied from M6's semantic section list.

### D-046: Selection flow — a lightweight, resilient AI classification step feeding a deterministic, always-authoritative rule engine

**Context:** "Theme selection must be rule-based with AI recommendations. AI should recommend. Rules should validate." Given `BusinessAnalysis.brandBrief.industry` is already free text, mapping it onto one of 8 fixed theme categories is a real classification task — better suited to a small AI call than brittle keyword regex alone — but it must never be the sole or final decision-maker.
**Decision:** Reused M6's `AiService` gateway rather than building parallel AI infrastructure — a new `theme-recommendation/v1.0` prompt template (`packages/ai/src/prompt/`) and a new `AiService.recommendThemeCategory()` method, deliberately lighter-weight than `analyzeBusiness()`: single attempt, transient-retried only (`withExponentialBackoff`, same as M6), no repair-prompt ladder or model escalation — a narrow 8-category classification doesn't warrant M6's full 3-attempt ladder. Critically, this method **never throws**: any provider failure or validation failure resolves to a typed `{status: 'failed'}` outcome, never a rejected promise. `ThemeSelectionService` treats a failed recommendation as "no AI signal available" and proceeds with rules alone — the AI step is a pure enhancement, and the module produces a correct result with zero AI availability.
Rules (`packages/themes/src/scoring/compatibility-scorer.ts`, D-047) blend the AI's classification into the industry-compatibility check as one signal among several (keyword overlap, `Business.category`) — capped so AI confidence alone can carry a theme to at most 90/100 on that one check, never fully overriding an absence of real keyword evidence. The AI recommends; the deterministic scorer decides.

### D-047: Compatibility validation, `THEME_NOT_FOUND`, and full ranking (founder's explicit additions)

**Context:** Beyond the original architecture's single-recommendation design, the founder required: (1) `ThemeConfiguration` to carry `themeName`/`themeVersion`/`themeHash`/`selectedAt`/`selectedByEngineVersion`/`compatibilityScore`; (2) explicit compatibility validation across industry/layout/accessibility/mobile/component-availability before selection, with `THEME_NOT_FOUND` returned (never a forced incompatible fit) if nothing clears a minimum score; (3) every compatible theme ranked, not just the top pick, with the full ranking stored for a future manual-selection feature; (4) a dedicated `theme:select` permission, not a reuse of `business:analyze` — theme selection named as its own independent business capability with its own future extensions (premium themes, a theme marketplace, manual override, an approval workflow, agency-specific themes).
**Decision (scoring):** `scoreThemeCompatibility()` computes exactly the five named checks as a weighted composite (industry 40%, layout 20%, accessibility 15%, mobile 10%, component availability 15%) — industry via direct/partial keyword match blended with the AI signal (D-046) plus a Corporate-only floor (40) so it remains a viable universal fallback; layout via fuzzy keyword overlap against M6's free-text `layoutStyle`; accessibility/mobile as real guards against a misconfigured theme definition (not decorative — every registered theme is authored to pass, but the check is genuine); component availability as the fraction of `BusinessAnalysis.brandBrief.websiteSections` the theme's `componentSet`/`sectionOrder` can plausibly cover.
**Decision (gate):** `rankThemes()` filters to themes scoring ≥ `MINIMUM_COMPATIBILITY_SCORE` (50) and sorts descending; an empty result is not treated as "pick the best of a bad lot" — `ThemeSelectionService.selectTheme()` throws `ThemeNotFoundException` (`THEME_NOT_FOUND`, 404), matching the founder's literal instruction.
**Decision (ranking storage):** the full ranked list (every theme that cleared the threshold, with `rank`/`themeId`/`themeName`/`themeVersion`/`themeHash`/`compatibilityScore`) is stored as `ThemeConfiguration.rankedThemes` (Json), with the top entry's data denormalized onto the row's own top-level `themeId`/`themeName`/`themeVersion`/`themeHash`/`compatibilityScore` columns for query convenience — matching the founder's "store the complete ranking for future manual selection" instruction without requiring a separate ranking table for what is, structurally, a small bounded array (at most 8 entries).
**Decision (`selectedByEngineVersion`):** a new `THEME_ENGINE_VERSION` constant (`apps/api/src/theme-engine/theme-engine.constants.ts`), deliberately distinct from an individual theme's own `themeVersion` — this versions the _selection algorithm_ (rule weights, minimum threshold, scoring logic), not the _theme content_, so a future change to the ranking rules is distinguishable in the audit trail from a change to what `RestaurantTheme` itself contains.
**Decision (permission):** `theme:select` added to the `PERMISSIONS` matrix, granted to the same role set as `business:analyze`/`discovery:run` (all three gate real per-call spend or an independently-valuable capability) — not merged into `business:analyze`, per the founder's explicit reasoning about future premium/marketplace/approval-workflow features needing their own permission boundary.
**Decision (synchronous, not fire-and-forget):** unlike M6's `PENDING`/fire-and-forget dispatch (justified there by a potentially-3-attempt, escalation-tier AI ladder), theme selection's AI step is a single lightweight call and the ranking/scoring is pure, fast, synchronous code — `POST /leads/:id/theme` runs the full flow within the request and returns `201 Created` (a cache hit returns the existing configuration, `200 OK`) rather than `202 Accepted`. Own judgment call, not asked about directly — flagged in the architecture doc's presentation and not challenged.

### D-048: Post-review follow-up — `ThemeSelectionService` integrates with M6's `CostService`, no cost-tracking logic duplicated

**Context:** M7 shipped and was reviewed with its AI-recommendation step (D-046) uncosted — `recommendThemeCategory()` calls made no reservation against the monthly ceiling and left no record of provider/model/tokens/actual spend, unlike M6's `BusinessAnalysisRunnerService`, which already reserves-then-logs through `CostService.charge()` (D-010). The founder's explicit follow-up: reuse `CostService` as-is, reserve before the AI call, record actual usage/cost/provider/model/duration after, respect the ceiling, duplicate no cost-tracking logic, and change nothing else about M7's behavior — most importantly, the "AI failure never blocks theme selection" resilience guarantee (D-046) had to survive a new failure mode (`QuotaExceededException`) without any special-casing.
**Decision (no duplication):** the token→USD cost formula, previously private to `BusinessAnalysisRunnerService`, was extracted verbatim into a new shared `apps/api/src/common/cost/ai-cost.util.ts` (`computeActualAiCostUsd`) — both M6's runner and M7's `ThemeSelectionService` now call the same function; neither has its own copy. `AI_THEME_RECOMMENDATION_ESTIMATED_COST_USD` ($0.02) was added to `cost.constants.ts` as M7's own reservation-estimate constant, sized for a single-attempt, standard-model-only, non-escalated classification call (D-046) — far below M6's worst-case 3-attempt Opus-tier estimate.
**Decision (reserve-then-log, folded into the existing resilience boundary):** `costService.charge('theme_ai_recommendation', AI_THEME_RECOMMENDATION_ESTIMATED_COST_USD, {businessId})` is called as the first statement inside `selectTheme()`'s existing AI try/catch, immediately before `aiService.recommendThemeCategory()` — not as a separate try/catch. A `QuotaExceededException` from `charge()` is therefore caught by the exact same handler as a transient AI failure: logged as "AI recommendation unavailable," rules-only ranking proceeds, and `selectTheme()` never fails because of it. This was a deliberate choice not to add a second, differently-shaped resilience path for the cost-ceiling case — one boundary, one behavior, matching "do not change any other behavior."
**Decision (usage capture):** on a `status: 'completed'` recommendation, `ThemeSelectionService` captures `aiProvider`/`aiModel`/`promptTokens`/`completionTokens` from the outcome, computes `totalTokens` and `aiRecommendationCostUsd` (via the shared util), and brackets the AI call with `Date.now()` for `aiRecommendationExecutionTimeMs` locally — `recommendThemeCategory()`'s return type was not widened with a duration field, keeping `packages/ai` unchanged, since the caller can time its own await. These seven values are persisted onto the same `ThemeConfiguration` row the selection already creates; they stay unset (→ `null` in Postgres) whenever the AI step was skipped (ceiling reached) or failed, mirroring `BusinessAnalysis`'s own nullable provider/model/token/cost columns.
**Decision (migration amendment, not a second migration):** the 7 new nullable `ai_recommendation_*` columns were added directly into the `CREATE TABLE "theme_configurations"` block of the existing, unshipped `20260730030000_m7_theme_engine` migration, rather than as a new migration file. This environment has no live database (the same constraint every prior module's migration was authored under), and that M7 migration had never been applied anywhere — amending it in place keeps M7's schema history a single coherent artifact instead of two migrations for a module that never shipped between them. Had the original migration already been applied to a real database, this would instead have been a new, additive migration (the standard non-destructive pattern) rather than an edit to shipped SQL.
**Decision (shared-types nullability):** the 7 new `ThemeConfiguration` fields are required-but-nullable in `themeConfigurationSchema` (`z.string().nullable()`, not `.optional()`) — every row has a defined state (AI ran and produced usage data, or it didn't and every field is explicitly `null`), so `undefined` (the key silently missing) is treated as a shape error, not a valid third state. Same convention M6 already established for its own provider/model/token/cost columns.

### Reviewed and found sound, not changed

- **`GET /leads/:id/theme` returns `null` (not a 404) when a lead has no theme configuration yet** — same precedent as M6's `GET /leads/:id/business`; only an unknown `leadId` itself is a 404.
- **`POST /leads/:id/theme` throws `BusinessAnalysisNotFoundException` (reused from M6, not a new code) when no `COMPLETED` `BusinessAnalysis` exists** — theme selection has a hard dependency on M6 having produced brand-identity fields; there is no fallback path that invents them.
- **`packages/themes`'s theme-definition content is authored data, not generated** — 8 hand-written modules with deliberately distinct, industry-appropriate structural defaults (e.g. Dental/Medical/Law Firm carry a stricter `AAA` accessibility profile and `subtle`/`none` animation than Restaurant/Gym's `AA`/`moderate`-`expressive`) — a real design pass, not placeholder data, since "production-ready" was the explicit instruction.

## M8.1 — Layout Generator (phase 1 of 4, Module M8 — Website Generator)

The founder is building Module M8 across four internal implementation phases (M8.1 Layout Generator, M8.2 Component Generator, M8.3 Content Binding, M8.4 React/Next.js Assembly) — explicitly phase boundaries only, not a roadmap restructuring; `docs/21-implementation-roadmap.md`'s M8 entry is untouched (D-022's frozen-roadmap discipline still applies). The M8.1 brief specified objective/inputs/outputs/determinism requirement/validation list directly; an architecture was then presented (package placement, `LayoutConfiguration` shape, derivation rules) with three open forks flagged, all resolved before implementation — same pre-implementation gate as every prior module.

### D-049: `sectionComponentMap` — closing a real gap in M7's theme data model, not a heuristic

**Context:** M8.1's brief requires `LayoutConfiguration.componentPlaceholders` to bind theme components to page sections. But M7's `ThemeDefinitionContent` (`packages/themes`) had no such link: `componentSet` (e.g. `['hero-banner', 'menu-showcase', ...]`) and `sectionOrder` (e.g. `['hero', 'about', 'menu', ...]`) were two independent flat lists. Founder's resolved fork, offered three options (extend the M7 data model explicitly; guess via name-matching heuristics; keep components and sections decoupled) — chose the first.
**Decision:** Added `sectionComponentMap: Record<string, string[]>` to `ThemeDefinitionContent`, populated by hand for all 8 existing theme definitions (verified: every `componentSet` entry appears in exactly one section's array, every map key is a real `sectionOrder` entry — enforced by a new `static-theme-registry.test.ts` invariant test). Copied through onto the persisted `ThemeConfiguration` row exactly like `componentSet`/`sectionOrder` themselves (`ThemeSelectionService.selectTheme()`), and into `themeConfigurationSchema` (`packages/shared-types`) as a required-but-present field. The new column was folded directly into the still-unshipped `20260730030000_m7_theme_engine` migration (same amendment rationale as D-048) rather than a second migration.
**Why not the heuristic:** name-matching (`'menu-showcase' -> 'menu'`) would silently break for a 9th theme that didn't follow the naming convention, and encodes an undocumented assumption as string-matching logic instead of an explicit, test-verified data contract.

### D-050: `packages/website-generator` — one package per module, one subdirectory per phase

**Context:** M8 is one module built across four sequential internal phases that all operate on the same evolving artifact (a generated website), unlike M6/M7 which were each a single self-contained capability with their own dedicated package (`packages/ai`, `packages/themes`).
**Decision:** A single new `packages/website-generator` package, mirroring `packages/ai`'s internal-subdirectory structure (`prompt/`, `validator/`, `gateway/`, `provider/`) rather than `packages/ai`/`packages/themes`'s one-package-per-module precedent taken literally as one-package-per-capability. This phase populates `layout/`; M8.2/M8.3/M8.4 are expected to add `component/`, `content-binding/`, `assembly/` alongside it as they're built, avoiding three additional near-empty packages. Real `tsc`/CommonJS build from day one (D-042 precedent), Prisma/NestJS-free — `generateLayout()` has no framework dependency, same "must stay usable outside apps/api's specific stack" reasoning as `packages/ai`/`packages/themes`.

### D-051: `generateLayout()` — pure, deterministic derivation from fixed lookup tables only

**Context:** "Given the same BusinessAnalysis and ThemeConfiguration, it must always generate the same LayoutConfiguration. No randomness." — an explicit, testable determinism requirement, stronger than M6/M7's "no AI" boundary (M7 still calls an AI service, just non-authoritatively; M8.1 calls no external service at all).
**Decision:** Every `LayoutConfiguration` field is either a verbatim pass-through of a `ThemeConfiguration` value (`navigation.style`, `hero.style`, `footer.style`, `ctaPlacements[].style` — same brand/theme-identity-lock discipline as D-045: this module derives structural parameters from a style the theme already chose, it never picks a different one) or computed from a fixed `Record<InputEnum, OutputValue>` lookup table (e.g. `heroStyle -> mediaPosition`, `footerStyle -> columns`, `animationLevel -> gap`) or simple arithmetic over array lengths/positions (`ctaSlots = min(ctaRecommendations.length, 2)`, `pageStructure` order = `sectionOrder` index). No `Date.now()`/`Math.random()`/I/O inside `generateLayout()` itself — the one true timestamp (`createdAt`) is stamped by the Prisma column default at persistence time, not by the generator. Verified by a unit test asserting three consecutive calls with identical input produce `toEqual`-identical output.
**Decision (grid derivation):** a section renders as a `'grid'` `layoutType` when it has at least one mapped component (via D-049's `sectionComponentMap`) and isn't the hero section — reframing "grid" as "this section's content is a component collection, rendered in a responsive grid regardless of item count" rather than "multiple distinct component types in one section" (which the current 8 themes' data — one component per section, at most — would never trigger). Column counts are a fixed `{mobile:1, tablet:2, desktop:3}` constant; `gap` varies by `animationLevel`.
**Decision (no display copy):** `navigation.items` and `componentPlaceholders[].componentId`/`.sectionId` carry theme-authored ids verbatim, never human-readable labels — inventing display text is a content concern (M8.3 Content Binding), out of scope per the brief's explicit "must NOT generate website content" constraint.

### D-052: Validation-failure semantics — an internal assertion, not a new domain exception

**Context:** The brief requires validating required sections, responsive rules, accessibility constraints, navigation integrity, and section ordering. Founder's resolved fork: should a failure be a real, catchable business outcome (M7's `THEME_NOT_FOUND` precedent) or an internal bug signal?
**Decision:** `validateLayoutConfiguration()` throws a plain `Error` (not an `AppException` subclass, no new HTTP error code) on any invariant violation. Reasoning: `generateLayout()`'s inputs are already M6/M7-validated, and every derivation rule is a fixed lookup over a known, finite domain — there is no legitimate input shape that should cause a validation failure. A failure here means a bug in the generator itself, not a "the data genuinely doesn't support a good outcome" case like M7's compatibility-scoring gate. `LayoutGenerationService` does not catch this error — it propagates as an unhandled 500, the correct signal for an internal invariant violation.

### D-053: API exposure this phase — `GET/POST /leads/:id/layout`, new `layout:generate` permission

**Context:** The M8.1 brief specified inputs/outputs/architecture but not an endpoint. Founder's resolved fork, consistent with M6/M7 both shipping their endpoint the same phase they shipped their engine: ship it now rather than wait for a later M8 phase.
**Decision:** `LayoutGenerationController` (`apps/api/src/layout-engine/`) — `GET` (returns the latest configuration or `null`, gated by `leads:read`) / `POST` (generates, gated by a new dedicated `layout:generate` permission, same role set as `theme:select`/`business:analyze` — same "independently-assignable capability" reasoning as D-047's permission decision, not merged into `theme:select`). Cached per `themeConfigurationId` (the more specific of `LayoutConfiguration`'s two upstream dependencies, since `ThemeConfiguration` is itself already FK'd to `businessAnalysisId`) — a repeat call against the same theme configuration returns the existing row (`200`) rather than regenerating; a genuinely new one persists (`201`), same synchronous-completion convention as M7's own `POST` (no `PENDING`/`202` — `generateLayout()` is fast, pure, synchronous code, an even stronger case for this than M7's single AI call). New `ThemeConfigurationNotFoundException` (`THEME_CONFIGURATION_NOT_FOUND`, 404) for the hard dependency on a persisted M7 `ThemeConfiguration` — mirrors `BusinessAnalysisNotFoundException`'s role for M7's own hard dependency on M6.

### D-054: `LayoutConfiguration` persistence — versioned, dual-FK provenance, Json-blob compound fields

**Context:** Needs the same "never overwrite, full audit trail" discipline as `BusinessAnalysis`/`ThemeConfiguration`, but is the first M8-family model with two upstream dependencies (`BusinessAnalysis` _and_ `ThemeConfiguration`) rather than one.
**Decision:** New `LayoutConfiguration` Prisma model, `configVersion` versioned per business (never overwritten, `@@unique([businessId, configVersion])`, same allocation pattern as `BusinessAnalysis.analysisVersion`/`ThemeConfiguration.configVersion`), FK'd to both `businessAnalysisId` and `themeConfigurationId` (`onDelete: Cascade` on both, matching every prior FK in this schema) for full provenance — a website generated today stays traceable to the exact brand brief and theme selection it came from, even after either is superseded by a later re-run. Every compound structure (`pageStructure`, `navigation`, `hero`, `footer`, `grid`, `responsiveRules`, `ctaPlacements`, `componentPlaceholders`) is a single `Json` column — same "the whole value is read together" reasoning as `ThemeConfiguration.colorPalette`/`.typography` (D-038): nothing in this module or its documented future consumers (M8.2/M8.3/M8.4) queries an individual sub-field in isolation. `sidebar` is the one nullable `Json?` column (populated only when `navigationStyle === 'sidebar'` — untriggered by any of the 8 current themes, but forward-compatible). New, purely additive migration (`20260731000000_m8_1_layout_generator`) — a genuinely new table for a new module, unlike D-049/D-048's amendments to M7's own still-unshipped migration.

## M8.2 — Component Generator (phase 2 of 4, Module M8 — Website Generator)

The founder's phase brief specified the objective, inputs/outputs (BusinessAnalysis + ThemeConfiguration + LayoutConfiguration → `ComponentManifest`), the determinism/no-hallucination requirements, the validation list, and — in a follow-up message — an explicit Theme Tokens requirement with concrete examples (`token.primary`, `token.radius.large`, `token.heading`, `token.spacing.md`). An architecture was then presented (package placement, the full `ComponentManifest`/`ThemeTokens` shape, the deterministic derivation rules) with two open forks flagged, both resolved before implementation — same pre-implementation gate as every prior module/phase.

### D-055: A closed `SupportedComponentType` taxonomy, classified via a single global registry — not per-theme, not a naming heuristic

**Context:** "Only supported components may be generated" requires collapsing the ~31 distinct free-text `componentId`s across the 8 M7 themes (`menu-showcase`, `listing-grid`, `class-schedule`, `faq-accordion`, ...) onto a small closed enum. Founder's resolved fork, offered three options (extend `ThemeDefinitionContent` again, explicitly, per-theme, mirroring D-049's `sectionComponentMap`; classify by componentId name pattern; ship with no sub-typing this phase) — chose the first, "extend the data model explicitly."
**Decision:** Rather than literally duplicating a `componentType` field across all 8 theme definitions (as D-049's `sectionComponentMap` legitimately does, since section names vary theme to theme), classification is a single global lookup — `COMPONENT_TYPE_REGISTRY: Record<string, SupportedComponentType>` (`packages/themes/src/provider/component-type-registry.ts`) — because a `componentId` like `hero-banner` means the same structural thing in every theme that uses it; duplicating the mapping 8 times would risk inconsistent classification across themes with no benefit. This is still the founder's chosen "extend the explicit data model" resolution, just normalized to one source of truth instead of eight copies of an identical mapping. A new registry test (`static-theme-registry.test.ts`) asserts every theme's `componentSet` entries are covered. `generateComponentManifest()` (`packages/website-generator`) throws a plain `Error` if it ever encounters an unclassified `componentId` — the "no hallucinated components" guard is enforced at generation time, not just by the closed TypeScript enum.
**The 16-type taxonomy:** 3 structural types the generator itself introduces (`navigation`, `section`, `sidebar`) plus 13 theme-owned types covering all 31 known `componentId`s (`hero`, `card-grid`, `profile-grid`, `carousel`, `cta-banner`, `logo-strip`, `info-panel`, `accordion`, `schedule-table`, `pricing-table`, `search-form`, `map-embed`, `menu-list`).

### D-056: Two-level component hierarchy — section wrapper → theme component, no synthetic sub-children

**Context:** `ComponentDefinition` carries both `parentComponentId` and `childComponentIds`, but the fields alone don't dictate how deep the hierarchy should go — e.g. should a `card-grid` component pre-declare individual card children now? Founder's resolved fork: stay at 2 levels this phase; a fixed-count 3rd level was the alternative, rejected because the count would be arbitrary until real content exists.
**Decision:** A synthetic `section` wrapper component per `LayoutConfiguration.pageStructure` entry (root-level, `parentComponentId: null`), with that section's mapped theme component(s) — from M8.1's `componentPlaceholders` — as its `childComponentIds` (each with `parentComponentId` pointing back). A root-level `navigation` component (cross-cutting, not tied to any single section) and an optional `sidebar` component (only when `LayoutConfiguration.sidebar` is populated — D-054) round out the manifest; both have empty `childComponentIds`. No individual cards/list items are pre-declared inside grid-type components — their count depends on bound content, explicitly out of scope until M8.3 (Content Binding) exists. `validateComponentManifest()` enforces parent/child pointer consistency both directions (a listed child's own `parentComponentId` must match).

### D-057: Theme Tokens (founder's explicit requirement) — one resolved set per manifest, every component references by path string

**Context:** "Component Manifest me direct values ki jagah tokens reference kare" — components must reference `token.primary`/`token.radius.large`/`token.heading`/`token.spacing.md`-style paths, never embed resolved color/font/radius values directly.
**Decision:** `ThemeTokens` (computed once per manifest by `computeThemeTokens()`, `packages/website-generator/src/component/component-tokens.ts`) holds the actual resolved values — `primary`/`secondary`/`accent`/`background`/`text` (verbatim from `ThemeConfiguration.colorPalette`), `heading`/`body` (verbatim from `.typography`), `button`/`card`/`animation` (verbatim `ctaStyle`/`cardStyle`/`animationLevel`), plus two fixed universal scales `radius: {small,medium,large,full}` and `spacing: {xs,sm,md,lg,xl}` (same "fixed constant, not derived from either input" technique as M8.1's `BREAKPOINTS`, D-051), and `shadow` (the one token whose _resolved value_ is theme-derived, via a fixed `cardStyle → shadow` lookup table). Every `ComponentDefinition.themeTokens` field is `Record<string, string>` of **reference paths only** (e.g. `{backgroundColor: 'token.background', radius: 'token.radius.large'}`) — never a copied value; the manifest's own top-level `themeTokens` is the single source of truth every reference resolves against. Which `radius` rung a component defaults to (`small`/`medium`/`large`) is theme-derived via `cardStyle` (`defaultRadiusToken()`), authored per `SupportedComponentType` in `component-type-definitions.ts` alongside each type's content-slot/accessibility rules.

### D-058: Content contract, not content — `requiredContent`/`optionalContent`/`placeholders` never carry business copy

**Context:** The brief requires "Required Content", "Optional Content", and "Placeholder Definitions" per component, while explicitly forbidding "website content" generation — these must declare a content _shape_, never a bound value.
**Decision:** `requiredContent`/`optionalContent` are `ContentSlot[]` (`{slotName, kind}`, `kind` ∈ `text|image|icon|link|list`) — a fixed, hand-authored table per `SupportedComponentType` (`COMPONENT_TYPE_DEFINITIONS`, `component-type-definitions.ts`), same "authored data, not generated" discipline as M7's 8 theme definitions. `placeholders` is the flattened, binding-ready view of both lists, each entry adding `required: boolean` and a `placeholderLabel` — a generic structural label derived purely from `slotName` by deterministic string transform (`backgroundImage` → `"[Background Image]"`), never AI-generated or business-specific text; this is a structural/editor-preview marker, not generated website content. The one direct use of `BusinessAnalysis` beyond what's already threaded through `ThemeConfiguration`/`LayoutConfiguration`: a `hero` component gets an additional optional `trustSignal` slot only when `brandBrief.trustSignals` is non-empty for this specific business — real data presence gating a slot's existence, not content generation.

### D-059: `ComponentManifest` persistence — versioned, triple-FK provenance, same Json-blob-for-compound-structures pattern

**Context:** The third M8-family model, now with three upstream dependencies (`BusinessAnalysis`, `ThemeConfiguration`, `LayoutConfiguration`).
**Decision:** New `ComponentManifest` Prisma model, `configVersion` versioned per business (never overwritten, same pattern as every prior M6-M8 output), FK'd to all three inputs (`onDelete: Cascade` on each) for full provenance. `themeTokens` and `components` are single `Json` columns — same "the whole value is read together" reasoning as every other compound-structure column in this schema. Cached per `layoutConfigurationId` (the most specific of the three dependencies, since `LayoutConfiguration` is itself already FK'd to both others) — a repeat call against the same layout configuration returns the existing manifest (`200`) rather than regenerating; a genuinely new one persists (`201`). New, purely additive migration (`20260801000000_m8_2_component_generator`). New `component:generate` permission (same role set as `layout:generate`/`theme:select`) and `LayoutConfigurationNotFoundException` (`LAYOUT_CONFIGURATION_NOT_FOUND`, 404) for the hard dependency on a persisted M8.1 `LayoutConfiguration` — mirrors `ThemeConfigurationNotFoundException`'s role for M8.1's own hard dependency on M7. `GET/POST /leads/:id/components` shipped this phase, consistent with M6/M7/M8.1's own precedent (not re-litigated as a fork this time).

### D-060: Validation-failure semantics carried forward unchanged from D-052

**Context:** Same question M8.1 already resolved: should `validateComponentManifest()` failures be a new domain exception or an internal-bug signal?
**Decision:** Not re-opened as a fork this phase — `validateComponentManifest()` throws a plain `Error` on any invariant violation (hierarchy/parent-child integrity, exactly one `navigation` component, a `sidebar` component's visibility tied to its own presence, accessibility metadata well-formed, responsive grid columns monotonic), same internal-assertion semantics as D-052, for the same reason: every input is already M6/M7/M8.1-validated and every rule here is a fixed lookup, so a failure means a generator bug, not a legitimate business outcome.

## M8.3 — Content Binding (phase 3 of 4, Module M8 — Website Generator)

The founder's phase brief specified the objective ("bind existing structured data, never generate new content"), inputs/outputs, the no-AI/deterministic-mapping requirement, the validation list, and an explicit "every field traceable to its origin" requirement with a concrete `{value, source}` example. An architecture was then presented (package placement, the full `ContentManifest` shape, the deterministic binding rules) with three open forks flagged, all resolved before implementation — plus two data-model gaps discovered and resolved without re-blocking (D-062).

### D-061: An explicit `unresolvedBindings` gap list — never a hard failure, never a fabricated value

**Context:** Several `SupportedComponentType`s from M8.2 have a _required_ content slot with genuinely no real upstream data anywhere in the pipeline — `accordion` (FAQ), `schedule-table`, `pricing-table`, `logo-strip`, `profile-grid` (individual team members). Taken literally, the brief's "every required component has content" and "never invent facts / never store anonymous content" are incompatible for gym/dental/law-firm/salon/real-estate/corporate themes (all of which include at least one such type). Founder's resolved fork, offered three options (explicit gap list, manifest still validates; hard-fail generation for any theme with an unsourceable required component; silently omit with no flag) — chose the first.
**Decision:** `ContentManifest.unresolvedBindings[]` records `{componentId, slotName, required, reason: 'no-source-available'}` for every slot — required or optional — that has no real source. `validateContentManifest()` requires every _required_ slot to be either bound with a real `SourcedValue` or explicitly present in `unresolvedBindings` — never silently missing, never fabricated. The manifest as a whole still validates successfully; the gap is visible and traceable rather than hidden or invented. `CONTENT_UNRESOLVED_REASONS` is a closed one-value enum (`'no-source-available'`) so a future reason is a deliberate schema change.

### D-062: Two data-model gaps found and resolved without re-blocking — `Business` as a necessary additional input, `placesData.fullDetails.reviews` deliberately not used

**Context:** While designing the binder, two real gaps surfaced against the phase brief's own stated input list and output requirements.
**Decision (Business as a 5th input):** "Contact Information", "Business Hours", "Gallery References", and `LocalBusiness`/`Organization` structured data are impossible to bind from `BusinessAnalysis`/`ThemeConfiguration`/`LayoutConfiguration`/`ComponentManifest` alone — none of those carry phone/address/photos/hours/rating; only the M2/M5 `Business` record does. Rather than re-block on a fourth AskUserQuestion fork (there was no real alternative that kept those four output categories real), a minimal `BusinessContactInfo` interface (`packages/shared-types/src/content-manifest.ts`) was added as a necessary 5th input to `generateContentManifest()`, mapped from the Prisma `Business` row by a new `toBusinessContactInfo()` (`apps/api/src/content-engine/dto/business-contact-info.mapper.ts`). `openingHours` stays fully opaque (`unknown`, passed through verbatim) — no stable typed contract for Places' opening-hours shape exists anywhere in this codebase, so parsing/reformatting it would risk misrepresenting real data.
**Decision (real Google review text not used):** `Business.placesData` (opaque `Json`, `fullDetails.reviews: PlaceReview[]`) sometimes contains real customer review text — a stronger testimonials source than `socialProofSuggestions` (D-063). Deliberately not used this phase: `placesData`'s shape is not a stable typed contract (it varies depending on which sync path wrote it — `discovery-runner.service.ts`'s early write has no `fullDetails` at all), and reaching into an undocumented opaque blob from a pure, typed content-binder was judged the wrong tradeoff for this phase. Flagged in the review report as a known limitation / future refinement opportunity, not silently implemented.

### D-063: Testimonials bind from `socialProofSuggestions`/`trustSignals`, honestly labeled as AI-suggested angles

**Context:** No verbatim customer-quote text exists anywhere in the typed pipeline (see D-062). Founder's resolved fork: bind from BusinessAnalysis's real (if AI-suggested rather than verbatim) social-proof fields, vs. treat as unsourced like FAQ.
**Decision:** `carousel.items` (the `testimonial-carousel` component type) binds from `BusinessAnalysis.brandBrief.socialProofSuggestions`, `source: 'BusinessAnalysis.brandBrief.socialProofSuggestions'` — never mislabeled as an actual customer review. This is real, typed analysis output, honestly sourced; the founder's guidance was that a suggested social-proof angle, correctly labeled as such, satisfies "traceable to origin" even though it isn't a literal quote.

### D-064: SEO meta title assembled via a fixed template; meta description mapped verbatim (no template needed)

**Context:** No single upstream field is a "meta title." Founder's resolved fork: fixed-template assembly from real fields (every word traceable, template itself is non-creative scaffolding) vs. leaving `metaTitle`/`metaDescription` unresolved entirely.
**Decision:** `metaTitle = "${Business.businessName} | ${BusinessAnalysis.brandBrief.industry} in ${Business.city}"`, `source: 'Business.businessName+BusinessAnalysis.brandBrief.industry+Business.city'` — the template never varies, every word traces to a real field, same class of technique as M8.1/M8.2's structural `titleCase()`/`placeholderLabel` transforms. `metaDescription`, on reflection, needed no template at all — `BusinessAnalysis.brandBrief.businessSummary` already reads like a description, so it's mapped verbatim, `source: 'BusinessAnalysis.brandBrief.businessSummary'`. Because `businessName`/`industry`/`city`/`businessSummary` are all guaranteed non-empty by upstream schema constraints (M2's non-nullable columns, M6's `min(1)` schema), both SEO fields are always resolvable in practice — `validateContentManifest()`'s "SEO metadata completeness" check never expects them to appear in `unresolvedBindings`.

### D-065: CTA targets are internal componentId references, not fabricated HTML anchors

**Context:** "CTA targets exist" needs something concrete to validate against. Every M7 theme's `sectionOrder` places `'contact'` immediately before `'footer'` (verified across all 8) — a deterministic, always-resolvable target.
**Decision:** Every CTA-shaped binding (`hero.primaryCta`, `cta-banner.ctaLink`) resolves its target to the real `section-contact` componentId in the same `ComponentManifest` (falling back to the last non-footer section if a future theme lacks a literal `'contact'` section). Represented as `targetComponentId` — an internal reference within the same manifest, not a fabricated `href`/anchor string — since generating HTML anchor syntax would be premature (that's M8.4's job). `validateContentManifest()`'s "CTA targets exist" check walks every link-kind field's `targetComponentId` and confirms it resolves to a real component.

### D-066: `ContentManifest` persistence — versioned, quad-FK provenance, same Json-blob-for-compound-structures pattern

**Context:** The fourth M8-family model, now with four upstream dependencies.
**Decision:** New `ContentManifest` Prisma model, `configVersion` versioned per business (never overwritten, same pattern as every prior M6-M8 output), FK'd to all four inputs (`onDelete: Cascade` on each) for full provenance. `componentContent`/`unresolvedBindings`/`seoMetadata`/`structuredData` are single `Json` columns — same "the whole value is read together" reasoning as every other compound-structure column in this schema; every value inside still carries its own `source` string, enforced by Zod at the application layer (not a DB constraint — Postgres has no native way to require a sibling key inside a JSONB blob). Cached per `componentManifestId` (the most specific of the four dependencies). New, purely additive migration (`20260802000000_m8_3_content_binding`). New `content:bind` permission (same role set as `component:generate`/`layout:generate`/`theme:select` — named for the verb this module actually performs) and `ComponentManifestNotFoundException` (`COMPONENT_MANIFEST_NOT_FOUND`, 404) for the hard dependency on a persisted M8.2 `ComponentManifest`. `GET/POST /leads/:id/content` shipped this phase, consistent with M6/M7/M8.1/M8.2's own precedent (not re-litigated as a fork).

### D-067: Validation-failure semantics carried forward unchanged from D-052/D-060

**Context:** Same question M8.1/M8.2 already resolved.
**Decision:** Not re-opened as a fork this phase — `validateContentManifest()` throws a plain `Error` on any invariant violation (no orphan bindings, no duplicated bindings, no slot both bound and unresolved, every required slot bound-or-unresolved, CTA targets exist, SEO/schema.org completeness), same internal-assertion semantics as D-052/D-060, for the same reason.

## M8.4 — React/Next.js Website Assembly (phase 4 of 4, Module M8 — Website Generator)

The founder's phase brief specified the objective, inputs (all five prior M6-M8.3 artifacts), the full technology stack (Next.js App Router, React, TypeScript, Tailwind, shadcn/ui, Framer Motion, next-seo, React Hook Form, Zod), accessibility/SEO/performance requirements, the validation list, and an explicit "must build and run with zero manual edits" requirement — followed by a founder-authored **Additional Architecture Requirement**, quoted directly: _"The Website Assembly Engine must use templates... Never concatenate JSX strings. Never generate source code using string templates. Use structured template rendering so websites remain maintainable and deterministic."_ An architecture was then presented resolving that requirement concretely, with two open forks flagged (persistence model, component breadth), both resolved before implementation.

### D-068: "Templates, not string concatenation" — static, pre-authored components plus TypeScript Compiler API for the two files that truly vary

**Context:** The founder's constraint rules out both naive string-concatenated JSX and a templating-language approach (Handlebars/EJS-over-JSX) that would still ultimately serialize to unchecked strings. Every other M8 phase's "deterministic, fixed lookup" discipline needed an equivalent for _source code generation_ specifically.
**Decision:** Two-tier design. **Tier 1 — templates are real, static, production-quality `.tsx`/`.ts` files** (`packages/website-generator/templates/nextjs-base/`), one per `SupportedComponentType` (16) plus a `Footer`/`SectionWrapper` plus the full Next.js project skeleton (config files, `app/layout.tsx`, shadcn/ui primitives, `lib/` helpers) — authored once, byte-identical across every business/theme, never generated or modified at runtime; read verbatim off disk (`static-template-loader.ts`). **Tier 2 — only structured _data_ varies per business**, expressed as literal JS objects, never as source text: `lib/site-data.ts` (one type-annotated `export const <id>Props: <ComponentPropsType> = {...}` per component) and `app/page.tsx` (which components render, in what order, wrapped in what JSX) are the only files with per-business content, and both are built via the **TypeScript Compiler API** (`ts.factory.*` + `ts.createPrinter()`, `assembly/ts-ast-helpers.ts`) — a real AST is constructed and printed, so output is syntactically valid by construction; there is no step where a JS value is interpolated into a string that becomes source code. `theme-tokens-css-generator.ts`/`seo-files-generator.ts` follow the same AST-or-fixed-line-serializer discipline for their own outputs (CSS custom properties, `robots.ts`/`sitemap.ts`/`manifest.ts`).
**Resolved forks (AskUserQuestion, before implementation):** (1) persistence — new `GeneratedWebsite` Prisma model, `files: Json` as `{path, content}[]`, same convention as every M6-M8.3 artifact (no S3/object storage exists anywhere in this stack) — chosen over inventing new infrastructure. (2) component breadth — all 16 `SupportedComponentType`s built now to one consistent, real, accessible standard, chosen over a smaller reference slice, since a partial set would leave 5 of 8 themes unable to fully assemble.

### D-069: One combined, type-annotated props object per component — not a single `as const` data blob

**Context:** `page.tsx`'s JSX needs to be uniform (`<ComponentName {...xProps} />` for every component regardless of type) while still being fully type-checked against each component's own props interface (which mixes string-literal unions like `CtaStyle`/`MediaPosition` with ordinary mutable arrays like `SourcedTextList.value: string[]`). The first design tried a single `export const siteData = {...} as const` object — `as const` correctly narrows literal-union properties, but also turns every array into a readonly tuple type, which TypeScript then refuses to assign to the static components' plain `string[]`-typed props (`The type 'readonly [...]' is 'readonly' and cannot be assigned to the mutable type 'string[]'`).
**Decision:** `component-props-mapper.ts` merges each `ComponentDefinition`'s bound `ContentManifest` fields with its structural/theme-derived values (`mediaPosition`, `ctaStyle`, grid `columns`, `sticky`, `mobileBehavior`, section `layoutType`, ...) into one plain JS object per component, computed once at generation time by iterating `componentManifest.components` (Node.js, not the generated project's runtime). `site-data-generator.ts` emits one `export const <componentId>Props: <ComponentPropsType> = {...}` per component instead — a plain **type annotation**, not `as const`: TypeScript's contextual typing against the named interface narrows literal-union properties correctly while leaving arrays as ordinary mutable `string[]`, satisfying both constraints at once. `component-template-registry.ts` is the fixed lookup from `SupportedComponentType` to `{componentName, propsTypeName, importPath}` that both `site-data-generator.ts` and `page-ast-generator.ts` share, so they always agree on which static component and props shape a given `ComponentDefinition` maps to.

### D-070: JSON-LD via a raw `<script type="application/ld+json">`, not next-seo's per-type components

**Context:** `next-seo` is a stated stack dependency, and its `LocalBusinessJsonLd`/`OrganizationJsonLd`/`BreadcrumbJsonLd`/`FAQPageJsonLd` components are the obvious first choice for the SEO requirement's "JSON-LD" line — but each expects schema.org fields pre-decomposed (e.g. `address` as `{streetAddress, addressLocality, ...}`, `aggregateRating` as `{ratingValue, reviewCount}`) that M8.3's binder never produced (it only ever combined a single "street, city" string and a single human-readable "4.5/5 (120 reviews)" string — see `seo-binder.ts`). Forcing that decomposition here would mean inventing structure the data doesn't actually have, violating the same "never fabricate" discipline every prior phase has held to.
**Decision:** `jsonld-mapper.ts`'s `structuredDataToJsonLd()` converts each `StructuredDataBinding` into a real schema.org object using only the fields M8.3 actually bound, emitted in `page.tsx` as a plain `<script type="application/ld+json" dangerouslySetInnerHTML={{__html: ...}}>` — the idiomatic Next.js App Router pattern for structured data, and Next.js's own documented recommendation. `address` as a plain string is valid schema.org (the property's range includes `Text` directly, not only `PostalAddress`). `aggregateRating` is knowingly emitted as a plain human-readable string rather than a proper `AggregateRating` object — flagged as a known limitation (the assembler has no access to the original numeric `rating`/`reviewCount` fields, only M8.3's already-combined string) rather than silently accepted as correct. `next-seo` remains a declared dependency (matches the stated stack) but is not wired into JSON-LD generation.
**Related fix (`section-wrapper.tsx`):** the real `npm run build` smoke test (D-074) caught that `SectionWrapperProps.children` was typed as required, but the generated `lib/site-data.ts` never includes a `children` field (real child components are injected via JSX nesting in `page.tsx`, not spread as a prop) — a section with zero mapped children (a legitimate case, not hypothetical) failed `next build`'s typecheck. Fixed by making `children?: React.ReactNode` optional on the static template component, the only change made to a template file after the real build surfaced it.

### D-071: `businessName` is read back out of `ContentManifest.structuredData`, not passed as a 6th input

**Context:** No M8.x manifest has a dedicated `businessName` field of its own — it lives only on the raw `Business` Prisma row, which sits outside the four manifests the assembler's core function actually needs (`ThemeConfiguration`/`LayoutConfiguration`/`ComponentManifest`/`ContentManifest`). The phase brief names `BusinessAnalysis` as one of "5 manifests," but `BusinessAnalysis` itself never carried a business name either (M6's `BusinessAnalysisOutput` has no such field — see D-062's note that Contact Information required a separate `Business` input for M8.3).
**Decision:** `website-assembler.ts`'s `extractBusinessName()` reads it back out of `ContentManifest.structuredData`'s `Organization`/`LocalBusiness` entry — `data.name.value` — which M8.3's `seo-binder.ts` always binds from `Business.businessName` with full source traceability (D-066). `assembleWebsite()`'s public input type is therefore exactly the four manifests it uses; `BusinessAnalysis`/`Business` are never touched directly by this pure function (unlike `ContentBindingService`, `WebsiteAssemblyService` has no `BusinessModule` dependency at all). `GeneratedWebsite`'s Prisma model still records `businessAnalysisId` for full five-artifact FK provenance (D-073), matching every other M8.x model's discipline even though the generator function itself only reads four of the five.

### D-072: A dedicated `GeneratedWebsite` model — not a repurposed pre-existing `Website`/`WebsitePage` scaffold

**Context:** `packages/db/prisma/schema.prisma` already contained `Website`/`WebsitePage`/`GenerationJob`/`Deployment` models from the original pre-M6 roadmap scaffolding (keyed directly off `Lead`, a generic `templateKey` string, a `contentBlocks: Json` CMS-block shape) — placeholders for the roadmap's eventual generation/deployment modules, authored before M6-M8's concrete phase-by-phase architecture existed.
**Decision:** A new `GeneratedWebsite` model, following the exact same pattern as `LayoutConfiguration`/`ComponentManifest`/`ContentManifest`: `configVersion` versioned per business (never overwritten, `@@unique([businessId, configVersion])`), FK'd to all five upstream artifacts (`businessAnalysisId`/`themeConfigurationId`/`layoutConfigurationId`/`componentManifestId`/`contentManifestId`, `onDelete: Cascade` on each) for full provenance, `files: Json` holding the entire generated project as a flat `{path, content}[]` array — same "no object storage exists anywhere in this stack" reasoning as every other M8.x Json blob. The pre-existing `Website`/`WebsitePage`/`Deployment` scaffolding is untouched — it doesn't share this module's FK chain or Json-manifest shape, and repurposing it would have meant bending a differently-shaped placeholder to fit rather than following the established "one new model per phase" precedent (D-054/D-059/D-066). New, purely additive migration (`20260803000000_m8_4_website_assembly`). New `website:assemble` permission (same role set as `content:bind`/`component:generate`/`layout:generate`/`theme:select`) and `ContentManifestNotFoundException` (`CONTENT_MANIFEST_NOT_FOUND`, 404) for the hard dependency on a persisted M8.3 `ContentManifest`. `GET/POST /leads/:id/website` shipped this phase, consistent with every prior M6-M8.3 phase's own precedent.

### D-073: Validation-failure semantics carried forward unchanged from D-052/D-060/D-067

**Context:** Same question M8.1/M8.2/M8.3 already resolved, now for assembly-specific invariants (every `LayoutConfiguration.pageStructure` section has a matching `ComponentManifest` section component, every internal link target resolves to a real component, every required file is present in the assembled output).
**Decision:** Not re-opened as a fork this phase — `validateWebsiteAssembly()` throws a plain `Error` on any invariant violation, same internal-assertion semantics as D-052/D-060/D-067, for the same reason: every input manifest is already M8.1-M8.3-validated, and every rule here is a fixed structural check, so a failure means an assembler bug, not a legitimate business outcome.

### D-074: A real, unmocked `npm install && npm run build && npm run dev` smoke test — not just "the generator didn't throw"

**Context:** The phase brief's explicit requirement — "must be immediately runnable... without manual edits" — cannot actually be verified by unit/e2e tests alone: `vitest`/`jest` never invoke the TypeScript compiler or bundler against the _generated project's own_ source, so a type error inside `lib/site-data.ts`/`app/page.tsx` (as opposed to the assembler code that produces them) would pass every test in this repository while still failing a real `next build`. This is exactly what happened — the `SectionWrapperProps.children` bug (D-070) was invisible to all 87 assembly-related unit/e2e tests and was only caught by materializing a real fixture-driven project to disk and running Next.js's own toolchain against it.
**Decision:** Beyond the automated test suite, a real generated project (fixture business data, run through the actual, unmodified `assembleWebsite()`) was materialized to a scratch directory and put through the genuine npm lifecycle: `npm install` (131 packages, real network fetch, no errors), `npm run build` (`next build` — compiled, typechecked, linted, and statically generated all routes: `/`, `/robots.txt`, `/sitemap.xml`, `/manifest.webmanifest`, `/icon.svg` — zero errors after the one fix above), and `npm run dev` (booted, served `GET /` with a real `200`, page contained the `main-content` landmark and JSON-LD script tags). This is a one-time manual verification step, not a repeatable automated test (no CI job runs it) — documented here and in the review report as the substantiation for the "builds with zero manual edits" claim, not left as an unverified assertion.

## M9 — Website Preview

The founder's module brief specified the objective ("review, validate, and approve a generated website before deployment — never regenerate, never modify"), inputs (`GeneratedWebsite`/`BusinessAnalysis`/`ThemeConfiguration`), outputs (`WebsitePreview`/`PreviewReport`/`PublishReadinessReport`), device preview modes, the full four-category validation checklist (general/accessibility/SEO/performance), per-rule field requirements, an explicit "no Lighthouse, deterministic readiness checks only" instruction, and the architecture skeleton (Preview Engine + independent `SEOValidator`/`AccessibilityValidator`/`PerformanceValidator`/`PublishReadinessEngine`). An architecture was presented and approved, including one genuine open fork resolved via AskUserQuestion before any code was written (D-076). The founder then sent four explicit numbered Decisions refining that approved architecture — Preview Immutability, Cache Strategy, Validation Architecture, Permission — all incorporated below before implementation began.

### D-075: A dedicated `packages/website-preview` package with zero import of `packages/website-generator` — read-only enforced structurally, not just by convention

**Context:** The founder's Decision 1 ("The Preview Engine must never modify the GeneratedWebsite. It must be completely read-only.") needed to be more than a documented intention — M8's own packages have historically been where "this phase's job" gets enforced by what a package can even import (D-050's precedent: one dedicated package per module).
**Decision:** New `packages/website-preview` package, mirroring `packages/ai`/`packages/themes`/`packages/website-generator`'s standalone `tsc`/CommonJS structure. It depends on `@riznexia/shared-types` and `typescript` (for read-only AST _parsing_ via `ts.createSourceFile()` — the exact mirror of `website-generator`'s `ts.factory`-based AST _building_) but never on `@riznexia/website-generator` itself in production code (`@riznexia/website-generator` is a devDependency, used only by test fixtures to build a realistic `GeneratedWebsite` to validate against — the same convention `apps/api`'s own test specs already use). This makes "never regenerates" a package-boundary guarantee: there is no import path by which this module's business logic could call `generateLayout()`/`generateComponentManifest()`/`generateContentManifest()`/`assembleWebsite()` even by accident.

### D-076: Rendering-mechanism fork — structural/data preview only this phase, no live rendering server

**Context:** The brief's device-preview-mode requirement ("Desktop/Tablet/Mobile, instant switching") implies something a user can actually look at, but a true pixel-accurate render requires the full Next.js toolchain (compiled Tailwind CSS, `next/image`'s loader, Radix/Framer Motion client hydration) — none of which can run without either executing the generated project for real or a much larger custom SSR+CSS-compile pipeline, both sitting uneasily against "business logic must never depend on Next.js internals." Founder's resolved fork, offered three options via AskUserQuestion: (1) structural preview only — file manifest + summary + fixed viewport presets, no live process; (2) ephemeral build-and-serve — materialize files, run a real `next build`+`next start` per request, proxy the live server; (3) a constrained SSR snapshot — `ReactDOM.renderToString()` against a pre-compiled Tailwind stylesheet, partial fidelity, no client hydration. Founder chose option 1.
**Decision:** `generateWebsitePreview()` returns a file-path/byte-size manifest, a business/theme summary, and fixed desktop (1440px)/tablet (768px)/mobile (375px) viewport-width presets — no live process, no execution of any generated code, zero new infrastructure. Live visual rendering (an actual running instance a user can look at) is explicitly out of scope for this phase, flagged as a known limitation in the review report, not silently omitted — a separate future infrastructure decision, consistent with option 2/3's real complexity costs never being worth taking on without a dedicated design pass of their own.

### D-077: A `StructuralValidator` and a `ContentCompletenessValidator` beyond the three named in the brief — resolving overlap, then splitting further to satisfy Decision 3

**Context:** The brief's Architecture section names three validators (`SEOValidator`/`AccessibilityValidator`/`PerformanceValidator`) plus `PublishReadinessEngine`, but the separate "Validation Engine" checklist (missing pages/assets, broken routes/links/images, missing sitemap/robots.txt/manifest.json) doesn't map cleanly onto any of the three — it's about file/reference _existence_, not SEO metadata _value_ completeness, accessibility, or speed. Separately, the founder's readiness-report requirement lists both "Content Completeness" and "Structural Integrity" as distinct named scores, while Decision 3 requires `PublishReadinessEngine` to _only_ aggregate, never validate — meaning both of those scores need to come from real, independently-computed rules, not from `PublishReadinessEngine` inspecting `GeneratedWebsite.files` itself.
**Decision:** Two additional validators, each still following Decision 3 (independent, no cross-calls): `structuralValidator` (`category: 'structural'`) owns file/route/link/image _existence_ checks — mapped 1:1 to the readiness report's "Structural Integrity" score. `contentCompletenessValidator` (`category: 'content'`) owns the check that every content field M8.3's binder actually bound into `lib/site-data.ts` is non-empty — mapped 1:1 to "Content Completeness". `RULE_CATEGORIES` grew from a hypothetical 3 to 5 (`structural`, `content`, `seo`, `accessibility`, `performance`) to carry this split; still a closed enum (same "deliberate schema change, not a silently-accepted new string" discipline as `SupportedComponentType`/D-055) — a future validator with a genuinely new category (Security/Legal/Cookie/Brand/Broken-Link, the founder's own Future Compatibility examples) adds one new enum value when it's actually built, not pre-declared speculatively now (D-051's "only literal values the algorithm actually produces" discipline).

### D-078: Every M9 endpoint is a single GET that computes-and-caches — no POST anywhere in this module

**Context:** Every M6-M8.4 phase shipped a POST (generate + persist) alongside a GET (return latest-or-null), because generation had a real, explicit cost worth gating behind an intentional action (an AI call, or at minimum a deliberate "run this pipeline stage"). The founder's brief for M9 lists only three GET endpoints — no POST — and validation here is pure, synchronous, in-memory static analysis with no AI call and no third-party API, so there's no comparable cost to gate.
**Decision:** `GET /leads/:id/preview`, `/preview/validation`, `/preview/readiness` each independently compute fresh and auto-persist a new versioned row only when the cached row's `generatedWebsiteVersion` no longer matches the current `GeneratedWebsite.configVersion` — otherwise the cached row is returned (founder's Decision 2, "regenerate only when the GeneratedWebsite version changes"). This is the identical cache-then-generate logic every M6-M8 POST already used, just triggered by GET instead, since there's no cost-based reason here to require an explicit generate step. All three GETs are gated by the new `website:preview` permission rather than `leads:read` (unlike every M6-M8 GET) — because unlike those GETs (a trivial DB read), an M9 GET performs real computation (parsing/validating the generated website), so viewing it is itself the privileged action, matching the founder's own "future-proof for client approval / internal QA / review workflow" framing of the permission.

### D-079: "All reports must be generated independently" — no FK between `PreviewReport` and `PublishReadinessReport`, readiness never reads a persisted validation report

**Context:** Founder's Decision 1 explicitly states "All reports must be generated independently," and Decision 3 states `PublishReadinessEngine` "must never perform validation itself." Taken together, these rule out the most obvious design (readiness reads the latest persisted `PreviewReport` row and aggregates its `rules`) — that would make `/readiness` depend on `/validation` having been called first, and would blur the two into a single pipeline stage rather than two independent artifacts.
**Decision:** `WebsitePreviewService.getReadinessReport()` independently calls the exact same `runAllValidators()` entry point `getValidationReport()` calls, in-memory, and never queries the `PreviewReport` table at all. `PublishReadinessReport`'s Prisma model has no FK to `PreviewReport` — only to `businessId`/`generatedWebsiteId`, same as `WebsitePreview` and `PreviewReport` themselves. All three models are siblings, not a chain; `PublishReadinessEngine.aggregateReadiness()` itself only ever receives an already-computed `ValidationRuleResult[]` and performs pure arithmetic over it — verified by an apps/api test asserting `/readiness` never triggers a `PreviewReport` query.

### D-080: Every readiness score explains itself via a `ScoreBreakdown` — equal-weight-per-rule scoring, not a severity-weighted formula

**Context:** Founder's explicit requirement: "Each score must explain why points were deducted." A bare 0-100 integer can't satisfy that on its own.
**Decision:** `ScoreBreakdown = {score, maxScore: 100, deductions: ScoreDeduction[]}`, where each `deductions[]` entry names the exact rule (`ruleId`/`ruleName`), how many points it cost, and why (`reason` — the rule's own `message`). Within a category, every rule is worth an equal share of 100 points (`100 / ruleCount`); a `warning` costs half its share, an `error` costs all of it, a `pass` costs nothing — deliberately the simplest possible formula that's still fully auditable, rather than a `severity`-weighted scheme that would make "why did this drop 12 points" harder to explain in one sentence. A category with zero registered rules scores 100 (nothing was found wrong, since nothing was checked) — documented as a known limitation, not a silently favorable default. `overallPublishScore` is a fixed-weight average of the five named category scores (SEO 20% / Accessibility 25% / Performance 15% / Content Completeness 20% / Structural Integrity 20%), with its own `deductions[]` naming which category's shortfall cost how much of the overall score.

### D-081: Validator registry as the sole Future Compatibility extension point — verified by a real bug the design itself caught

**Context:** Founder's explicit Future Compatibility requirement, with named examples (Security/Legal/Cookie/Brand/Broken-Link Validator) a later module might add.
**Decision:** `WebsiteValidator` (`{category, validatorVersion, validate(input)}`) is the only contract a validator must implement; `VALIDATOR_REGISTRY: WebsiteValidator[]` in `validator-registry.ts` is the only place that knows about all five current validators, and `runAllValidators()` just flattens their independent output. A future validator is one new file plus one array entry — verified directly by a test that constructs a synthetic sixth validator, adds it to a copy of the registry, and confirms both that its output appears and that every existing validator's own output is byte-identical to before.
**A real bug this design caught, not merely a hypothetical:** the first version of `structuralValidator`'s broken-internal-link check parsed `app/page.tsx`'s literal JSX `href`/`id` attributes via `ts.isStringLiteral`. Against a real assembled website (not a hand-authored fixture), this was silently vacuous — M8.4's actual templates spread `{...props}` (which carries `id`) and build `href` from a runtime template literal (`` `#${targetComponentId}` ``, an unevaluable dynamic expression to a static parser), so no literal `href`/`id` JSX attributes exist anywhere in a real generated `page.tsx`. The check always found zero hrefs to inspect and always reported "pass," regardless of whether a link was actually broken. Caught by testing against `packages/website-preview`'s own real-fixture assembled output (built via the actual `assembleWebsite()`, not a stub) rather than assuming the check was correct from reading the generator's source — fixed by reading `id`/`targetComponentId` directly out of `lib/site-data.ts`'s already-resolved props instead, the one place those real values actually live.

## M10 — Sales CRM

The founder's module brief specified the objective ("manage the complete lifecycle of selling AI-generated websites... NOT a generic CRM"), the discover→demo→deploy workflow, core features (Opportunity Pipeline, Sales Stages, Follow-ups, Tasks, Reminders, Activity Timeline, Notes, Proposal Tracking, Website Status, Lead Assignment), a default 10-stage pipeline, activity types, task/proposal field lists, dashboard reporting requirements, four dedicated permissions, five named "separate modules" (Pipeline/Task/Activity/Proposal/Reporting Engines), Future Compatibility attachment points, and explicit constraints (no email/WhatsApp sending, no deployment, no analytics, no AI). An architecture was presented and approved with twelve founder Decisions refining it before implementation — recorded individually below (D-083 onward), after the scope question every other decision depended on.

### D-082: `docs/21-implementation-roadmap.md`'s M10 entry is superseded as an implementation spec — the roadmap file itself is untouched

**Context:** `docs/21`'s actual M10 entry describes a different module than the founder's live brief: an AI Sales Agent (pitch drafting), AI Proposal Generator, CRM Assistant agent (lead summarization), a daily stale-lead sweep, and a per-rep AI quota — "merges the old 'Sales & Outreach' and 'CRM Assistant' modules." The founder's brief instead specifies Pipeline/Stage/Task/Activity/Proposal-**tracking**/Reporting, explicitly excluding AI ("Do NOT implement: ...AI chatbots"), with an "AI Sales Assistant" listed only under Future Compatibility (reserved, not built). These aren't elaboration-of-a-terse-heading (the pattern every prior module's roadmap-vs-brief relationship followed) — they're two different feature sets sharing a module number. Flagged directly rather than silently resolved, given how emphatically "the roadmap is frozen" has been stated every phase; founder's explicit Decision 1: the live, approved architecture is the implementation source of truth, and `docs/21`'s M10 entry is not to be treated as governing during implementation.
**Decision:** M10 is built exactly as specified in the founder's brief and the architecture approved in this conversation — `SalesStage`/`LostReason`/`LeadCRM`/`CrmTask`/`SalesProposal`/`CrmSettings`, five engines, four permissions, zero AI. `docs/21-implementation-roadmap.md` itself is **not edited** — its M10 entry becomes stale relative to what's actually built, a documented, deliberate gap (this entry), not a silent contradiction. The roadmap's AI-Sales-Agent/Proposal-Generator/CRM-Assistant/stale-lead-sweep/per-rep-quota content remains available as a candidate for a future module if the founder revisits it; nothing here builds toward or against it.

### D-083: `LeadCRM` as a dedicated bounded-context entity — `Lead` (M2/M4) is never extended with CRM fields

**Context:** The obvious shortcut — add `stage`/`dealValue`/`lostReason`/`owner`/`nextFollowUpAt` columns directly to `Lead` — would blur two already-established, independently-owned concepts: `Lead` is Module M2/M4's discovery/business-pursuit record (`pipelineStage`, `assignedToId`, tags, notes), while everything the founder's brief calls "the sales pipeline" is CRM-specific state that a non-CRM consumer of `Lead` (Discovery, Business Analysis, Website Generator) should never need to know exists. Founder's explicit Decision 3: "Do not extend the Lead entity with CRM-specific business fields. Instead introduce a dedicated LeadCRM entity."
**Decision:** New `LeadCRM` model, one-to-one with `Lead` via a unique `leadId` FK (`onDelete: Cascade`), owning `stageId`/`dealValueUsd`/`lostReasonId`/`ownerId`/`nextFollowUpAt`/`lastActivityAt`. Rows are created **lazily** — `LeadCrmService.getOrCreate()` — the first time any CRM engine touches a given lead, rather than `LeadsService.create()` inserting one up front; `LeadsModule` never imports anything from `crm/`, keeping the dependency direction strictly one-way (`crm/` → `leads/`, never the reverse). `Lead.assignedToId` (M4, "who's pursuing this business") and `LeadCRM.ownerId` (M10, "who owns this deal") are deliberately two independent fields that coexist without conflict or synchronization — simpler than the originally-proposed permission-layering on `PATCH /leads/:id`, which this design makes unnecessary since that endpoint is untouched.

### D-084: `SalesStage` and `LostReason` as real, seeded, archivable tables — never a hardcoded Postgres enum

**Context:** Every other closed taxonomy in this codebase (component types, activity types, pipeline stages) is a Prisma enum. A sales pipeline's stages and lost-reasons are different in kind: the founder needs to rename/reorder/add them without a schema migration, and a stage or reason already referenced by historical deals can never be safely removed outright. Founder's explicit Decisions 2, 10, and 11: "SalesStage will remain a configurable database table," "Sales stages should support archive instead of hard delete," "Lost Reasons should be configurable... use a LostReason table instead of a fixed enum."
**Decision:** `SalesStage` (`id`/`key`/`name`/`order`/`isWon`/`isLost`/`archivedAt`) and `LostReason` (`id`/`key`/`label`/`order`/`archivedAt`) are both plain tables, each seeded with its defaults by its own migration's `INSERT` statements (10 stages — NEW through LOST, `order` 1-10 — and 7 lost-reasons), not application code. "Delete" is a PATCH that sets `archivedAt = now()`; default list queries filter `archivedAt: null` with an `includeArchived` query param for admin views; an archived row's `id` remains a fully valid FK target, so a `LeadCRM`/`CrmSettings.defaultStageId` row referencing an archived stage keeps working exactly as before — only new assignments to it are discouraged by the UI, never blocked by the schema. (An initially-drafted `SalesStageInUseException`, meant to block archiving a referenced stage, was removed before ever being wired up — it directly contradicted this "archiving never breaks an existing reference" design.)

### D-085: `SalesProposal` rows are immutable per-version — "editing" always inserts a new row, never updates `content`

**Context:** A generic "edit this proposal" PATCH would let a rep silently rewrite what was actually sent to a client after the fact, making "what did version 2 actually say" unanswerable from the audit trail. Founder's explicit Decision 7: "Sales Proposals must support immutable version history. Never overwrite proposal versions."
**Decision:** `SalesProposal.content` and `.version` are set once at `create()` and never touched again; `version` is server-computed (`max(existing versions for this lead) + 1`, never client-supplied) and constrained by `@@unique([leadId, version])`. Only lifecycle/tracking fields (`status`, `sentAt`/`viewedAt`/`acceptedAt`/`rejectedAt`) mutate in place, via a separate `PATCH /leads/:id/proposals/:proposalId` whose request schema (`updateSalesProposalStatusSchema`) structurally has no `content` key at all — a client that appends `content` to that PATCH body has it silently stripped by Zod's default (non-strict) parsing before it ever reaches the service, verified directly by an e2e test asserting the Prisma `update()` call Zod's output produces has no `content` property. `content` itself is nullable (renamed from the model's original required `draftContent`) since this module tracks proposals, it doesn't draft them — a rep may log "sent v2" purely for tracking with the real document living elsewhere. `status: 'sent_manually'` is the one transition that also writes a `PROPOSAL_SENT` `LeadActivity` entry and touches `LeadCRM.lastActivityAt`, matching the founder's Activities-to-track list; `viewed`/`accepted`/`rejected` only update their own timestamp.

### D-086: `LeadActivityType` extended and reused for the CRM timeline — no parallel activity system

**Context:** M4 already built a rep-facing lead timeline (`LeadActivity`/`LeadActivityService`). Founder's explicit Decision 5: "Reuse LeadActivity. Do not create another activity system." — ruling out a CRM-specific activity table even though the CRM's event types (calls, meetings, proposal-sent) are conceptually different from M4's (stage changes, notes).
**Decision:** `LeadActivityType` (Prisma enum) gains seven values — `CALL`/`EMAIL`/`MEETING`/`WHATSAPP`/`WEBSITE_GENERATED`/`PREVIEW_SENT`/`PROPOSAL_SENT` — alongside its original seven, and `LeadsModule` now exports `LeadActivityService` (previously internal) specifically so `crm/pipeline`, `crm/activities`, and `crm/proposals` can inject and reuse it. The Activity Engine's own original contribution is narrow: `POST /leads/:id/activity`, restricted by its request schema to the four types a rep can genuinely originate by hand (call/email/meeting/whatsapp) — `note_added` already has its own endpoint (M4's `POST /leads/:id/notes`), and `website_generated`/`preview_sent`/`proposal_sent` are system-emitted by their owning engines, never through this manual path. This same engine also owns keeping `LeadCRM.lastActivityAt` current, touching it inside the same transaction as every activity write (manual logging, and the Proposal Engine's `sent_manually` transition) so the denormalized pointer never drifts from the timeline it summarizes.

### D-087: `CrmSettings` as a genuine singleton — seeded once by the migration, fetched by `findFirst()`, never `create()`d again

**Context:** Founder's explicit Decision 12: "Create CRM Settings for future extensibility. Include: Default Pipeline, Currency, Timezone, Business Hours, Default Reminder." A single-organization system (same "no multi-org support" scope as `TeamMember`) needs exactly one settings row, not a keyed table.
**Decision:** `CrmSettings` (`defaultStageId`/`currency`/`timezone`/`businessHours`/`defaultReminderMinutesBeforeDue`) is seeded with exactly one row by its own migration (`defaultStageId` pointed at the seeded `new` stage); `CrmSettingsService` only ever reads it via `prisma.crmSettings.findFirst()` and updates it by the id that query returns — it never calls `.create()`. A missing row is an internal invariant violation (the migration failed to run, not a legitimate empty-settings state a caller could hit), so `CrmSettingsService.get()` throws a plain `Error`, not a domain `AppException` — same internal-assertion-vs-domain-exception split established since D-052. This is a soft guarantee (nothing in the schema itself prevents a second row from being inserted by a different code path), acceptable because this service is the only writer this table will ever have.

### D-088: `WebsiteGenerationStatus` — computed fresh from M6-M9's own tables on every request, nothing new stored

**Context:** Founder's explicit Decision 8: "Website Status remains computed. Never duplicate M6-M9 data." The founder's Core Features list names "Website Status" as something the CRM must show, but M6 (`BusinessAnalysis`)-M9 (`WebsitePreview`/`PublishReadinessReport`) already persist every fact needed to answer "how far along is this lead's website" — duplicating that into a new stored column would immediately risk drifting out of sync with the tables that are the actual source of truth.
**Decision:** `WebsiteStatusService.getForLead()` runs eight parallel Prisma existence-checks (`BusinessAnalysis` COMPLETED → `ThemeConfiguration` → `LayoutConfiguration` → `ComponentManifest` → `ContentManifest` → latest `GeneratedWebsite` → `WebsitePreview` → latest `PublishReadinessReport`) and folds them into a `WebsiteGenerationStage` via a sequential loop that stops advancing at the first missing milestone — even if a later one somehow exists (a defensive stance against inconsistent data, directly tested). No new column, nothing to keep in sync. The type is named `WebsiteGenerationStatus`/`websiteGenerationStatusSchema` — deliberately not `WebsiteStatus` — to avoid colliding with `lead.ts`'s pre-existing, unrelated `Business.websiteStatus`/`WebsiteStatus` (M1/M5, "does this business currently have a live website"). `GET /leads/:id/website-status` is gated on `leads:read`, not `crm:view` — it's a read-only view over existing M6-M9 data, not new CRM data, matching the same reasoning as this decision's title.

### D-089: Reporting Engine — read-only aggregation over Pipeline-computed facts, in a cache-ready pure-function shape

**Context:** Founder's explicit Decision 6: "Reporting Engine must remain read-only. Business calculations belong inside Pipeline Engine. Reporting only aggregates already-computed data." And Decision 9: "Dashboard statistics should support future caching. Design the architecture accordingly." Together these rule out `ReportingService` independently re-deciding "what does this mean" (e.g., re-implementing "is this stage won" from scratch) and rule out a design that couldn't sit behind a cache without a redesign.
**Decision:** `ReportingService.getDashboardStats()` reads `LeadCRM` joined with `SalesStage`/`LostReason`/`TeamMember` directly via Prisma (not through `PipelineService`'s per-entity methods, which have no bulk-list surface and would turn an org-wide rollup into an N+1) — but every "what does this mean" judgment it makes is a plain read of a field the Pipeline Engine already computed and persisted (`SalesStage.isWon`/`.isLost`, `LostReason.label`, `TeamMember.name`), never a re-derivation of pipeline business rules. `DashboardStats` is a pure function of `(dateRange, filters)`: `generatedAt`/`filters` plus `pipelineValueByStage`/`totalPipelineValueUsd`/`conversionRatePercent`/`winRatePercent`/`averageSalesCycleDays`/`lostReasonsBreakdown`/`salesPerformanceByRep`, fully JSON-serializable with no live cursors — the shape a future cache keyed on those same inputs could sit in front of without a redesign; no caching is actually wired this phase. `averageSalesCycleDays` is approximated from the most recent `STAGE_CHANGED` activity whose `detail.to` matches a lead's current won stage (falling back to `LeadCRM.updatedAt` when no such activity exists, e.g. seeded data), documented as an approximation since no dedicated `wonAt` timestamp is stored anywhere. `conversionRatePercent` (won ÷ all leads ever in the CRM pipeline) and `winRatePercent` (won ÷ (won + lost), i.e. of decided opportunities) are deliberately different metrics, matching the founder's dashboard list naming both separately. `GET /crm/dashboard` is gated on the dedicated `crm:report` permission, not `crm:view` — seeing individual leads doesn't imply seeing org-wide sales metrics.

### D-090: Four dedicated CRM permissions, none reused from an earlier module

**Context:** Founder's brief named exactly four permissions to create: `crm:view`, `crm:manage`, `crm:assign`, `crm:report`. Every module since M3 has followed a strict `resource:verb` naming convention with no permission ever reused across modules.
**Decision:** All four added to `PERMISSIONS`. `admin`/`sales_manager` hold all four. `sales_executive` holds only `crm:view`/`crm:manage` — a rep can see and work their own leads' CRM state but cannot reassign deal ownership (`crm:assign`) or see org-wide sales metrics (`crm:report`), matching the same restriction pattern already applied to `cost:view`. `developer`/`viewer` get none of the four. Every mutation across all five engines is gated by the specific permission it needs, never a blanket `crm:manage` fallback: stage transitions and the generic `LeadCRM` PATCH use `crm:manage`; owner assignment uses `crm:assign`; the dashboard uses `crm:report`; every read uses `crm:view` (except `GET /leads/:id/website-status`, gated `leads:read` per D-088).

### D-091: `CrmTask` extended with `estimatedDurationMinutes`/`actualDurationMinutes`/`completedById` — founder's Decision 4

**Context:** The brief's base Task field list (Due Date/Priority/Status/Assigned User/Reminder) didn't originally include duration tracking or a record of who completed a task. Founder's explicit Decision 4: "Extend CrmTask with: estimatedDuration, actualDuration, completedBy."
**Decision:** `CrmTask` carries `estimatedDurationMinutes`/`actualDurationMinutes` (both plain optional integers, directly settable via PATCH, no derived relationship enforced between them) and `completedById`/`completedAt`, both stamped automatically — not client-supplied — by `CrmTaskService.update()` the moment `status` transitions to `completed`. This stamping is idempotent: re-PATCHing an already-completed task with `status: 'completed'` again leaves the original `completedAt`/`completedById` untouched (preserving the true completion record), while explicitly moving a task's status _away_ from `completed` (reopening it) clears both fields. "Follow-ups" and "Reminders" (the founder's Core Features list) are deliberately not separate entities — a follow-up is just a `CrmTask` with a descriptive title, and `reminderAt` is a stored scheduling field with no delivery mechanism this module (no notification channel exists yet; email/WhatsApp sending are explicitly out of scope per the founder's Constraints).

## M11 — Deployment

The founder's module brief specified the objective (publish generated websites to production; must not generate or modify them), the inputs (`GeneratedWebsite` M8, `PublishReadinessReport` M9), a provider-agnostic Deployment Provider abstraction, the full lifecycle (Requested → Build Validation → Started → Completed → Health Check → Production Ready, with a Failed/Retry branch), immutable deployment history, rollback-as-a-new-deployment, domain/SSL metadata management with no DNS automation, deterministic health checks, four dedicated permissions, five named independent engines (Deployment Engine, Deployment Provider, Health Check Engine, Rollback Engine, Domain Engine), and explicit Future Compatibility reservations (GitHub/GitLab integration, CI/CD, preview/blue-green/canary/zero-downtime deployments). An architecture was presented and approved with ten founder Decisions refining it before implementation, recorded individually below (D-093 onward) after the naming-collision question every other decision depended on.

### D-092: `WebsiteDeployment` — a new model, not a repurposing of the pre-existing `Deployment`/`Website` scaffold

**Context:** `packages/db/prisma/schema.prisma` already has a `Website`/`WebsitePage`/`GenerationJob`/`Deployment` scaffold from Module M2, unused by any module built since (M8.4's own review already flagged it as untouched, not repurposed). That legacy `Deployment` model FKs to the legacy `Website` model, not `GeneratedWebsite` (M8) — which the founder's live M11 brief names as the actual input. Unlike M10's roadmap conflict, this isn't a scope disagreement requiring a founder decision (the brief is unambiguous about what M11 deploys); it's a mechanical naming collision, resolved the same way D-088 resolved `WebsiteGenerationStatus` colliding with the pre-existing `WebsiteStatus`.
**Decision:** The new deployment record is named `WebsiteDeployment`, FK'd to `GeneratedWebsite` directly. The legacy `Website`/`WebsitePage`/`GenerationJob`/`Deployment`/`BrandKit` scaffold is left completely untouched — not migrated, not deleted, not referenced by any M11 code. `docs/21-implementation-roadmap.md`'s M11 entry (GitHub adapter + Vercel adapter + `/websites/{id}/deployments`, tied to the legacy `Website` model) is superseded as an implementation spec the same way M10's was (D-082) — the founder's live, approved architecture governs; the roadmap file itself is **not edited**, per founder's explicit Decision 1.

### D-093: `DeploymentProvider` abstraction — `VercelProvider` fully implemented, four reserved provider classes, business logic never imports a concrete provider

**Context:** Founder's explicit Decision 2: "Implement the Deployment Provider abstraction. The business layer must never depend on a specific provider... Fully implement the Vercel provider. Create provider interfaces for: Cloudflare Pages, Netlify, AWS Amplify, Azure Static Web Apps. Future providers must be pluggable without changing business logic." The one existing precedent for this exact shape is `LocationProvider` (M5, D-033) — a single DI-bound interface, one concrete implementation, business logic depending only on the interface.
**Decision:** `DeploymentProvider` (`deploy()`/`getStatus()`/`isConfigured()`, optional `attachDomain()`) is the structural mirror of `LocationProvider`, injected everywhere behind the `DEPLOYMENT_PROVIDER` token via `ProviderModule` (the sole place deciding which concrete class is active — a `useClass` swap, no consumer changes). No `rollback()` method: a rollback is always a fresh `deploy()` call against a historical `GeneratedWebsite` snapshot (D-094), which is what makes rollback portable across every future provider without each needing a native rollback API. `VercelProvider` is fully implemented — a real `VercelAdapter` calling Vercel's REST API (deployments + project-domains endpoints), gated behind `VERCEL_API_TOKEN`/`VERCEL_TEAM_ID`, its tests mocking `fetch` itself rather than hitting the network (same convention as `PlacesAdapter`'s own tests, M5). `CloudflarePagesProvider`/`NetlifyProvider`/`AwsAmplifyProvider`/`AzureStaticWebAppsProvider` each genuinely implement `DeploymentProvider` (provably a one-line `useClass` swap away from being active, proving the abstraction actually holds) but their methods throw "reserved for a future module" until a real adapter backs them — the same reserved-not-built stance as every other closed-enum extension point in this codebase. `self_hosted` is a sixth reserved `DeploymentProviderName` enum value with no stub class, since the founder's Decision 2 named only the first four.

### D-094: Deployments are immutable — rollback and retry always create a new `WebsiteDeployment` row, never mutate history

**Context:** Founder's explicit Decision 3: "Deployments are immutable. Every deployment creates a new deployment record. Rollback is also a deployment. Never overwrite deployment history."
**Decision:** `WebsiteDeployment.status` (`REQUESTED → VALIDATING → IN_PROGRESS → COMPLETED`, or `→ FAILED`) has no `rolled_back` value — a rollback never mutates a superseded row's status; that fact lives entirely on the _new_ row's `rollbackFromDeploymentId` (self-FK). Retry works identically via `retryOfDeploymentId`. Both `RollbackEngineService.rollbackTo()` and `DeploymentEngineService.retryDeployment()` funnel through the exact same orchestration method, `deployGeneratedWebsite()` — rollback resolves its target's historical `GeneratedWebsite` snapshot (rejecting with `InvalidRollbackTargetException` unless the target is `COMPLETED` + `healthStatus: HEALTHY`), retry re-reads the failed row's own `generatedWebsiteId` (rejecting with `DeploymentNotRetryableException` unless the target is `FAILED`) — neither duplicates the deploy pipeline itself. A provider-call failure during that pipeline is caught and recorded as a `FAILED` row (with `errorMessage`), not re-thrown as an HTTP error — "Deployment Failed → Retry Available" is a normal API response (`201`), not an exceptional one, verified by an e2e test asserting the failed deployment is still returned successfully.

### D-095: Health Check Engine — deterministic, provider-independent, `healthStatus` orthogonal to `status`

**Context:** Founder's explicit Decision 5: "Health checks must be independent of deployment providers. Health Check Engine must validate: Deployment status, Website availability, SSL status, Domain status. Do not implement provider-specific health logic inside business services."
**Decision:** `HealthCheckEngineService` never calls `DeploymentProvider` — its "Website Availability" check is a plain HTTP `GET` against the deployment's own `liveUrl`, the same request any browser would make, independent of which provider served it. All four founder-named checks run every time (`deployment_status` reads `WebsiteDeployment.status`; `website_reachable` is the plain HTTP call; `domain_status`/`ssl_status` read the `Domain` row's `verificationStatus`/`sslStatus`, passing trivially when no domain is registered yet), and the result is recorded as a `DeploymentHealthCheck` row (one per check _run_, since a deployment is checked repeatedly — automatically right after every completion, and on demand via `POST .../health-check`) plus a denormalized `WebsiteDeployment.healthStatus` update, the same "maintained by the owning engine" pattern as `LeadCRM.lastActivityAt` (D-086). `healthStatus` (`UNKNOWN`/`HEALTHY`/`UNHEALTHY`) is a field orthogonal to `status`, not folded into one combined enum — "Production Ready" is `status = COMPLETED && healthStatus = HEALTHY`, not its own value. Deterministic given a fixed HTTP response: `runCheck()` never throws — a network blip hitting a freshly-deployed URL can only ever produce an `UNHEALTHY` result, never flip an already-`COMPLETED` deployment to `FAILED` (verified directly by a test that rejects the fetch and asserts the method still resolves).

### D-096: Domain Engine — `Domain` as a mutable pointer, metadata and provider-integration status only, no DNS/SSL automation

**Context:** Founder's explicit Decision 6: "The Domain Engine manages metadata only. Do NOT implement: DNS automation, SSL certificate issuance, Registrar APIs. Reserve architecture for future implementation."
**Decision:** Unlike `WebsiteDeployment`, `Domain` is a long-lived, mutable-in-place row — a hostname persists across many deployments going live under it — closer in kind to `LeadCRM` (D-083) than to any immutable-version table (D-085, D-094). `DomainEngineService.attemptVerification()` calls `DeploymentProvider.attachDomain()` (optional on the interface) as best-effort: if the active provider doesn't implement it, or the call itself throws, the `Domain` row still exists with `verificationStatus`/`sslStatus` staying `PENDING` — nothing here is a hard requirement for domain registration to succeed, matching the founder's "reserve architecture for future implementation" framing. No DNS record is ever written by this module — `attachDomain()` only asks the provider (Vercel) what verification record a human should add at their registrar, storing that response as opaque `verificationRecord` metadata. `sslStatus` tracks alongside `verificationStatus` (both flip together on verification) rather than a separate "check SSL" provider call, since Vercel auto-provisions SSL the moment a domain verifies — deliberately not building a redundant polling path Decision 6 already rules out.

### D-097: Build Validation reads M9's already-computed `PreviewReport`, never re-runs validators

**Context:** Founder's explicit Decision 4: "Deployment must not start unless: GeneratedWebsite exists, PublishReadinessReport passes validation, Required assets exist, Build configuration exists. Fail fast if validation fails."
**Decision:** `DeploymentEngineService.assertPublishReady()` calls `WebsitePreviewService.getValidationReport()` (now exported from `WebsitePreviewModule` for this purpose) and rejects with `DeploymentValidationFailedException` (422, carrying which rules failed) if any rule is `error`-severity — the same "read already-computed facts, never re-derive" boundary the Reporting Engine holds toward the Pipeline Engine (D-089), extended to Deployment's relationship with M9. "Required assets exist" is deliberately not a separate check: the Structural Integrity validator's own rules already verify exactly that, so a second check would just duplicate M9's logic. "Build configuration exists" is interpreted as _the target provider has credentials configured_ — `DeploymentProvider.isConfigured()`, checked first and cheapest, throwing `DeploymentProviderUnavailableException` (503) before any validation report is even fetched.

### D-098: Four dedicated deployment permissions, `deployment:view` reaching every role including read-only ones

**Context:** Founder's brief named exactly four permissions to create: `deployment:view`, `deployment:create`, `deployment:rollback`, `deployment:manage`, with the explicit instruction "Do not reuse previous permissions."
**Decision:** All four added to `PERMISSIONS`. `admin`/`sales_manager` hold all four. `sales_executive` holds `deployment:view`/`deployment:create` — deploying is the natural last step of the pipeline they already own end-to-end (`theme:select` through `website:preview`) — but not `deployment:rollback`/`deployment:manage`, matching the same manager-and-up split as `crm:assign`/`crm:report` (D-090). Unlike the CRM permissions, `deployment:view` is also granted to `developer` and `viewer` — a deployment failure is exactly the kind of operational fact a developer needs visibility into without being handed the ability to trigger, roll back, or reconfigure anything.

### D-099: Every `WebsiteDeployment` row carries the founder's explicit field list, including two self-referencing FKs

**Context:** Founder's explicit Decision 8: "Every deployment must store: deploymentVersion, deploymentHash, deploymentEngineVersion, provider, providerVersion, createdAt, completedAt, executionDuration."
**Decision:** All eight fields are stored exactly as named, plus the fields the lifecycle section of the brief separately required (`status`, `healthStatus`, `liveUrl`, `errorMessage`, `buildStartedAt`/`buildCompletedAt`, `environment`, `commitHash`, `providerDeploymentId`, `createdById`) and the two self-FKs D-094 introduced (`rollbackFromDeploymentId`/`retryOfDeploymentId`). `deploymentVersion` is server-computed (`max` existing for the business `+ 1`), never client-supplied, constrained by `@@unique([businessId, deploymentVersion])` — the same immutable-sequence pattern as `SalesProposal.version` (D-085). `deploymentHash` is a sha256 over the deployed file set, sorted by path first so file ordering can never change the hash for identical content (same pattern as `business-fingerprint.ts`). `deploymentEngineVersion` versions this module's own orchestration logic (`DEPLOYMENT_ENGINE_VERSION`, apps/api-local constant, same convention as `THEME_ENGINE_VERSION`); `providerVersion` is the active `DeploymentProvider`'s own version, read from the provider instance itself rather than hardcoded in the engine.

### D-100: Structured logging for every lifecycle event the founder named

**Context:** Founder's explicit Decision 9: "Log every deployment lifecycle event: Deployment Requested, Deployment Started, Deployment Completed, Deployment Failed, Rollback Requested, Rollback Completed, Health Check Completed."
**Decision:** Each line is logged by the engine that owns the transition it describes, not centralized in one place: `DeploymentEngineService` logs Requested/Started/Completed/Failed (via NestJS `Logger`, matching every other engine's logging convention in this codebase); `RollbackEngineService` logs Rollback Requested always, and Rollback Completed only when the resulting deployment's own status came back `completed` (a rollback whose redeploy attempt itself fails already gets its own "Deployment Failed" line from `DeploymentEngineService` — no separate "Rollback Failed" line exists, since the founder's list didn't name one); `HealthCheckEngineService` logs Health Check Completed on every run, success or failure, since a check "completing" and a check "passing" are different facts.

### D-101: Future Compatibility reservations — named, not built

**Context:** Founder's explicit Decision 10: "Reserve architecture for: GitHub Integration, GitLab Integration, CI/CD Pipelines, Preview Deployments, Blue/Green Deployments, Canary Deployments, Zero Downtime Deployments. Do not implement them in this module."
**Decision:** Two concrete reservations exist in the schema/types today, deliberately unused by any code path: `DeploymentEnvironment.PREVIEW` (only `production` is creatable via `POST /leads/:id/deployments` this phase — the `environment` field is entirely absent from `createWebsiteDeploymentSchema`, server-set, never client-supplied) reserves the slot Preview Deployments would occupy; `commitHash` (nullable, "if applicable") reserves the slot a future GitHub/GitLab integration would populate from a real commit, without this module ever calling a git provider itself. Blue/Green, Canary, and Zero-Downtime deployments have no reserved field yet — they're strategy-level concerns about _how_ a deploy transitions traffic, which would layer on top of the existing `DeploymentProvider.deploy()` contract rather than requiring a schema change today, so nothing was added speculatively for them (same discipline as leaving genuinely-unneeded reservations out entirely, per this codebase's general aversion to speculative fields).

### D-102: "DeploymentHistory" and "DeploymentStatus" are query views, not separate tables

**Context:** The founder's Outputs section named three things — "Deployment, DeploymentHistory, DeploymentStatus" — phrased as if each might be its own artifact, the same shape M9's "three independent artifacts" language had (D-075+). Unlike M9's case, only one of the three actually needed its own persisted model.
**Decision:** "Deployment" is the persisted `WebsiteDeployment` table (D-092). "DeploymentHistory" is not a separate table — it's `GET /leads/:id/deployments`, a query over the same immutable `WebsiteDeployment` rows ordered newest-version-first; a separate history table would just be a copy that could drift from the source of truth, the exact antipattern D-088 already avoided for `WebsiteGenerationStatus`. "DeploymentStatus" is also not a table — `DeploymentStatusService.getForLead()` computes a fresh `{latestDeployment, domain, productionReady}` snapshot on every request from `WebsiteDeployment`/`Domain` directly, the same "compute fresh, nothing new stored" pattern as `WebsiteGenerationStatus` itself (D-088). Both live inside the Deployment Engine's own module (`EngineModule`) rather than a separate one, matching how `WebsiteStatusService` was folded into the Pipeline Engine in M10 despite being its own computed concern.

## M12 — Analytics & Reporting

The founder's module brief specified the objective (collect/aggregate/analyze/report platform data; must never modify business data or generate AI content; read-only), a research mandate (review all completed modules, identify reusable infrastructure, avoid duplication), sixteen analytics scope domains, fifteen named reports, an Analytics Provider abstraction naming six providers, five named independent engines (Analytics/Reporting/Dashboard/Aggregation/Export), daily/weekly/monthly/yearly/custom aggregation, CSV/PDF/Excel export (architecture only), eight dashboard widgets, four dedicated permissions, explicit logging requirements, explicit performance constraints, Future Compatibility reservations, and explicit constraints (no AI content generation, no mutation of any other module's data). An architecture was presented — grounded in a research pass across M1-M11 identifying `CostService`/`AuditLogService`/`BusinessAnalysis`/M10's `ReportingService` as required-reuse infrastructure — and approved with eleven founder Decisions refining it before implementation, recorded individually below (D-104 onward) after the roadmap-governance decision every other decision depended on.

### D-103: `docs/21-implementation-roadmap.md`'s M12 entry is superseded as an implementation spec — the roadmap file itself is untouched

**Context:** `docs/21`'s actual M12 entry describes a narrower module than the founder's live brief: four endpoints (`/analytics/overview`, `/analytics/pipeline`, `/analytics/reps`, `/analytics/cost`) and cost-ceiling alerting, versus the founder's sixteen-domain, fifteen-report, five-engine, provider-abstracted architecture. Unlike M10's roadmap conflict, this isn't two different modules sharing a number — it's the same underlying idea ("visibility into whether the tool is working and what it costs") at very different scope, so no AskUserQuestion was needed; the founder's live brief is a strict superset, not a contradiction. Founder's explicit Decision 1: the latest approved architecture is the implementation source of truth.
**Decision:** M12 is built exactly as specified in the founder's brief and the architecture approved in this conversation. `docs/21-implementation-roadmap.md` itself is **not edited** — its M12 entry becomes stale relative to what's actually built, a documented, deliberate gap (this entry), not a silent contradiction, the same treatment D-082 and D-092 gave M10's and M11's roadmap entries.

### D-104: `AnalyticsEngineService` — one method per data domain, direct reads of the M1-M11 table that already owns each fact, never a re-derivation

**Context:** Founder's explicit Decision 2: "Analytics must remain completely read-only. Do not duplicate business logic already implemented in previous modules. Reuse existing services whenever possible, including: CostService, ReportingService, AuditLogService, BusinessAnalysis, Deployment services. Analytics must aggregate existing data only."
**Decision:** `AnalyticsEngineService` owns fifteen methods, each mapped in its own class docblock to the founder's sixteen named Analytics Scope domains (several domains share one underlying table/query, e.g. Business Analysis + AI Usage both read `BusinessAnalysis`, Website Generation + Website Preview both read `GeneratedWebsite`/`PublishReadinessReport`). Every method reads a table an earlier module already owns and persists to — never introduces a parallel computation of a fact that module already decided. `getSalesFacts()` is a direct passthrough to M10's own `ReportingService.getDashboardStats()` (now exported from `crm/reporting/reporting.module.ts` specifically for this), not a re-query of `LeadCRM` — the same "read already-computed facts, never re-derive" boundary the Reporting Engine (M10, D-089) held toward the Pipeline Engine, and the Deployment Engine (M11, D-097) held toward M9's `PreviewReport`, now applied one level up. `getCostFacts()` calls `CostService.currentSpend()` for the live ceiling/spend snapshot rather than re-summing `CostEvent` itself for that figure. `AnalyticsEngineService` writes nothing — it has no `create`/`update`/`delete` Prisma calls anywhere in the file, verified directly by its own docblock's claim and by the module's e2e suite never asserting a mutation.

### D-105: `AnalyticsProvider` abstraction — `SelfHostedAnalyticsProvider` fully implemented, five reserved provider classes, business logic never imports a concrete provider

**Context:** Founder's explicit Decision 3: "Implement an Analytics Provider abstraction. Business logic must never depend on a specific analytics platform. For this module: Fully implement the SelfHostedAnalyticsProvider. Create provider interfaces for: PostHog, Google Analytics, Mixpanel, Azure Application Insights, Datadog. Future providers must be pluggable without changing business logic." The established shape for this exact pattern is `LocationProvider` (M5, D-033), reused verbatim in M11 for `DeploymentProvider` (D-093).
**Decision:** `AnalyticsProvider` (`name`/`version`/`isConfigured()`/`track(input)`) is the structural mirror of `DeploymentProvider`, injected everywhere behind the `ANALYTICS_PROVIDER` token via `ProviderModule` — a `useClass` swap is the only thing that would change which concrete provider is active. `SelfHostedAnalyticsProvider` is fully implemented: `track()` writes directly to the module's own `AnalyticsEvent` table (D-106) via Prisma, `isConfigured()` always `true`. `PostHogProvider`/`GoogleAnalyticsProvider`/`MixpanelProvider`/`AzureApplicationInsightsProvider`/`DatadogProvider` each genuinely implement `AnalyticsProvider` (extending a shared `UnimplementedAnalyticsProvider` base, `isConfigured()` false, `track()` rejects with "reserved for a future module") but carry no real adapter yet — same reserved-not-built stance as every other closed extension point in this codebase (M11's four reserved `DeploymentProvider` classes, D-093). This abstraction was initially built without being called anywhere else in the module — a self-caught gap, fixed before this module was considered complete: `DashboardEngineService`, `ReportingEngineService`, and `ExportEngineService` all inject `ANALYTICS_PROVIDER` and call `.track()` alongside their `Logger.log()` calls for the four user-facing events D-111 names, through a private `trackBestEffort()` method on each that mirrors `AuditLogService.record()`'s established best-effort contract (D-028: "a logging failure never fails the privileged action it's describing") — a tracking failure is caught, logged as a warning, and never allowed to fail the primary action it's describing.

### D-106: `AnalyticsEvent` — the only table Module M12 owns; a plain append-only log, no "current state" concept

**Context:** Founder's explicit Decision 4: "AnalyticsEvent is the only table owned by Module M12. No other module's tables may be modified by analytics. Analytics must never duplicate data already persisted elsewhere."
**Decision:** `AnalyticsEvent` (`eventType`/`entityType`/`entityId`/`actorId`/`provider`/`metadata`/`occurredAt`) is the single new model this module introduces, populated exclusively by `SelfHostedAnalyticsProvider.track()` — no other file in `apps/api/src/analytics/` calls `prisma.analyticsEvent.create()`, and no file anywhere in the codebase calls `.update()` or `.delete()` on it. It is neither an immutable-per-version row (`SalesProposal`, D-085; `WebsiteDeployment`, D-094) nor a mutable pointer (`LeadCRM`, D-083; `Domain`, D-096) — it has no lifecycle at all, just an append-only record of "this happened," the shape a real analytics platform's own event log would take. Every other fact the Analytics/Reporting/Dashboard/Export Engines expose is computed fresh from tables M1-M11 already own (D-104) — `AnalyticsEvent` itself is never read back to answer a report or dashboard query this phase, keeping the "analytics aggregates existing data only" boundary from also requiring this module to become its own data source.

### D-107: Aggregation Engine — one shared `bucketize()`/`resolveRange()` pair, every trend-shaped report and the dashboard both consume it

**Context:** Founder's explicit Decision 5: "Implement a shared Aggregation Engine supporting: Daily, Weekly, Monthly, Yearly, Custom Range. All reports and dashboards must consume this engine."
**Decision:** `AggregationEngineService.resolveRange()` turns a `{period, fromDate?, toDate?}` query into a concrete `{from, to}` window — `custom` requires both dates and rejects a malformed or empty range with `InvalidAggregationRangeException`; every other period defaults to `toDate ?? now()` and a period-specific lookback (`{daily: 30, weekly: 84, monthly: 365, yearly: 1825}` days) when no `fromDate` is given, bounding an unbounded scan by default per Decision 10. `bucketize()` sums arbitrary rows into a chronological `TimeSeriesBucket[]` covering every bucket in range including empty ones (a trend chart needs gaps represented, not skipped), with ISO Monday-start weeks hand-rolled in `bucket-math.ts` (no date library exists anywhere in this monorepo, confirmed by grep before deciding to hand-roll, matching the precedent `cost.service.ts`'s `secondsUntilNextUtcMonth()` and M11's `deployment-hash.ts` already set for small well-defined date/hash logic). Every method that produces a time series — `getConversionRateFacts()`, `getCostFacts()`, `getWebsiteGenerationFacts()` in the Analytics Engine — calls this same `bucketize()`, never a bespoke date-grouping written inline; the Dashboard Engine's widgets and the Reporting Engine's `executive_dashboard` report share one `resolveRange()` call per request (D-108), so a dashboard view and its corresponding report are always computed over the identical window.

### D-108: Dashboard widgets are lean slices of existing Analytics Engine facts; Executive Report and the live Dashboard share one composition, not two

**Context:** Founder's explicit Decision 6: "Dashboard widgets must be composed from existing analytics. Do not implement separate business logic for dashboards. Dashboard and Executive Report must share the same aggregation layer."
**Decision:** `DashboardEngineService.composeWidgets(range, period)` is a public method that runs eight `AnalyticsEngineService` calls in parallel via `Promise.all` and slices each result into the matching one of the founder's eight named widgets (Leads/Sales/AI Usage/Costs/Deployments/Website Status/Conversion/System Health) — it never queries Prisma directly itself. `ReportingEngineService`'s `executive_dashboard` report case calls this exact same `composeWidgets()` method rather than re-implementing the composition, satisfying Decision 6's explicit requirement literally: one implementation, two consumers (a live `GET /analytics/dashboard` view and a `GET /analytics/reports/executive_dashboard` drill-down), never two parallel widget-assembly code paths that could drift apart.

### D-109: Export — CSV genuinely implemented, PDF/Excel reserved at the schema layer and rejected at the service layer, never at validation

**Context:** Founder's explicit Decision 7: "Implement: CSV Export. Reserve architecture only for: PDF Export, Excel Export. Do not implement PDF or Excel generation."
**Decision:** `exportQuerySchema`'s `format` field accepts all three `EXPORT_FORMATS` (`csv`/`pdf`/`excel`) — the API contract never has to change shape when a future module implements the other two, only which values succeed — but `ExportEngineService.exportReport()` throws `ExportFormatNotImplementedException` (`501 Not Implemented`) for `pdf`/`excel` before ever calling `ReportingEngineService.generateReport()`, the same "schema accepts the closed set, service layer enforces which are actually live" split M10 established for `SalesProposal.status` transitions. `toCsv()` (`csv-formatter.ts`) hand-rolls RFC-4180-ish escaping (quote-wrap on comma/quote/newline, doubled internal quotes) rather than adding a CSV library for a handful of lines, matching this codebase's established precedent for small well-defined formatting logic (D-107). Every export runs through `ReportingEngineService.generateReport()` — the identical computation the JSON report endpoint uses, capped at `EXPORT_ROW_LIMIT = 1000` rows — never a second, parallel report implementation that formats data pulled from a different code path.

### D-110: Four dedicated analytics permissions, none reused from an earlier module; `sales_executive` holds none of them

**Context:** Founder's explicit Decision 8: "Create dedicated permissions: analytics:view, analytics:report, analytics:export, analytics:manage. Do not reuse previous permissions."
**Decision:** All four added to `PERMISSIONS`. `admin`/`sales_manager` hold all four. Unlike CRM (where a rep genuinely has their-own-leads data to see, D-090), every M12 analytics domain is inherently org-wide — Lead Funnel, AI Cost, Deployment health — the same "manager-tier visibility" class `cost:view` already restricts, so `sales_executive` holds none of the four. `developer`/`viewer` hold only `analytics:view`. `analytics:view` gates `GET /analytics/dashboard` — the rolled-up, broader-audience view; `analytics:report` gates `GET /analytics/reports/:type` — the full per-report drill-down (Audit, User Activity, full AI Cost breakdowns), materially more detailed/sensitive than a dashboard widget summary, restricted to admin/sales_manager only; `analytics:export` gates the CSV download endpoint, same restricted tier. `analytics:manage` is created and assigned to roles now, per the founder's explicit instruction, but enforced on no endpoint yet — reserved for the Future Compatibility management surface (D-113: Scheduled Reports/KPI Alerts configuration), the same "defined ahead of its first consumer" precedent `team:manage`/`cost:view` set at their own introduction.

### D-111: Structured logging and best-effort provider tracking for every event the founder named

**Context:** Founder's explicit Decision 9: "Log: Dashboard Viewed, Report Generated, Aggregation Completed, Export Started, Export Completed."
**Decision:** Each event is logged by the engine that owns it, matching M11's per-engine logging convention (D-100): `DashboardEngineService` logs and tracks Dashboard Viewed; `ReportingEngineService` logs and tracks Report Generated; `AggregationEngineService.bucketize()` logs Aggregation Completed (`period`, bucket count, row count) on every call; `ExportEngineService` logs and tracks both Export Started and Export Completed. Aggregation Completed is deliberately logged only, never tracked through `AnalyticsProvider` — it fires on every internal `bucketize()` call inside a single report/dashboard request (several times per request for a multi-series report), a high-frequency internal computation step, not a discrete user-facing action the other four events represent. The four tracked events all go through each engine's own `trackBestEffort()` method (D-105) — logging and tracking are two independent side effects of the same request, and a tracking-provider outage can never turn into a failed dashboard/report/export response.

### D-112: Reports avoid unnecessary scans by reusing existing reporting services and computing fresh rather than caching

**Context:** Founder's explicit Decision 10: "Reports must avoid unnecessary database scans. Where possible: reuse existing reporting services, paginate large datasets, aggregate efficiently. Do not introduce duplicated reporting queries."
**Decision:** `getSalesFacts()`'s direct passthrough to M10's `ReportingService` (D-104) is the clearest instance of "reuse existing reporting services" — no parallel `LeadCRM` scan exists anywhere in the Analytics Engine. `getAuditFacts()` is cursor-paginated (`take: limit + 1`, `cursor`/`skip`) rather than loading the full `AuditLog` table, the same pagination shape used elsewhere in this codebase. `AggregationEngineService.resolveRange()`'s default lookback windows (D-107) bound every non-custom-period query's date range rather than defaulting to an unbounded scan. No caching layer is wired this phase — every report/dashboard/export computes fresh on each request, the same deliberate "no caching yet, cache-ready shape" stance M10's `DashboardStats` took (D-089, itself answering the founder's own Decision 9 in that module) — `AnalyticsReportEnvelope`/`AnalyticsDashboard` are both plain JSON-serializable snapshots of `(range, period)` with no live cursors, the shape a future cache keyed on those same inputs could sit in front of without a redesign.

### D-113: Future Compatibility reservations — named, not built

**Context:** Founder's explicit Decision 11: "Reserve architecture for: Scheduled Reports, Email Reports, Webhooks, KPI Alerts, Predictive Analytics, Machine Learning Insights. Do not implement these features."
**Decision:** No code path in this module implements scheduling, email delivery, outbound webhooks, threshold alerting, or any predictive/ML model. The reservations that do exist are the ones already required to make a future module additive rather than a redesign: the `analytics:manage` permission (D-110) is the reserved authorization boundary a future Scheduled Reports/KPI Alerts admin surface would be gated behind; `AnalyticsReportEnvelope`'s plain-JSON, no-live-cursor shape (D-112) is what a future Email Reports feature would serialize and send without changing the Reporting Engine itself; the `AnalyticsProvider` abstraction's five reserved vendor classes (D-105) are what a future Webhooks/external-alerting integration would route through rather than a bespoke webhook sender built inside this module. Nothing was added purely speculatively beyond that — matching the same discipline D-101 (M11) applied to Blue/Green and Canary deployments, where no field was reserved for a capability that would layer on top of an existing contract rather than requiring a schema change today.

### D-115: `apps/admin-web` is a new app; `apps/web` is left untouched; the backend's Clerk-only auth model means there is no custom login form

**Context:** The founder's frontend folder structure named `apps/admin-web` as the app to build; the repository already had a near-empty, pre-existing `apps/web` scaffold (flagged as out of scope in the v1.0 review, D-113/§11). The entire "Login Page" requirement is satisfied by wrapping Clerk's own hosted `<SignIn/>`/`<SignUp/>` components inside a themed `(auth)` route group layout (`app/(auth)/layout.tsx`) — building a parallel credential form would either go nowhere (no backend endpoint to submit to) or duplicate Clerk's own authentication logic, both of which the founder's constraints rule out.

### D-116: Sidebar navigation visibility is a small, admin-web-local, presentation-only role table — not a copy of the backend's 27-permission enforcement matrix

**Context:** The founder's approved architecture (§6) needed a way to decide which of the eight top-level nav items a given role should see, matching the pre-existing `docs/17` rule that permission-gated items "simply don't render... not shown-then-disabled." The backend's actual enforcement matrix (`apps/api/src/common/rbac/permission.constants.ts`, 27 permissions × 6 roles) is backend application code — out of reach without either a prohibited backend change or a prohibited duplication of business logic into the frontend.
**Decision:** `apps/admin-web/src/lib/auth.ts` defines `NAV_ITEMS` — eight entries, each naming only the _roles_ allowed to see that nav item (not permissions), a deliberately coarse presentation-only table distinct in kind from the backend's fine-grained matrix. Every actual data fetch/mutation still goes through the real API and its real 403 (`FORBIDDEN`) response; a stale or wrong entry here can at worst show a nav item that then renders `<ErrorState code="FORBIDDEN"/>` on click, or hide one from a role that technically has access — never expose data the backend wouldn't already have served. This boundary was flagged explicitly in the approved architecture, not decided unilaterally during implementation.

### D-117: Theme preference is persisted client-side only (`next-themes` + localStorage/cookie) — not synced through `TeamMember`, a deliberate deviation from the pre-existing `docs/17`

**Context:** `docs/17-ui-ux-wireframes.md` §16 (written in Phase 3, before the backend existed) specified that theme preference should be "stored against `team_member`, not just local storage, so it follows the rep across devices." The actual, frozen `TeamMember` Prisma model (verified against `packages/db/prisma/schema.prisma`) has no such column, and the backend is explicitly frozen with "do not change backend contracts."
**Decision:** `ThemeToggle` (`src/components/layout/theme-toggle.tsx`) uses `next-themes` with `attribute="class"`, default `dark`, persisted only to the browser (localStorage, read via a blocking inline script to avoid a flash of the wrong theme) — never synced to any backend field. This was flagged explicitly in the approved architecture (§8) as a forced deviation from the older design doc, not silently dropped; cross-device sync remains a real gap a future backend change could close, not something F1 attempted to work around.

### D-118: A dedicated "Account not provisioned" state for the one 401 that survives Clerk's own middleware — not a redirect to sign-in

**Context:** `middleware.ts`'s `clerkMiddleware` already guarantees every request reaching `(dashboard)/layout.tsx` has a valid Clerk session. The layout's own `GET /me` call can still 401 in exactly one case: a valid session with no matching (or soft-deleted) `TeamMember` row — the backend's own `ClerkAuthGuard` treats this identically as unauthenticated ("webhook sync hasn't landed yet, or the account was offboarded"). An initial draft redirected this case to `/sign-in`.
**Decision:** Redirecting was rejected during implementation, not shipped: since the Clerk session is still valid, `/sign-in` would immediately bounce the person back (Clerk's own `<SignIn/>` detects the active session and redirects to `fallbackRedirectUrl`), producing a redirect loop rather than a helpful message. `(dashboard)/layout.tsx` instead renders a dedicated `<NotProvisioned/>` component explaining the account isn't linked yet, with a sign-out action — the correct resolution for this specific case, not a generic error fallback.

### D-119: Every Radix- or React-Hook-Form-wrapping component in `packages/ui` requires an explicit `'use client'` directive — discovered via a real production build failure, not assumed upfront

**Context:** `packages/ui` is consumed across a genuine package boundary by `apps/admin-web`'s App Router, which bundles Server and Client Components separately (React's `react-server` module condition). A first build of `app/not-found.tsx` — a Server Component importing only `Button` from the `@riznexia/ui` barrel — failed: `react-hook-form`'s `react-server` export condition build lacks `FormProvider`/`Controller`/`useFormContext` entirely (they're meaningless in a server-only context), and Next's bundler evaluates the _whole_ barrel module graph for any import from it, pulling in `form.tsx` even though `not-found.tsx` never uses `Form`.
**Decision:** `'use client'` was added to every component file with a Radix primitive, `react-hook-form` hook, or other browser-only dependency (`avatar.tsx`, `button.tsx`, `dropdown-menu.tsx`, `error-state.tsx`, `form.tsx`, `input.tsx`, `label.tsx`, `separator.tsx`, `sheet.tsx`, `tooltip.tsx`) — deliberately all of them, rather than reasoning file-by-file about which ones happen to get imported into a Server Component today, since a future consumer could trigger the identical failure through any one of them. `skeleton.tsx` and `lib/utils.ts` (pure markup/pure function, no hooks) were left as-is. Caught by an actual `next build` run — the `typecheck`/`lint`/unit-test suites all passed with this bug still present, underscoring why a real production build is part of this module's own validation sweep, not merely typecheck/lint/test.

### D-120: Every top-level route ships as a real, navigable page in F1 — a shared `<FeaturePlaceholder/>`, never F2-F15's actual content

**Context:** The founder's brief: "This module should prepare everything required by all future frontend modules," paired with "Build only F1. Do not start F2."
**Decision:** All eight `(dashboard)` routes (`/`, `/discovery`, `/leads`, `/crm`, `/analytics`, `/team`, `/settings`, `/profile`) exist as real Next.js pages today, each rendering `<FeaturePlaceholder moduleId="F_" title="..."/>` — so the sidebar, header, breadcrumb, and route guards are all fully exercisable end-to-end now, without pre-building any business screen a later module owns. This includes `/` itself: the Dashboard _home screen_ is F2's own content, not F1's, so it renders the same placeholder as every other stub route rather than real widgets.

### D-121: `packages/config-eslint`'s Next.js default-export exception list is extended, not the underlying "named exports only" rule — an additive tooling fix, not a previous-module change

**Context:** `packages/config-eslint/nextjs.js` already carved out an exception to Doc 12 §1's "named exports only" rule for Next.js framework-reserved files requiring a default export (`page.tsx`, `layout.tsx`, `loading.tsx`, `error.tsx`, `not-found.tsx`, `route.ts`, and config files). F1 introduced three more framework-mandated default-export files this list didn't yet cover: `global-error.tsx` (Next's root-crash boundary), `middleware.ts` (Next requires its exported middleware function be the default export), and `vitest.config.ts`/`.mts` (Vite/Vitest's own convention).
**Decision:** The existing exception list gained three entries (`**/app/**/global-error.tsx`, `**/middleware.ts`, `vitest.config.*`) rather than disabling the rule more broadly or working around it per-file. This is judged additive shared-tooling maintenance, not a "modify previous modules" violation — it changes no backend behavior, no API contract, and no rule's meaning for any file outside these three new, genuinely framework-mandated cases; verified by re-running `pnpm lint` across the full monorepo afterward with zero change in outcome for every non-frontend package.

### D-122: RBAC Alignment — sidebar/route-guard/component visibility is driven by a derived permission set, not a role list; supersedes D-116's coarser role-per-nav-item table

**Context:** Approved F1 shipped nav visibility as a per-item `allowedRoles: TeamRole[]` list (D-116) — functionally correct, but a "which roles can see this" table is one abstraction layer further from the backend's actual model than necessary, and doesn't generalize to "can this specific button render" the way the backend's own `resource:verb` permission vocabulary does. Founder's explicit follow-up brief: navigation visibility must be permission-driven, route guards must support permissions, components must support permission-based rendering, roles must never be hardcoded inside UI components, with no new API call and no backend contract change.
**Decision:** A new `apps/admin-web/src/lib/permissions.ts` mirrors the backend's `PERMISSIONS`/`ROLE_PERMISSIONS` (`apps/api/src/common/rbac/permission.constants.ts`) verbatim — the same category of presentation-only mirror D-116 already established as acceptable, now covering the full 27-permission taxonomy instead of a coarse 8-row nav table, since the founder's brief explicitly names this pattern ("permissions may be derived from the authenticated user session") rather than leaving it an open judgment call this time. `getPermissionsForRole(role)` is called exactly once, in `AppShell`, from the `TeamMember.role` already returned by the existing `GET /me` call `(dashboard)/layout.tsx` makes — no new endpoint, no new field, no second request. The derived `Set<Permission>` is exposed via a client-only `PermissionsProvider` (`permissions-context.tsx`) and consumed through `usePermissions()`/`useHasPermission()`/`useHasAnyPermission()` — `Sidebar`, `MobileSidebar`, `SidebarNav`, and `Header` no longer take a `role` prop at all, and no component anywhere in `apps/admin-web` branches on `TeamRole` directly outside `permissions.ts` itself. `auth.ts`'s `NAV_ITEMS` changed from `allowedRoles: TeamRole[]` to `requiredPermission: Permission | null` (`null` meaning "visible to any authenticated, provisioned session" — Dashboard/Discovery/Leads, gated by nothing today), each value chosen to reproduce the exact visibility D-116 already shipped, verified item-by-item against the backend's real grants, not re-decided. A new `route-guard.ts` (`assertPermission()`/`hasPermission()`/`hasAnyPermission()`, calling `notFound()` on failure) gives Server Components the same capability for gating a whole route once a future module needs it — unused by any route today, since no F1 page requires more than "authenticated and provisioned," but present and tested ahead of its first real consumer, per the founder's "future-compatible" requirement. A new `<PermissionGate permission=".."/anyOf={[...]}>` (`components/auth/permission-gate.tsx`) gives any future component the same capability inline. None of this changes what any request is actually allowed to do — the backend's own guards remain the sole authority, unchanged; this entire layer is presentation-only, exactly as D-116 already established, now expressed in the backend's own vocabulary instead of a bespoke role list.

## F2 — Dashboard (Frontend)

The founder's brief pointed at the two dashboard endpoints the backend already exposes (`GET /analytics/dashboard`, M12; `GET /crm/dashboard`, M10) rather than the pre-M10 `docs/17` wireframe, which describes KPI cards and activity feeds no single endpoint actually backs. A complete architecture was presented — including two open questions flagged for the founder's own call rather than decided silently (what a `sales_executive`, who holds neither `analytics:view` nor `crm:report`, sees; whether a charting library is needed at all) — and approved, with two additional founder-requested improvements (a Dashboard Widget Registry; configurable auto-refresh) folded in before implementation. Decisions below record how the architecture's two open questions were resolved and how the two improvements were built.

### D-123: Dashboard Widget Registry — mirrors the backend's own `VALIDATOR_REGISTRY` idiom; each widget is a fully self-contained, independently data-fetching component

**Context:** Founder's explicit improvement request: "The Dashboard must not directly know every widget. Instead: Dashboard → Widget Registry → Individual Widgets. This keeps the dashboard extensible for future widgets." The backend already has exactly this shape for an analogous problem — `packages/website-preview/src/validation/validator-registry.ts`'s `WebsiteValidator` interface + `VALIDATOR_REGISTRY` array (M9, "a future validator is added by writing one new file... no existing validator file changes").
**Decision:** `src/features/dashboard/widgets/widget.interface.ts` defines `DashboardWidgetDefinition` (`id`/`requiredPermission`/`component`); `widget-registry.tsx`'s `DASHBOARD_WIDGETS` array is the only file that imports all eight individual widget components, and `WidgetRegistry` (the only thing `DashboardHome` itself renders) filters that array by the ambient `PermissionsProvider` and renders whatever survives. Each widget (`LeadsWidget`, `SalesWidget`, ...) is fully self-contained — it calls the shared `useAnalyticsDashboard()` query hook itself rather than receiving data as a prop, so the registry never needs to fetch or thread data through; TanStack Query dedupes the identical query key across all eight mounted components into one network request, not eight. `requiredPermission` is set per-entry (all eight currently share `analytics:view`, since they're all slices of the one M12 endpoint) rather than gating the whole registry once, so a future widget backed by a different endpoint/permission — e.g. a `cost:view`-gated widget — is a one-line addition to the array plus one new self-contained widget file, never a change to `WidgetRegistry` or `DashboardHome`.

### D-124: Configurable auto-refresh — one shared `RefreshIntervalProvider`, `refetchInterval` passed straight to every dashboard query, no bespoke polling code

**Context:** Founder's explicit improvement request: support Manual/30s/1m/5m auto-refresh "using TanStack Query refetch intervals... do not create additional backend endpoints."
**Decision:** `src/features/dashboard/refresh-interval.tsx`'s `RefreshIntervalProvider` holds one piece of state (`'manual' | 30_000 | 60_000 | 300_000`) shared by the whole dashboard tree, mounted once in `DashboardHome`; `useQueryRefetchInterval()` maps `'manual'` to `false` (TanStack Query's own "disable polling" value) and passes every numeric option straight through — no custom timer/interval code anywhere. Every dashboard query hook (`useAnalyticsDashboard`, `useCrmDashboard`, `useMyTasks`) reads this same hook and passes its result as `refetchInterval`, so selecting an interval once governs every section at once, not a per-widget setting. `DashboardToolbar`'s manual "Refresh now" button calls `queryClient.invalidateQueries()` against all three dashboard query keys regardless of which sections are actually mounted for the current role — the same button works whether a viewer sees the full widget grid or a `sales_executive` sees only the "My Work" fallback (D-125). No backend endpoint changed or was added; auto-refresh is purely a client-side polling cadence against the same two endpoints F2's architecture already named.

### D-125: `sales_executive` sees a "My Work" task list, not an empty dashboard — the architecture's open question 1, resolved as recommended

**Context:** The approved F2 architecture flagged, rather than silently decided, that `sales_executive` holds neither `analytics:view` nor `crm:report` and therefore has no endpoint returning any aggregate dashboard data, with three options presented: a scoped "My Work" worklist, the existing `<FeaturePlaceholder/>` treatment, or founder-directed alternative. Approved without pushback, taken as approving the recommended option.
**Decision:** `DashboardHome` branches structurally on `useHasPermission('analytics:view')`/`useHasPermission('crm:report')` — a role holding neither renders `<MyWorkPanel/>` instead of the widget grid or CRM section. `MyWorkPanel` calls a new `useMyTasks()` hook against `GET /crm/tasks?assignedToId=<self>&limit=5` — an endpoint `sales_executive` already holds `crm:view` for, using `id` from the already-fetched `TeamMember` (via a new `CurrentUserProvider`, D-126) rather than a second `/me` call. Deliberately not a KPI dashboard — `PaginatedCrmTasks`/`PaginatedLeads` are both cursor-paginated with no `total` field, so a real "leads assigned to me" count isn't cheaply obtainable without paging through everything, which does not belong on a dashboard; a short, un-totaled worklist is what the data actually supports.

### D-126: `CurrentUserProvider` — the session's already-fetched `TeamMember` made available by context, mirroring `PermissionsProvider`'s shape, for the one case a permission check isn't the right tool

**Context:** `MyWorkPanel` (D-125) needs the current session's own `id` to filter `GET /crm/tasks?assignedToId=`. `PermissionsProvider` (RBAC Alignment, D-122) already derives from the same `TeamMember` `AppShell` receives, but exposes only a permission set, not the identity fields a "my own records" query needs.
**Decision:** `src/lib/current-user-context.tsx` adds a second, minimal context — `CurrentUserProvider`/`useCurrentUser()` — mounted in `AppShell` alongside `PermissionsProvider`, both deriving from the one `TeamMember` the layout already fetched via `GET /me`. No second request, no duplicated fetch; this is additive read access to data the tree already has, not a new data source.

### D-127: No charting library added — pipeline-by-stage and system-health render as hand-rolled proportional bars, matching this codebase's own precedent for small, well-defined visual logic

**Context:** The approved F2 architecture flagged, as its second open question, that no chart library exists in F1's frozen stack (Tailwind/shadcn/Lucide/Framer Motion) despite the pre-M10 `docs/08` naming Recharts. Presented as a real open decision, tentatively defaulting toward Recharts if no objection was raised.
**Decision:** On inspecting the eight M12 widget shapes and the M10 pipeline-by-stage data directly (not assumed), none of them need a real charting library — every M12 widget is a single number, a percentage, or a two/three-way count; the only genuinely visual need is pipeline-by-stage's proportional value-per-stage comparison and system-health's three-way breakdown, both cleanly expressible as a handful of `<div>`s with a Tailwind-driven `width` percentage. This matches this codebase's own established precedent for small, well-defined visual/formatting logic (`bucket-math.ts`, `csv-formatter.ts` on the backend) — hand-roll rather than add a dependency for a genuinely small need. No charting library was added to `apps/admin-web`'s `package.json`; `CrmPipelineSection`'s bar list and `CostsWidget`/`SystemHealthWidget`'s progress bars are all plain markup. This resolution is a deliberate reversal of the architecture proposal's own tentative Recharts default, made once the real widget shapes were inspected rather than assumed — flagged here, not silently substituted.

## F3 improvement — Shared Data Table

Founder approved F2 and, before authorizing F3, requested one improvement: a reusable, fully generic Data Table in `packages/ui` (server-side pagination, sorting, global search, column filters, column visibility, row selection, bulk actions, empty/loading/error states, responsive layout) with an explicit constraint — "no business-specific logic, no Lead-specific logic, future modules must reuse this component." Two decisions governed how genericness and this system's own pagination reality were reconciled.

### D-128: `@tanstack/react-table` used as the engine, not a hand-rolled table — the one exception to this codebase's small-well-defined-logic precedent

**Context:** D-127 (immediately above) and the backend's own `bucket-math.ts`/`csv-formatter.ts` establish a real precedent in this codebase: hand-roll small, well-defined logic rather than add a dependency. **Decision:** `packages/ui/src/components/data-table/` is built on `@tanstack/react-table` (^8.20.5) — same vendor family as TanStack Query, already a frozen dependency since F1. `DataTable<TData>` is fully generic over its row type; genericness is proven directly by its own test suite using a made-up `Widget` type, deliberately not `Lead` or `DiscoveryJob`, so the tests themselves can't hide an accidental business-specific assumption. Two consumer-facing conventions keep the component itself free of domain knowledge: a `columnDef.meta: {label, filterVariant, filterOptions}` declarative convention (the toolbar renders whatever filter UI a column's own meta describes, never hardcoding which columns exist) and an auto-injected synthetic selection column (`__select__`) only when `enableRowSelection` is set. No Lead or Discovery import appears anywhere under `packages/ui`.

### D-129: `DataTable`'s `'server'` pagination mode is modeled on cursor pagination (`hasNextPage`/`onNextPage`/`onPreviousPage`), not a page-index picker

**Context:** The founder's brief said "server-side pagination" without specifying its shape. Every real paginated endpoint in this system (`GET /leads`, `GET /crm/tasks`, etc.) is cursor-based — `cursor`/`nextCursor`, no `total` count, no arbitrary page-N jump — a fact confirmed by reading the actual backend contracts rather than assuming a generic REST page-number convention.
**Decision:** `DataTablePaginationConfig`'s `'server'` variant is `{mode: 'server', pageSize, hasNextPage, hasPreviousPage, onNextPage, onPreviousPage, isFetching?}` — Prev/Next only, no page-number control, matching what every real backend endpoint this table will ever be wired against can actually support. `'client'` mode (page-size select + Prev/Next + "Page X of Y", computed entirely by TanStack's own `getPaginationRowModel`) exists for the one case that needs it in F3 itself — Discovery History's client-side pagination over its already-fully-loaded top-50 response (D-131 below) — not as a hypothetical future feature.

## Dev Tooling — Local Development Authentication Mode

The founder's own local run of the full stack (no Docker on the dev machine, so Postgres/Redis were substituted with Postgres.app + Homebrew Redis) hit a hard wall: no real Clerk application/credentials exist locally, so every route in `apps/admin-web` — including `/sign-in` itself, whose interactive widget depends on Clerk's remote script — was unreachable. The founder explicitly requested a **local-development-only** authentication bypass, with firm boundaries: never touch production auth, never weaken any production code path, and the bypass must require two independent conditions to ever activate.

### D-182: `DevAuthService` — backend Clerk bypass gated on `NODE_ENV=development AND DEV_AUTH_ENABLED=true`, added as a single early-return branch, real Clerk path left byte-for-byte unmodified

**Context:** `ClerkAuthGuard` is the single global `APP_GUARD` every non-`@Public()` route passes through (`apps/api/src/common/guards/clerk-auth.guard.ts`). Any bypass has to live here, but must not touch the real verification logic at all, so a bug in the bypass can never regress real auth, and a code reviewer can see at a glance that the real path is unchanged.
**Decision:** New `apps/api/src/auth/dev-auth.service.ts` (`DevAuthService`) exposes `isEnabled()` (`ConfigService.get('NODE_ENV') === 'development' && ConfigService.get('DEV_AUTH_ENABLED') === 'true'` — both required, read fresh per call, no caching) and `getDevRequestUser()` (looks up the real seeded Super Admin fixture by its exact `packages/db/prisma/seed.ts` `clerkUserId`, `'user_fixture_super_admin'`, and maps it through the same `TeamMemberService.toRequestUser()` the real path already uses — identical `RequestTeamMember` shape, so nothing downstream of the guard (permission checks, `/me`, any handler) can tell the difference). `ClerkAuthGuard.canActivate()` gained exactly one new `if (this.devAuthService.isEnabled())` block, inserted before the existing token-extraction line — every line of the real Clerk verification path is untouched, not refactored, not reordered. `super_admin: PERMISSIONS` in `permission.constants.ts` ("everything, unconditionally") means loading the real Super Admin row already satisfies "grant all permissions" — no separate override mechanism was needed. Registered in `AuthModule`; `apps/api/.env.example` documents `DEV_AUTH_ENABLED=false` as the safe default. Tests: `dev-auth.service.spec.ts` (new) plus `clerk-auth.guard.spec.ts`'s existing suite now explicitly asserts `devAuthService.isEnabled()` defaults to `false`, proving every pre-existing test still exercises the real, unmodified Clerk path.

### D-183: Frontend dev-auth — `middleware.ts` and `(dashboard)/layout.tsx` gain the same two-condition branch; a module-aliased Clerk shim replaces `@clerk/nextjs` client-side only in this mode, so none of the ~48 existing `useAuth()` call sites needed to change

**Context:** Bypassing the backend alone wasn't sufficient — `clerkMiddleware()`'s `auth.protect()` runs before any page renders, and even after routing past it, `(dashboard)/layout.tsx`'s `auth()` call and every feature hook's `useAuth().getToken()` (~48 files, verified by grep — only ever destructuring `{ getToken }`) depend on Clerk's client script actually loading. With only a placeholder Clerk key, `window.Clerk` never becomes ready, and `getToken()` never resolves — discovered directly during verification: the Leads table (and every other data-driven page) rendered an empty, permanently "loading" DataTable with zero console errors, because the request never even fired.
**Decision:** `src/lib/dev-auth.ts` exports one computed constant, `isDevAuthEnabled` (`process.env.NODE_ENV === 'development' && process.env.DEV_AUTH_ENABLED === 'true'`), imported by both `middleware.ts` and `(dashboard)/layout.tsx`. `middleware.ts` branches at the module's top level: `isDevAuthEnabled ? devAuthMiddleware : clerkMiddleware(...)` — the real `clerkMiddleware(...)` call is the exact same call that existed before, never reached in dev-auth mode, not modified. `devAuthMiddleware` redirects `/sign-in`/`/sign-up` straight to `/` and lets everything else through. `(dashboard)/layout.tsx` skips its `await auth()` call in dev-auth mode (calling real Clerk's `auth()` when `clerkMiddleware()` never ran for the request throws) and passes `token: null` to `GET /me`, which the backend's own bypass (D-182) ignores entirely. For the `useAuth().getToken()` hang specifically: `next.config.mjs` conditionally aliases the bare `@clerk/nextjs` specifier (webpack `resolve.alias['@clerk/nextjs$']` + `turbopack.resolveAlias`, both — `next dev`'s default bundler varies by version) to `src/lib/dev-clerk-shim.tsx`, a same-shape local module exporting `ClerkProvider` (passthrough), `useAuth` (`{ getToken: async () => null }`), `useClerk`, `SignOutButton`, `SignIn`, `SignUp` — verified against the exact shape this codebase actually destructures from each (only `getToken` off `useAuth()`, only `signOut` off `useClerk()`). `@clerk/nextjs/server` (middleware.ts, layout.tsx's own import) is untouched by the alias — only the client entry is swapped. ### D-186: Pre-existing, app-wide bug — every `[--color-*]` Tailwind arbitrary-value utility compiled to invalid, no-op CSS under the installed Tailwind v4; fixed by converting all 126 affected files to the `(--color-*)` syntax v4 actually requires

**Context:** Verifying the rebrand's new `--color-accent-foreground` token in a real browser, the "New Task" button and the active sidebar nav item both showed a fully transparent background — reproducible even on a freshly opened tab with a fully cleared `.next` cache, ruling out the "stale browser tab" pattern seen earlier in this session. Inspecting the actual served CSS (`fetch()`'d from the page, not assumed) showed the generated rule was `.bg-\[--color-accent\] { background-color: --color-accent; }` — a literal, unwrapped custom-property name with no `var(...)`, which is invalid CSS the browser silently drops. Tailwind v3 auto-detected a bracket value starting with `--` and wrapped it in `var()`; Tailwind v4 (the version actually installed here, `4.3.3`) removed that shorthand from square-bracket syntax — `[--foo]` is now always used as the literal arbitrary value verbatim, and the CSS-variable-shorthand is spelled with parentheses instead: `(--foo)` → `var(--foo)`. This codebase was written entirely in the v3 spelling, so **every themed color in every module built so far — F1 through F10, not just this rebrand's own additions — has been invisible in a real browser for the app's entire history**; this is almost certainly what the founder meant by "UI zero hai."
**Decision:** `grep -rlE '\[--color-[a-zA-Z0-9-]+\]'` found 126 affected files across `apps/admin-web/src`, `apps/admin-web/app`, and `packages/ui/src`; a single `sed -E 's/\[(--color-[a-zA-Z0-9-]+)\]/(\1)/g'` pass converted every occurrence (`bg-[--color-accent]` → `bg-(--color-accent)`, including compound/variant forms like `group-[.toast]:bg-[--color-accent]` and `focus-visible:ring-offset-[--color-bg-canvas]`) with zero remaining bracket-syntax occurrences afterward (re-grepped to confirm) and zero other `[--*]` custom-property patterns left unconverted. Verified with a computed-style check in a real browser tab post-fix: the "New Task" button and active nav item now resolve to `rgb(217, 181, 101)` background / `rgb(22, 34, 58)` text — exactly `#d9b565` / `#16223a`, the intended dark-mode gold-on-navy pair — across both dark and light mode, on the Dashboard, Leads, and Sales CRM pages. Full `@riznexia/ui` (40 tests) and `@riznexia/admin-web` (338 tests) suites plus a full `tsc --noEmit` pass all stayed green through the rewrite, since it only ever changed a class-string literal's delimiter, never a value or a component's structure.

### D-201: Deployment Settings shows real deployment stats (`deployment` report); provider/project/domain configuration is server environment variables with no GET endpoint, never guessed at

**Context:** `VERCEL_TEAM_ID`/`GITHUB_ORG`/etc. are environment variables read by `VercelAdapter`; the M11 `DeploymentProvider` abstraction is a DI-registration-time wiring choice (`DEPLOYMENT_PROVIDER` token), not a stored, API-readable setting.
**Decision:** `DeploymentSettingsPage` fetches `GET /analytics/reports/deployment` (gated `analytics:report`), reusing `ReportView`'s existing `DeploymentReportView` verbatim, and marks Provider/Default Project/Production Domain/Preview Domain/Team as `NotConfigurable`, linking to the real Deployment dashboard (F11) instead.

### D-202: Cost & Budget reuses the real `ai_cost` report and `ReportView`; Custom Range is deliberately not offered here, to avoid reproducing a known F12 bug in new code without touching F12 itself

**Context:** This module's own code-review pass (conducted immediately before F13 began, at the founder's request) found a real, already-confirmed defect in F12's `use-analytics-period.ts`/`PeriodRangeSelect`: `isCustomRangeIncomplete` is computed but never checked by any F12 consumer before firing the report query, so selecting "Custom Range" fires `GET /analytics/reports/:type?period=custom` with no `from`/`to` and the backend correctly 400s (`InvalidAggregationRangeException`) before the user has picked dates. Per this module's own "before changing any previous frontend module, verify it is absolutely necessary" rule, fixing F12's shared hook was judged not necessary for F13's own scope.
**Decision:** `CostBudgetPage` uses a small local `useState<AggregationPeriod>` toggle (Daily/Weekly/Monthly/Yearly only, no Custom Range option, no dependency on `useAnalyticsPeriod`/`PeriodRangeSelect` at all) against `GET /analytics/reports/ai_cost` (gated `analytics:report`), rendered via the existing `ReportView`/`AiCostReportView` verbatim. The over-ceiling warning banner (≥80%) is computed client-side purely from the two real numbers (`currentMonthSpendUsd`/`monthlyCeilingUsd`) the report already returns — a presentational threshold, not a fabricated business rule. F12's own Costs page and its underlying hook are untouched; the known bug is flagged here rather than fixed, since fixing it was outside this module's requested scope.

### D-203: Analytics Settings states real, verifiable fixed system behavior (CSV-only export, 1000-row cap) — never an invented retention/threshold setting

**Context:** M12 has zero configuration surface anywhere — no retention policy, no configurable threshold, no per-user export-format preference is stored or readable via any endpoint. The brief explicitly warns "do not invent retention settings."
**Decision:** `AnalyticsSettingsPage` states two real, code-verified facts (`ExportEngineService`'s hard-coded 1000-row cap; `pdf`/`excel` accepted by the request schema but rejected with `EXPORT_FORMAT_NOT_IMPLEMENTED` before any report runs, per M12/D-192's own precedent) as fixed system behavior, not as editable settings, plus a `NotConfigurable` block naming what genuinely has no config surface.

### D-204: System Information shows only the one real, live signal (`GET /health`) — every other named field is honestly "Not available," never a hard-coded guess that could go stale the moment the backend actually changes

**Context:** `HealthController` (`apps/api/src/health/health.controller.ts`) returns exactly `{status: 'ok', timestamp}` — no version, build identifier, git commit, environment name, database-connectivity status, or cache-connectivity status is exposed by this or any other endpoint anywhere in the backend.
**Decision:** `SystemInformationPage`'s `useHealth()` hook polls the real, public (`@Public()`, no token) `/health` endpoint every 30s and shows a live Reachable/Unreachable status plus the real server timestamp and real last-checked-at time. Application Version/Build Version/Git Commit/Environment/Database Status/Cache Status/Backend Version all render via `NotConfigurable` — a hard-coded `"v0.1.0"` (from `package.json`, itself not exposed via API) would be a guess presented as live data, which is exactly what the brief's "Research First" rule forbids.

### D-205: Audit History reuses F12's `AuditLogsPage` component verbatim — literally the same component, not a re-implementation against the same endpoint

**Context:** The brief is explicit: "Reuse existing audit APIs. Never build a second audit system." F12 already built a complete, tested `AuditLogsPage` (`GET /analytics/reports/audit`, gated `analytics:report`, cursor-paginated `DataTable`).
**Decision:** `app/(dashboard)/settings/audit/page.tsx` renders a thin `SettingsAuditHistoryPage` wrapper that imports and renders F12's `AuditLogsPage` directly, inside F13's own `SettingsAccessGate`/`SettingsSubNav` shell — zero duplicated table/column/pagination/gating logic. F12's component, its own internal `AnalyticsSubNav`, and its own `analytics:report` gate are unmodified and untouched; F13 adds nothing but the outer Settings-section chrome.
